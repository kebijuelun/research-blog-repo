# JetSpec++：并行草稿与验证，解码再提速

大模型逐 Token 生成文本，每一步都要等待上一步完成，回答越长，延迟越容易累积，直接影响交互体验。投机解码用“小模型先猜、大模型再验”减少等待，但草稿模型一旦变强、计算变贵，自身也会成为瓶颈。JetSpec++ 将下一块草稿的生成与当前块的验证放到两张 GPU 上并行，并利用等待时间反复修正草稿。在两块 GB200 上，它让 Qwen3-8B 的 BF16 解码达到 1,361 Token/s，相对自回归解码最高提速 7.45 倍，相对 DSpark 最高提速 1.54 倍，同时保持输出分布不变。

这套方法的价值不只是提高吞吐数字，更在于重新安排草稿模型的工作时间：原本串行等待的计算，被放进了目标模型验证的空档。

## 草稿更强，为什么反而更慢

自回归解码是大模型常见的生成方式：模型根据已有上下文预测下一个 Token，把它接回上下文，再预测后一个。由于计算存在串行依赖，目标模型每前进一步，通常只能提交一个 Token。

投机解码（Speculative Decoding）引入成本更低的草稿模型，让它一次提出多个候选 Token，再由目标模型并行验证。目标模型不必逐个生成这些候选，只需判断哪些可以接收，因此一轮验证有机会提交多个 Token。

收益取决于两个条件：草稿要足够便宜，候选也要足够容易被目标模型接受。草稿太弱，验证经常提前拒绝，浪费计算；草稿太强，生成候选的时间又会拉长。尤其是一类会读取目标模型隐藏状态的草稿模型，虽然预测更准，却往往要等上一轮验证结束、拿到最新状态后才能开始。

于是，目标模型验证时，草稿模型可能在等待；草稿模型生成时，目标模型又可能在等待。两份计算能力没有充分重叠，草稿成本始终留在关键路径上。JetSpec++ 要解决的正是这段空闲时间。

## 如何提前生成下一块草稿

JetSpec++ 将目标模型和草稿模型分别放在两张 GPU 上。目标模型验证第 t 个块时，草稿模型不再空等，而是提前生成第 t+1 个块；验证完成后，如果提前准备的结果符合实际情况，就能直接接续下一轮。

难点在于，第 t 个块尚未验证完，草稿模型既不知道最终会接受多少个 Token，也不知道验证结束时额外产生的锚点 Token（bonus anchor token）是什么。如果连起点都猜错，提前生成的下一块就无法使用。

为此，JetSpec++ 采用“预见式草稿”（foresight drafting）：先预测当前验证可能出现的结果，再针对若干较有把握的结果分别准备草稿。每个预期结果包含被接受的草稿 Token 数量和随后的锚点 Token。系统把对应的下一块草稿填入投机缓存，相当于提前准备几条可接续的路线。

验证结束后，真实结果若命中缓存，匹配的草稿就成为下一块；若没有命中，系统则退回普通的投机解码步骤。预测只用于提高并行效率，不要求每次都猜对，更不会把未经验证的内容直接提交给用户。

笔者认为，这个设计的聪明之处在于，它没有强行消除不确定性，而是用有限的候选缓存覆盖较可能出现的未来：命中时获得并行收益，未命中时仍有明确的保守路径。

## 预测隐藏状态，补上提前计算的信息

提前生成草稿还缺少目标模型在当前块上的隐藏状态。隐藏状态是模型内部对上下文的中间表示，能帮助草稿模型判断目标模型接下来更倾向输出什么。但真实状态要等目标模型计算后才会产生，提前生成草稿就必须先做出预测。

JetSpec++ 的预见式草稿由适配器、解码器和草稿模型组成。适配器通过一次并行前向计算，预测当前待验证块中每个位置的目标隐藏状态；解码器复用目标模型最后几层的冻结权重，再接上目标模型最终的归一化层和语言模型输出头，把预测状态转换为输出分布。

这样，解码器一次计算就能给所有候选验证结果打分，草稿进程再挑选较有希望的结果，批量生成对应草稿。复用冻结权重而非另起一套完整大模型，也是在利用目标模型已有的表示能力。

预测状态终究不等于真实状态，因此仍需上下文刷新。项目页给出的结果是，在不进行上下文刷新的情况下，草稿模型仍能保留使用真实目标状态时所达到接受长度的 95%–98%。近似状态会带来损失，但尚不足以抵消并行化的价值。

## 用等待时间继续修正草稿

完成第一版下一块草稿后，验证可能还没有结束。JetSpec++ 会利用剩余时间进行自我修正（self refinement），让草稿模型在并行计算中修改候选，提高随后能被目标模型接受的长度。

这一过程包含三种操作：

- **Jacobi 迭代**：每轮更新时，各个位置基于上一轮已生成的 Token 并行提出新值，而不是严格等待前一个位置完成。它用并行计算换取更多草稿改进机会。
- **上下文刷新**：适配器针对当前草稿重新预测目标隐藏状态，让后续修改使用更新后的上下文信息。
- **锚点替换**：解码器寻找自己最有把握的 Token 与草稿首次出现分歧的位置，并替换该位置的 Token；下一轮只需重新生成其后的位置。

三种操作分别处理候选 Token、上下文表示和首个分歧点，目标都是把验证期间的空档转化为草稿改进机会，而不是增加一次更昂贵的串行计算。

## 加速但不改变输出分布

草稿生成得更快、更激进，会不会改变最终回答？JetSpec++ 给出的“无损”保证，依据并不是草稿预测足够准确，而是最终提交的每个 Token 仍要经过目标模型验证。

系统使用拒绝采样接受规则决定哪些 Token 可以提交。缓存预测错误只会导致草稿无法复用，自我修正不充分也只会影响接受长度；它们影响速度，不改变最终输出分布。因此，这里的“无损”是生成分布层面的保证，不应理解成所有系统在所有实现细节下都逐位一致。

这也解释了为什么 JetSpec++ 可以同时追求更高的每轮接受 Token 数和更激进的流水并行：正确性由最后的验证环节把守，前序模块可以专注于提高效率。

## 两块 GB200 上的速度与接受长度

项目页和 Hao AI Lab 发布的信息给出了 Qwen3-8B 与 Qwen3.8-27B 的结果。以下数字均对应两块 GB200；不同模型、精度、批量和测试负载的结果不能直接混作同一比较。

| 模型与设置 | 解码速度 | 对比信息 |
|---|---:|---|
| Qwen3-8B，BF16 | 1,361 Token/s | 相对自回归最高 7.45 倍，相对 DSpark 最高 1.54 倍 |
| Qwen3.8-27B，BF16 | 367 Token/s | 发布信息未列出该行的分项倍率 |
| Qwen3-8B，NVFP4 与内核优化 | 超过 4,000 Token/s；项目页列出 4,117 Token/s | MATH-500，batch size 1 |
| Qwen3.8-27B，NVFP4 与内核优化 | 超过 900 Token/s | 发布信息未列出该行的分项倍率 |

项目页在 BF16 的 Qwen3-8B 设置中列出了相对 DSpark 1.51 倍的结果，发布信息给出的则是“最高 1.54 倍”。两者并不必然冲突：前者是具体展示配置，后者强调最高端到端收益，阅读时应保留各自的测试边界。

速度之外，接受长度决定了每次目标模型验证能推进多少 Token。在 7 个基准上，JetSpec++ 在温度为 0 和 1、验证预算为 16 和 32 的设置中，每轮提交的 Token 数都超过所列基线。温度为 0、预算为 16 时，J3-R3 配置在 Qwen3-8B 上平均每轮提交 8.94 个 Token，DSpark 为 6.89 个。

这组结果与方法设计相互印证：流水线隐藏草稿成本，自我修正提高每轮验证的产出。只优化其中一项，都难以完整解释最终的端到端收益。

## 收益之外，还要看部署成本

JetSpec++ 的展示配置使用两张 GPU，一张运行目标模型，一张运行草稿模型。因此，单请求加速并不自动等于相同硬件成本下的吞吐提升；评估部署价值时，还要把额外设备、模型大小、批量和实际请求负载一起计算。

批量也是尚未完全展开的一维。较大 batch 通常会提高总吞吐量，却可能降低每个请求的生成速度。项目页披露的只是 Qwen3-8B 在 MATH-500 上的初步结果：batch size 为 2 到 4 时，JetSpec++ 在总吞吐和单用户速度上都领先 DSpark。团队仍将更高 batch 与更真实的服务负载列为后续工作。

更大的目标模型则是另一个计划方向。目标模型越大，验证相对草稿生成越昂贵，理论上留给自我修正的时间窗口也越大。不过，面向跨多 GPU 的生产模型仍需进一步训练与系统验证，不能把当前两块 GB200 上的结果直接外推到所有部署环境。

## 结语

JetSpec++ 的核心贡献可以归纳为三点：

- 用草稿与验证的流水并行，隐藏强草稿模型的大部分生成成本。
- 用隐藏状态预测、验证结果缓存和锚点解码，让“提前生成下一块”成为可能。
- 用 Jacobi 迭代、上下文刷新和锚点替换，把验证期间的剩余时间转化为更高的接受长度。

它没有改变最终验证所保证的输出分布，而是重新利用了原本被等待浪费的时间。接下来值得观察的是，这套调度思路在更高并发、更大模型和更复杂服务负载下，能否同时保住单请求延迟与整集群吞吐的优势。
