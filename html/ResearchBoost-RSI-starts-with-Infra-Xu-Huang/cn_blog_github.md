# ResearchBoost：四项训练几何平均提速 2.60 倍

研究代码里，一个 kernel 变快，并不等于端到端训练一定变快；数据等待、同步、通信和重复计算，都可能吃掉局部优化的收益。ResearchBoost 把这个问题作为 AI4AI 的切入点：让 Agent 在固定任务、可靠评测和持续反馈下，逐轮优化完整训练系统，而不是只生成一份看似更快的代码。团队在 RAE、Self Forcing、DMD 和 LLaVA 四个项目的已测试配置中，分别取得 5.32×、2.08×、1.72× 和 2.39× 训练加速，几何平均为 2.60×。比这些数字更值得关注的是，每次加速都必须先回答一个问题：训练语义有没有被改坏？

## 为什么从训练 Infra 开始

ResearchBoost 所讨论的 RSI，即递归自我改进，并不只是一项新算法或一种新模型范式。作者把它看成一个系统问题：Agent 若要参与构建 AI，就需要一个能持续开展研发工作的环境，让每轮尝试都得到准确、丰富且及时的反馈，再据此形成下一轮改进。

一个现实目标，是让 Agent 逐步承担基模研究员的日常工作，包括准备领域数据、搭建基础设施与实验脚手架、运行训练和评估结果。训练基础设施（Infra）适合作为起点，一方面因为研究实验消耗大量算力，而研究代码往往缺少充分的性能优化；另一方面因为它的边界相对清楚：在保证训练正确的前提下，是否更快、快了多少，都能通过实验检验。

这个范围也足够完整。只优化单个 kernel，可能看不到端到端收益；把数据、计算、通信与训练状态一起纳入评测，才能观察 Agent 如何分析瓶颈、处理失败，并判断局部改动是否真正缩短了实验时间。实验轨迹、研究者反馈和真实用户案例，还可以反过来帮助团队研究下一代模型需要具备哪些能力。

## 四个项目快了多少

四个结果都来自优化实现与各自原始实现的对比，测试使用相同机器和配置，并通过冻结评测的完整检查。它们不是跨项目性能排名：RAE Stage-1 与 Self Forcing DMD 训练使用 2 张 H200 级 GPU，DMD2 单步 SD1.5 蒸馏与 LLaVA-1.5-7B Stage-2 微调使用 4 张 H20，项目之间的硬件和工作负载并不相同。

![四个研究项目相对各自原始实现的训练加速比](https://raw.githubusercontent.com/kebijuelun/research-blog-repo/main/html/ResearchBoost-RSI-starts-with-Infra-Xu-Huang/images/figure-1_hu4950802473483369864.webp)

> 图解：横轴是相对原始实现的训练加速比，虚线 $1\times$ 为各项目自身基线。RAE、Self Forcing、DMD 和 LLaVA 分别为 5.32×、2.08×、1.72× 和 2.39×；几何平均为 2.60×，算术平均为 2.88×。图中结果均通过结构、收益、逐位与统计四项检查，硬件差异意味着只能比较各项目相对自身基线的变化。

精度条件也不能省略。图 1 将 RAE 和 DMD 标为 N2，即允许局部精度降低；Self Forcing 和 LLaVA 标为 N1，即保持相同的实值函数。因此，这些结果说明 Agent 在指定配置与明确精度约束下能找到有效优化，但不能直接外推为任意项目、任意硬件都能获得相同收益。

加速也不是一次生成的结果。RAE 经过 12 轮实验，从 1,835.53 ms/step 降至 345.13 ms/step；Self Forcing 经过 9 轮，从 10,811.0 ms/iter 降至 5,191.9 ms/iter；DMD 经过 73 轮，从 3.7368 s/iter 降至 2.1704 s/iter；LLaVA 经过 28 轮，从 20,934.3 ms/step 降至 8,777.1 ms/step。

![四个项目逐轮累积训练加速的优化轨迹](https://raw.githubusercontent.com/kebijuelun/research-blog-repo/main/html/ResearchBoost-RSI-starts-with-Infra-Xu-Huang/images/figure-2_hu15148281449584154629.webp)

> 图解：四个子图的横轴均为实验轮数，不是实际经过的时间；纵轴为截至当轮验证得到的最佳加速比，各子图刻度独立。深红实线表示通过完整检查的最佳结果，浅红虚线表示只通过 quick 检查的最佳结果；空心点与灰色标记保留未刷新最佳值、被拒绝、无收益或出错的尝试。图中只绘制有绝对加速数据的轮次，不做插值。

轨迹里的几次主要跃迁，展示了不同工作负载需要不同的优化方向：

- **RAE**：启用 TF32 矩阵乘和 cuBLAS 后端，使阶段最佳值从 1.00× 升至 2.54×；在解码器和判别器中使用 BF16 attention，从 3.04× 升至 3.83×；再在解码器的 MLP 与投影 GEMM 中使用 BF16，从 3.83× 升至 5.08×。
- **Self Forcing**：为 Hopper 构建 FlashAttention-3，从 1.00× 升至 1.24×；以逐位一致的方式削减 EMA、主机同步和 FSDP gather 开销，从 1.24× 升至 1.72×；加入 CUDA Graph 与融合逐元素 kernel，从 1.72× 升至 2.02×。
- **DMD**：在无梯度 UNet 前向中使用 BF16 autocast，从 1.08× 升至 1.28×；减少 fake UNet 的激活检查点，从 1.29× 升至 1.40×；编译 fake 与 generator UNet，从 1.40× 升至 1.67×。
- **LLaVA**：按 token 长度组织 micro-batch，从 1.09× 升至 1.33×；平衡不同 micro-step 的 token 数，从 1.50× 升至 1.61×；端到端使用 packed attention，从 1.65× 升至 1.79×；在解码器层之间传递 packed hidden states，从 1.91× 升至 2.03×。

不过，轨迹中“没有通过”的实验同样重要。一次 LLaVA 算子融合曾显示 1.46× 加速，检查却发现 MLP 的梯度链路被切断；补齐反向传播后，这部分收益随之消失。另一次融合触发随机数状态检查，团队最终定位到 Triton 缓存使用全局随机数生成临时文件名；隔离这一副作用后，候选通过快速检查，得以继续优化。

这两个案例揭示了 Eval 的两种价值：既能拦住漏算造成的假加速，也能把有潜力但存在副作用的候选救回来。评测在这里不只是终点裁判，还是下一轮实验的定位工具。

## 用可靠 Eval 驱动持续优化

Agent 要持续改进基础设施，需要知道当前瓶颈在哪里、自己的判断是否成立、改动有没有破坏训练语义，以及下一步应该验证什么。团队将支撑这一闭环的 Eval 概括为四个相互制约的特点：

- **Fast**：反馈足够快，让 Agent 能在有限时间和预算内完成更多有效实验。
- **Faithful**：评测忠实反映目标工作负载，能够发现错误，并可靠判断优化是否有效。
- **Local**：反馈能定位到具体问题，并可按需读取证据，减少无关信息占用上下文。
- **Dense**：反馈覆盖关键阶段和状态，足以帮助 Agent 形成下一轮可验证的假设。

四项要求必须一起满足。评测很快却漏掉训练错误，速度就没有意义；评测足够完整但每轮需要几天，Agent 也难以充分迭代。真正困难的不是单独提高某一项，而是在反馈成本、正确性覆盖和诊断深度之间取得平衡。

### Fast 与 Faithful：先校准正常波动

每次改动后都跑完整训练，成本过高；要求所有结果逐 bit 一致，又会排除许多合理优化。算子融合或归约顺序变化可能带来浮点舍入差异，而这不一定意味着训练逻辑出错。因此，评测需要区分原始训练本身的随机波动，与优化实现额外引入的偏差。

团队的做法是先让参考实现在多个随机种子下运行一段较短轨迹，例如前 100 步，记录 Loss、梯度以及 Adam 等优化器的关键状态，计算标准差 $\sigma$，据此建立正常波动范围。优化实现随后在对应条件下运行，检查变化是否超出预先校准的容差。作者以 $3\sigma$ 举例；图 1 所示结果采用配对随机种子的短轨迹统计检查，并将阈值 $\delta$ 预先冻结为参考实现种子间标准差的 2 倍。

实际验证分为三层：

1. **局部检查**：对改动涉及的算子或路径使用相同输入，比较输出、梯度与状态更新，尽早发现明显错误。
2. **短程训练检查**：在固定配置下比较训练轨迹，结合多种子基线判断偏差是否可接受。
3. **更长程确认**：对最终版本进一步检查短程测试没有覆盖的累积影响。

这里最重要的是“通过”二字的边界。短程 Eval 只支持它已经覆盖的状态、路径与训练时长内的结论，不能替代更长程确认；覆盖哪些状态、能发现哪些错误、还有哪些盲区，都应写进评测协议。

### Local 与 Dense：让反馈指向下一步

吞吐量可以告诉 Agent 是否变快，却不能解释为什么。团队因此把 PyTorch Profiler、Nsight Systems 和 Nsight Compute 纳入迭代流程，观察算子、kernel、CPU 调度、通信和 GPU 时间线：耗时集中在哪个阶段，GPU 在计算还是等待，某条高频路径是否在做重复工作，局部收益是否转化为端到端吞吐，以及正确性差异最早出现在哪个张量、状态或训练步。

所谓 Dense，不是把完整日志全部塞给模型，而是让关键观察足以支撑下一步判断。每条反馈尽量包含位置、实际观测、比较基准和证据索引；可能原因则单列为待验证假设，避免把推测写成事实。

Local 也有两层含义：既能把问题定位到具体阶段、代码路径、输入条件和时间窗口，也能让 Agent 按需读取证据。完整日志与 trace 保存在外部，上下文先放与当前假设相关的摘要，需要细节时再沿索引展开。性能分析还要与正式计时分开，避免 profiler 自身开销污染加速比。

## 小而明确的 Harness 如何运转

有了评测，还需要一个约束实验过程的 Harness，也就是让 Agent 运行、修改、测量和记录的实验脚手架。ResearchBoost 的设计重点不是让 Agent 不停运行，而是让每轮只回答一个具体问题，并留下可追溯的结果。

![AI4AI 中由评测反馈驱动的单假设优化闭环](https://raw.githubusercontent.com/kebijuelun/research-blog-repo/main/html/ResearchBoost-RSI-starts-with-Infra-Xu-Huang/images/figure-3_hu11977431537368186746.webp)

> 图解：任务在 Agent 开始前冻结；每轮依次分析当前最佳版本、修改一个热点、计时与快速筛查、在达到计时目标后执行完整检查、记录结果，再决定进入下一轮或停止。冻结评测依次执行结构、收益、逐位和统计检查，输出 PASS、no_benefit 或 INCORRECT；失败与无收益轮次同样写入日志。图中每轮从取得 GPU 锁起最多运行 30 分钟。

正式优化前，团队先准备 `Bench.py`：跑通参考实现，写好计时、性能分析和正确性检查三个入口，再用多个随机种子的波动确定容差。任务、精度与语义要求冻结后记录哈希，同时加入负例和学习率乘以 1.02 的对照；随后用 `GOAL.md` 写明目标、唯一判据、每轮流程和约束。Agent 在沙箱中使用自己的 GPU，只能读取评测，不能直接修改 `bench/`、`numerics/` 与任务定义。

每轮开始，Agent 先对当前最佳版本做 profile，根据证据选择一个热点或一类瓶颈，只验证一个优化假设。候选改动放在默认关闭的开关后，先计时并按需快速检查；达到目标后才进入完整检查。这样可以减少多个改动相互干扰，也更容易判断一个方向应该保留、调整还是放弃。达到目标、触及已分析出的性能上限、用尽预算，或遇到需要人工处理的问题时，流程都应停止。

长任务还会跨越多个上下文窗口。Agent 每轮在 `WORK_LOG` 中记录 profile、改动、结果和失败原因；会话中断或上下文压缩后，先读取日志与最近评测结果，再继续同一目标。有效改进还会沉淀为长期 skill，供后续项目复用。监督者可以是 Claude 子 Agent 或人，但只依据规则与事实介入、恢复停滞目标，不替 Agent 决定优化方向。

## 从四个案例走向可复现 Benchmark

团队已将优化后的实现与 Infra Optimization Agent 一同开源，代码位于 [ResearchBoost-Agent](https://github.com/AI4AI-for-Anything/ResearchBoost-Agent)。ResearchBoost Wishlist 则用于收集真实项目：提交者需要提供仓库、运行配置和瓶颈，团队会按适配情况与算力资源选择项目免费优化，并继续开源成果。JiT、Bagel 和 Robotwin 等项目已在后续优化计划中。

下一步是 Infra Optimization Mini-Bench v0.1。团队计划把更多案例整理成可复现任务，在固定正确性要求下，比较不同模型能获得多少加速、消耗多少时间与预算，并保留成功和失败的实验轨迹，分析能力差距来自哪里。这些任务还计划作为模型训练环境，逐步从训练加速扩展到数据、Harness 和其他研究环节。

目前证据仍限于四个项目的指定配置。不同硬件、工作负载和精度约束不能混为一谈，短程检查也不能证明更长训练中的全部累积行为；图 2 的轮数同样不代表实际耗时。对训练速度受限的研究者而言，更可行的使用方式是带着可复现仓库、固定配置和明确瓶颈参与，而不是只期待一个通用的“自动加速”按钮。ResearchBoost 已经证明可靠反馈能让 Agent 完成部分真实 Infra 优化，接下来要验证的是，这套闭环能否在更多项目与模型上稳定复现。
