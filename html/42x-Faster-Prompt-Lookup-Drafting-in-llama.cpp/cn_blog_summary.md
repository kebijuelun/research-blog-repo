# 42 倍提速：把 llama.cpp 的 Prompt Lookup 草稿机制压榨到极致

llama.cpp 的 Prompt Lookup Decoding 用 n-gram 查表当"草稿模型"做投机采样，但生成草稿 token 太慢，且语料越大越慢。作者不改任何算法逻辑，只靠四个纯工程的数据结构优化，就把每个草稿 token 的延迟从最高 165.48 µs 压到 3.98 µs，提速 **42 倍**，峰值内存最多省 **2.6 倍**；叠加 Daniel Lemire 本人的 PR 后，整体提速达 **140 倍**。

## 背景速览

- 草稿打分依赖三层 n-gram 缓存：随生成更新的**上下文缓存**、存历史会话的**动态缓存**、离线构建后只读的**静态缓存**。
- 草稿 token 需过两道阈值（出现次数 ≥ $a_n$、占比 ≥ $p_n$），瓶颈全在数据结构上，与算法无关。

## 四刀优化

**1. 修掉热路径上的 Map 整份拷贝。** 每步打草稿时内层 Map 被多处复制，改为按引用访问。提速 **4.5~25.6 倍**——最大的收益往往来自最不起眼的 bug。

**2. 外层 `std::unordered_map` 换成 ankerl::unordered_dense 的 `segmented_map`。** 链地址哈希对 CPU 缓存极不友好；segmented 变体按段增长，避免默认 map 翻倍扩容在 541 MB 大语料上反噬内存 16%。加载提速 **1.41~1.65 倍**。

**3. 内层 Map 换成有序数组。** 先看清数据分布：**64% 的 2-gram 只有 1 个后继**，99% 不超过 100 个——为它们各配一个哈希表纯属浪费。但重尾分布下少数高频 2-gram 有上万后继，故用有序 `std::vector` + 二分查找。关键细节：手写**固定迭代次数的二分查找**，把循环控制流与内存依赖解耦，让 CPU 乱序执行提前发射指令（直接用 `std::lower_bound` 反而变慢 0.89 倍）。内存最多省 **1.97 倍**。

**4. 静态缓存换上 Lemire 的 constmap。** 利用其"加载后不再修改"的性质，用基于 binary fuse filter 的不可变映射，存每个 2-gram 的 (起始位置, 后继个数)，挤进一个 64 位整数；加载即一次文件读取，零解析零插入。加载提速 **6.32~16.12 倍**（541 MB 语料从 3.76 秒降到 0.23 秒），内存占用≈文件大小。

## 番外与结论

- Lemire 的 PR 把"算完再筛"改为"提前判负就退出"：先查总次数是否过 $a_n$，再只看最高频后继能否过 $p_n$，drafting 再快最多 4.2 倍，整体 **140 倍**。
- 全程零算法改动，草稿接受率与原实现一致——纯粹的工程胜利：读懂数据分布 + 选对数据结构，在 AI 基础设施里依然能打出惊人效果。
- 展望：阈值仍硬编码，动态/上下文缓存尚未享受不可变结构的待遇。
