# NariQ：27B模型压至10GB，长程智能体对齐BF16

27B参数模型的BF16权重需要53.8GB，Nari Labs在2026年11月20日发布的NariQ 3-bit版本则把语言模型权重压到10.1GB。更值得关注的是，团队报告DeepSWE长程软件工程任务平均pass@1从39.8%升至41.0%，Terminal-Bench 2.1从62.6%升至63.8%，大幅压缩后没有出现预期中的明显掉分。

不过，“对齐BF16”仅指Nari Labs自己的长程智能体、数学和图像理解测试，尚不代表所有任务都获得独立验证。NariQ也不是普通GGUF文件，必须搭配团队的llama.cpp分支运行。

## 用真实智能体轨迹校准量化

NariQ是一种建立在QTIP之上的格编码训练后量化（PTQ）方法。其校准数据不是泛化文本，而是真实编程智能体轨迹：模型需要持续规划、调用工具、读取反馈并修正动作。长链条中的局部偏差可能逐步累积，因此简短问答分数不足以判断量化是否成功。

团队提供3、2.5和2比特文件，采用可在单张GPU上运行的存储布局。3-bit在DeepSWE（113项任务、3轮）和Terminal-Bench（82项任务、3轮）上分别达到41.0%和63.8%，AIME 25+26为98.3%，高于BF16的97.7%；但MGSM从94.0%降至93.1%，RealWorldQA则同为82.4%。所以结论是整体接近，而非全面提升。

2.5-bit的DeepSWE达到41.9%，Terminal-Bench却回落至60.2%；2-bit在这两项分别只有28.6%和52.4%，AIME也降至86.0%。测试均由Claude Code CLI 2.1.309驱动，开启thinking、effort设为max，上下文为262,144 tokens。BF16第3轮有一次验证器超时并按零分计算，339次试验实际评分338次，三个NariQ版本均完成339次评分。

## 选择文件时还要算运行时与显存

团队默认推荐10.12GB的3-bit；8.44GB的2.5-bit适合进一步节省显存；6.75GB的2-bit虽然最小、解码更快，但数学和智能体能力明显较弱。三个版本还需共用0.93GB的BF16视觉投影组件，视觉塔也未压缩。

权重变小不等于长上下文没有内存压力：KV缓存和激活仍为BF16。团队估算，24GB GPU分别可容纳约135K、160K和184K上下文；完整262K上下文则约需30GB、28GB和27GB显存，因此建议使用32GB或更大显存，显示器共享GPU时还需降低上下文。

真正的门槛是兼容性。标准llama.cpp、Ollama和LM Studio暂时无法加载NariQ；当前分支重点优化SM120，AMD和Intel GPU尚不支持，早于Ampere的GPU会退回较慢的CPU执行，Apple M系列也明显较慢。MTP模块尚未包含，KV缓存和激活量化仍属后续工作。

回到最初的问题：3-bit确实以约10GB权重在团队测试中保住了长程智能体能力，是值得优先尝试的版本，2.5-bit可作为省显存的折中；但接受专用运行时、确认硬件适配，仍是结论成立的前提，跨硬件表现和独立复现仍待补齐。方法细节见[技术报告](https://arxiv.org/abs/2611.26157)。
