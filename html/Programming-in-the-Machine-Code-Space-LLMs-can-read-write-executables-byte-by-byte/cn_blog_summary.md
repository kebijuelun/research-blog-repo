# Machine Code Programming：大模型直接读写可执行文件字节

一个已编译、剥离符号的程序，能否不借助反汇编器就被大模型读懂？George Xenos 和 Sotiris Giannopoulos 的初步实验显示：只提供可执行文件的十六进制转储，GPT-6.1 Sol 正确解释了四个程序，为三个程序直接改字节添加功能，还从零写出三个可运行程序。作者将其称为“机器码空间编程”：模型绕过源码、汇编和反编译，直接围绕字节推理。

## 无工具、一次机会，直接处理字节

作者通过 Codex CLI 0.166.0 调用 GPT-6.1 Sol，推理强度为 high。除从零生成外，输入均为 `xxd` 转储，每字节约耗 2.4 个 token。本地中继移除了全部工具，并审计事件流；每个程序只回答一次，没有反馈。生成及修改后的程序与 GCC 参考构建运行同一组测试，标准输出和退出码必须逐字节一致，并在 Apple Silicon 上通过 qemu-x86_64 执行。

阅读测试中，模型认出了三个自建程序和 FreeBSD 的 `ministat`。后者大小为 67,392 B，经 `-O3` 构建、静态链接 musl、剥离符号并处理字符串。Sol 仍恢复了全部八个选项，还从原始 64 位浮点数表中发现：标为 99.5% 置信度的 `-c 99.5` 实际使用约 99.8% 的临界值。作者随后借助 Claude 对照源码，确认了这一上游缺陷。

修改测试要求等长字节替换，不能扩大文件。模型为 wordcount 增加最长行输出、为 AES 工具增加 `dec` 解密、为 Bank ledger 增加 `transfer` 转账，分别修改 74、544、379 字节，三个程序均一次通过检查新旧功能及长输入的隐藏测试。其做法包括寻找填充区、修改段头权限、写入新代码并覆盖调用指令。

从零生成时，模型连 ELF64 文件头也自行填写。三个生成文件分别为 391 B、4,144 B 和 3,584 B，均通过全部测试；对应 GCC 构建为 5,432 B、9,408 B 和 8,896 B。直接扩展现有程序则少用了约 1.8 至 3.7 倍输出 token。这些大小差异只对应三个小程序的特定构建，不能证明机器码编程普遍优于编译器。

## 真实恶意软件与开放权重模型

面对一个未注明性质、仅 4,608 字节的 PE32+ Windows 样本，Sol 在 211 秒后判断其下载机器码并在内存执行，给出服务器 `165.154.205.34:443` 和正确请求 URL。作者按 SHA-256 找到 VMRay 公开报告核验：13 个隐藏 API 的循环右移 13 位哈希全部吻合，地址、URL 和下载行为也得到沙箱支持；但“每 10 秒重试”未被确认，沙箱也没有直接证实 `0x99` 异或密钥。这仍只是一个样本、一次运行。

作者又用 opencode 和开放权重模型 DeepSeek V4.1 Flash 重复实验。它得到相同的下载执行结论和服务器地址，但仅正确识别 9/13 个 API，并把 URL 参数 `h` 误写为 `fh`；推理 token 从 Sol 的 5,178 增至 89,902，耗时从 211 秒增至 859 秒。其轨迹确实推导了入口跳转、栈上构造 `GET /?a`、异或解码及调用缓冲区，但托管构建无法确认，opencode 也未沿用此前的严格工具隔离，因此不能视为完整复现。

## 上下文仍是硬限制

十六进制表示使 67 KB 的 `ministat` 约需 163,000 个 token，10 MB 程序则约需 2,400 万个；作者最大的测试也只有 67 KB。以递归语言模型配合 REPL、按偏移读取并分派子调用，只是后续设想，尚未验证。

这些实验没有证明大模型即将取代编译器或反汇编器，而是表明它们可能不再必须经过为人设计的表示层。回到最初的问题：直接读写字节确实已经发生，但少量小程序和一次真实样本分析，远不足以证明其能稳定处理大型、复杂或强混淆软件；模型给出的地址、API 与解码逻辑仍需哈希重算、沙箱和内存证据分别核验。
