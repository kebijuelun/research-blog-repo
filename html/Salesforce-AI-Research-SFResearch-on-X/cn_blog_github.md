# SFR-AutoR&D：当 AI Agent 自己跑完整个研发闭环，会发生什么？

AI Agent 能写代码已经不新鲜了，但如果让它 **自己决定研究什么、动手实验、并拿出可复现的证据证明改进有效**，会是什么水平？Salesforce AI Research 最新发布的 **SFR-AutoR&D** 就是在回答这个问题：它是一套自主研究与开发（Autonomous R&D）系统，你只要给一个研究目标、一个可操作的代码仓库或模型、再加上预算约束，剩下的"假设—实现—验证—迭代"闭环全部交给 Agent 跑。结果相当硬：AutoR&D-Engineer 把 pandas 行级归约最高提速 **1.84 倍**、USearch 检索 QPS 提升 **17.5%**、自家 RL 训练栈生成速度快了 **3.14 倍**；TrainForge 则自主发明训练方法，在留出的数学、代码和研究类基准上拿到 **+11 到 +14 个百分点** 的提升。这篇文章就带大家拆解这套系统的设计思路和证据链。

## 它要解决什么问题？

传统的 AI 编程 Agent（比如各种 coding assistant）本质上是"执行者"：人告诉它做什么，它去做。但真正的研发工作不是这样运转的——研发的核心循环是：**观察现状 -> 提出假设 -> 设计实验 -> 验证证据 -> 决定下一步**。这个循环里最难的不是写代码，而是"决定试什么"和"证明它真的有效"。

SFR-AutoR&D 的出发点就是把这个完整闭环自动化。它的定位不是"帮你写补丁的工具"，而是一个能对结果负责的"虚拟研究员"：没有通过验证的改进不会被采纳，每一个交付物都必须附带可复现的基准证据。

> 图解：SFR-AutoR&D 的总体工作流。左侧是输入——一个研究目标（"哪里可以做得更好？"），包括要操作的工件（Artifact，代码仓库或模型）、可度量的目标（Target）以及预算与约束（Bounds）。中间是 Agent 的闭环：Discover（发现问题/假设）-> Build（实现方法）-> Evaluate（评估证据）-> Learn（从结果中学习），每一轮实验的结果都会指导下一次实验（底部虚线"Every experiment informs the next"）。右侧是输出——"Verified progress"，即附带证明的更优方案：一个新方法、一个补丁或 checkpoint，以及可复现的证据。

这个设计的聪明之处在于把"验证"放进了闭环的核心位置，而不是事后补救。Agent 产出的不是"看起来能跑"的代码，而是"有证据链支撑"的改进——这也是它和普通代码生成 Agent 最本质的区别。

## 系统全貌：两个专业 Agent + 一套共享基础设施

SFR-AutoR&D 目前由三个部分组成，分工明确：

- **AutoR&D-Engineer**：面向已有代码库的"研发工程师"。输入是仓库 + 研究目标（系统、指标和约束），输出是经过验证的实现（补丁 + 基准证据）。
- **TrainForge**：面向模型训练的"训练方法发明家"。输入是基线模型 + 目标（任务、评估方式和算力预算），输出是最优的已验证 checkpoint 和评估记录。
- **AutoInfra**：共享的训练与推理基础设施。TrainForge 用它并行启动和对比模型实验；它还负责训练支撑前两个 Agent 的模型。更有意思的是，两个 Agent 验证过的改进可以回流到 AutoInfra，反哺下一个研究周期——系统在"自己改进自己"。

理解了整体架构后，我们逐个看这两个 Agent 到底做出了什么。

## AutoR&D-Engineer：在"已经被榨干"的开源库里找性能

最能体现这套系统实力的，是它选择的战场：pandas、hnswlib、USearch 这些被大量使用、也 **已经被深度优化过** 的开源库。在这些地方找性能提升，等于在别人的 SOTA 上做改进。

### 案例：pandas 行级归约的 1.84 倍提速

以 pandas 为例。对于 nullable dtype（可空整数、浮点、布尔及其 Arrow 变体）的列，执行行级 `sum`、`prod`、`min`、`max` 时，pandas 会把整个 DataFrame 拍平成一维数组，然后走 groupby 聚合内核。问题在于：为了告诉内核"每个值属于哪一行"，它需要先构造一个 **和整个 DataFrame 一样大的"行标签"数组**——一个用完即弃的临时对象。

设一个 $n$ 行 $c$ 列的 DataFrame，所有列共享同一个 nullable dtype。原实现把各列拼接成长度为 $n \cdot c$ 的一维扩展数组 $A$（列优先布局），并构造标签向量 $L$：

$$
A[c \cdot n + r] = X[r, c], \quad L = \text{tile}(\text{arange}(n), c), \quad |L| = n \cdot c
$$

这个 $L$ 在 64 位机器上是 $n \cdot c$ 个 8 字节整数，唯一的用途就是标记归属。AutoR&D-Engineer 发现：完全可以用另一种视角看同一份数据——把现有的 data 和 mask 缓冲区 **视作** $(c, n)$ 矩阵，转置为 $(n, c)$，然后用 **单个分组** 调用同一个内核。内核的每一"列"恰好就是 DataFrame 的一行，在这行的 $c$ 个观测上做聚合。由于每个输出单元消费的数值和列顺序与原来完全一致，结果是 **逐位相同（bit-identical）** 的，消失的只有那个标签数组。

效果数字：

- 在 pandas 自己的 40 个 benchmark 单元（4 种操作 × 5 种 nullable dtype × 2 种形状）上提速 **1.22–1.84 倍**，中位数 **1.38 倍**，且每一个 bootstrap 置信区间都在 1 以上（即统计上显著快于基线）；
- 在 1000 万元素的 DataFrame 上，峰值内存下降 **12–15%**（例如 Int64 的 sum 从 449 MB 降到 396 MB）——这正是被消掉的标签数组的体积；
- 验证规模：**134,064 个差分测试用例**（141,120 次调用），覆盖所有 dtype、两种 `skipna` 设置、`min_count` 边界、退化形状、无穷大和 NA 模式，结果、mask、dtype、异常行为 **零差异**；加上前两个补丁的 1,910 个用例，全部精确匹配。

博主觉得这里最值得学习的不是优化本身，而是 **证据链的厚度**。一个 Agent 生成的性能补丁能不能合入上游，瓶颈从来不在"快不快"，而在"你敢不敢信"。13 万个差分测试、猴子补丁证明旧路径永远不会被意外触发、437 个新测试加 44,458 个存量测试全过——这种验证规格已经接近人类资深工程师提交上游 PR 的标准了。

三个 pandas 优化共享同一个思路，用一句话概括就是：**先检查数据，安全时跳过不必要的工作**。每个优化都为满足特定条件的输入提供 fast path，其余输入仍走原有实现——这是一种非常保守、非常适合上游合入的改造策略。

除了 pandas，AutoR&D-Engineer 还在向量检索库 USearch 上把 QPS 提升了 **17.5%**，在 Salesforce 自家的 RL 训练基础设施（SFR-RL）上把生成速度提升了 **3.14 倍**。注意这些都是相对各自 workload 基线的实测增益，不是合成 benchmark 上的数字。

解决了"优化已有代码"之后，下一个更难的问题来了：能不能让 Agent 去发明 **不存在的东西**——比如新的模型训练方法？

## TrainForge：不只是训练模型，而是决定"下一步试什么"

TrainForge 的定位比 Engineer 更激进：它要 **发明训练方法**。给它的输入只有一个基线模型和一个目标（任务、评估方式、算力预算），它自己选择研究方向、生成候选训练策略、跑实验、根据结果提出下一轮更好的方案——"没有改进就不提升（No improvement means no promotion）"，只有验证过的 checkpoint 才会被保留。

它的新颖性控制值得一提：已有方法只是参考，而不是固定菜单。Agent 会广泛搜索、辩论备选方案、围绕每个目标重新设计完整的改进回路；每个提案在被先前工作核查和实验验证之前，都只能算"新颖性候选"。评估用的是 **冻结的留出数据集**（held-out evaluation），训练数据与评估数据严格分离，避免自评自夸。

在一个硬数学推理任务上，TrainForge 自主选择的研究方向是："模型能否保留推理结构，而不只是最终答案？"它在 Qwen3-4B 上生成了三种训练方法并在留出基准（Omni-MATH、AIME 2025、AIME 2026）上评估。整体来看，TrainForge 发明的训练策略在数学、代码和研究类留出基准上带来了 **+11 到 +14 个百分点** 的平均提升。

这个幅度值得多说一句：后训练方法上十几个点的提升，通常是一个研究团队数月迭代的结果。而这里的想法生成、代码实现、训练、评估、晋级全部由 Agent 闭环完成，人类只提供了目标和预算。

## AutoInfra：支撑闭环的底座，以及"自我改进"的飞轮

前面两个 Agent 能产生多大价值，很大程度取决于背后的基础设施。AutoInfra 提供了共享的训练和推理平台，其规格相当夸张：支持 **1T 参数模型在 100 万 token 上下文下的全参数训练**。

更重要的是它的飞轮结构：AutoInfra 既支撑研究闭环（TrainForge 用它并行跑实验），也负责训练驱动两个 Agent 的模型；而 Engineer 和 TrainForge 验证过的改进（比如更快的算子、更好的训练方法）又会被合并回 AutoInfra。也就是说，**系统每一轮研究都在让下一轮研究的底座变得更强**——这大概就是"Autonomous R&D"这个概念最迷人的地方。

## 总结与展望

回顾全文，SFR-AutoR&D 的核心要点：

- **定位**：不是代码助手，而是自主跑完"假设—实现—验证—迭代"完整研发闭环的 Agent 系统。
- **证据优先**：所有交付物必须附带可复现的基准证据，未通过验证的改进一律不采纳。
- **AutoR&D-Engineer**：在 pandas / hnswlib / USearch 等成熟开源库上拿到 1.84× 提速、+17.5% QPS 等实测增益，验证规格达 13 万+ 差分用例零差异。
- **TrainForge**：自主发明训练策略，在数学、代码、研究类留出基准上提升 +11 至 +14 个百分点。
- **AutoInfra**：支持 1T 参数、1M 上下文全参数训练的共享底座，两个 Agent 的改进可回流，形成自我增强飞轮。

展望未来，Salesforce 给出的路线是三个方向：更多目标（从数据基础设施扩展到更广的开源生态和自家平台）、更深的自主性（一次发现启发下一个假设的长研究弧线）、以及开放贡献（把发现打包成附带完整证据的上游 PR）。目前的局限也很明显：案例仍集中在有明确可度量指标的领域，对于那些"好"很难定义、评估本身没有共识的开放性研究问题，这套"证据驱动"的闭环能走多远，还需要更多验证。但无论如何，"找到没人想到要问的改进，并证明它是真的"——这个愿景值得整个社区关注。
