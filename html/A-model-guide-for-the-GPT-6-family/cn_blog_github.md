# GPT-6 家族模型实战指南：选型、Prompt 与长任务管理的最佳实践

GPT-6 系列模型发布了，但"模型更强"不等于"用得更对"。这篇 OpenAI 官方指南要解决的，正是开发者最头疼的现实问题： **三个模型怎么选、Prompt 要不要重写、动辄几小时的 Agent 任务怎么管住、成本怎么压下来** 。核心思路一句话概括：把模型选择、推理档位、速度模式当成一个"智能/价格"的权衡旋钮，再配合缓存、压缩、转向（steering）等工程手段，把 GPT-6 用进生产环境。最硬的两个数字：缓存命中的输入 token 最高可省 **95%** 成本，GPT-6.1 Sol 能以 **五分之一** 的价格提供接近旗舰模型的智能水平。

## 模型阵容：三档定位，覆盖从重推理到规模化任务

GPT-6 家族目前包含三个模型，定位非常清晰：

- **GPT-6 Astra** ：家族中最智能的旗舰，面向最难的推理任务。价格：输入 \$10.00 / 输出 \$50.00（每百万 token），缓存输入 \$1.00。
- **GPT-6.1 Sol** ：接近 Astra 的智能水平，价格只有五分之一。适合复杂编码、研究和 Computer Use 场景。价格：输入 \$2.00 / 输出 \$10.00，缓存输入 \$0.10。
- **GPT-6 Luna** ：快速高效的日常主力，适合大规模、目标明确的重复性任务——比如抽取发票字段、分类请求、生成结构化摘要。价格：输入 \$0.10 / 输出 \$0.50，缓存输入 \$0.01。

博主点评：这个梯度设计的聪明之处在于，它把"用哪个模型"从一道玄学题变成了一道算术题——先估任务难度，再查价格表，基本就能定位到答案。

## 上线生产之前：把效率和可观测性先铺好

模型选好了，下一个问题是：怎么让它在生产环境里跑得又稳又省。指南给出了几条上线前的必做检查。

### 砍掉多余上下文，复用共享上下文

- **精简上下文** ：删掉任务不需要的内容，但保留关键证据。应用支持的话，把相互独立的任务并行跑，避免一个慢步骤拖住所有不相关的工作。
- **Prompt Caching（提示缓存）** ：对重复性工作复用共享上下文。缓存命中的输入 token 成本最高可降低 **95%** （视模型而定）。实操要点是：把稳定的指令和参考材料放在 Prompt 前面，变化的任务细节放后面，并保持工具定义（tool definitions）一致——这些做法直接影响缓存命中率。
- **Compaction（上下文压缩）** ：长对话场景下，压缩可以在保留继续工作所需状态的同时缩小上下文体积。
- **成本估算** ：估算完整工作流成本时，别忘了把缓存写入和长上下文费率算进去。官方提供了缓存看板（caching dashboard）和诊断指南来定位缓存失效的位置。

### 度量与监控

上线前先跑一批有代表性的任务，度量三个指标： **任务成功率、延迟、单次成功任务的成本** 。同时提前规划好行为监控方案和数据控制（data controls）策略。

## 选型方法论：智能与价格的权衡旋钮

指南把模型选择抽象成一个三维权衡： **模型 × 推理档位（reasoning effort） × 速度模式** 。

### 推理档位：让模型"花多少力气"可调

在 API 中可以为每个任务指定推理强度：

- **Low** ：例行任务，如抽取事实、小改动。
- **Medium** ：需要判断力的工作，如规划一个功能、比较方案。
- **High** ：困难的调试、深度分析、细致审查。
- **Extra high / Max** ：当 High 不够用时再试，且只有在效果提升值回增加的时间和成本时才保留。

一个实用细节：在 API 中可以 **在对话中途调整推理档位而不破坏缓存** 。在 Codex 中则建议从模型默认档位起步，简单任务调低、深度分析调高。

### 速度模式：为响应时间付费

- **Fast 模式** ：适合聊天应用、编码工具等对响应时间敏感的场景，响应更快更稳定，但每 token 成本高于标准处理。
- **Ultrafast 模式** ：在 Codex 和 API 中可用（目前支持 GPT-6 Astra），为快速编码迭代等场景单独加速 token 生成，与推理档位相互独立。

## 重写你的 Prompt 和 Skills：少即是多

解决了"选哪个模型"之后，下一个问题是"指令怎么写"。这里指南抛出了一个反直觉的观点：

> "模型在理解细微差别和模糊性方面已经好太多了，过去有帮助的过度具体的指导，现在反而可能妨碍结果。"
> —— Eric Provencher, OpenAI 开发者体验团队

换句话说，GPT-5 时代那种事无巨细的"保姆级 Prompt"，在 GPT-6 上该瘦身了。正确姿势是先给出 **清晰的任务委派** ：想要什么结果、给谁看、相关背景和约束、"完成"的判定标准。然后重点检查四个方面：

- **优化 Skills 定义** ：描述要短，明确说明每个 skill 何时触发；支撑细节按需加载；用适合当前模型的指导取代僵化的"菜谱式"步骤。
- **更新 AGENTS.md** ：说明哪些文档和测试在什么场景下相关；明确授权安全的例行工作流（比如用一次性数据跑本地测试、不碰生产环境）。
- **设定决策边界** ：明确哪些操作模型可以自主执行、哪些必须请示，用清晰的边界取代一刀切的"凡事都问"。
- **对"完成"给出严格定义** ：把"done"定义为实现变更 + 运行验证 + 检查结果 + 修复失败，并标明哪些决策需要人工复核。

此外，还要 **定义你需要的输出形态** ：告诉模型哪些选择它可以自己做（比如摘要怎么组织）、哪些必须先问你（比如改变项目范围），以及一份有用的交付长什么样——比如面向目标读者的技术深度，外加一段简短的交接说明，涵盖"改了什么、验证了什么、还有什么待办"。

博主点评：这一节本质上是把 Prompt Engineering 从"技巧活"升级成了"管理活"——你要管理的不再是一个聊天机器人，而是一个有自主权的数字员工，指令的写法自然要向"岗位职责说明书"靠拢。

## 长任务优化：让跑几小时的 Agent 不跑偏

GPT-6 家族已经可以承担 **跨越数小时甚至数天** 的任务。但任务越长，中途跑偏、需求变更、意外决策点的概率就越高。指南分 API 和 Codex 两条线给出了管理工具。

### API 侧：转向、异步与委派

- **Mid-turn steering（中途转向）** ：通过 Responses WebSocket API，在模型工作过程中发送修正指令。更新会进入队列——它不会取消正在运行的工具调用，也不会撤销已完成的动作。
- **Asynchronous tool calling（异步工具调用）** ：模型可以在你的应用跑慢任务（比如测试套件）的同时继续推进独立工作，结果就绪后再返回。注意：依赖该结果的后续工作必须等结果到位再启动。
- **多智能体委派** ：GPT-6.1 Sol 在 Responses API 中支持 multi-agent 工作流（目前为 beta），可以把独立子任务（比如调查代码库的不同部分）分派给子智能体，最后汇总成完整响应。

### Codex 侧：澄清与纠偏

- **工作中主动提问** ：配合 GPT-6 Astra，Codex 可以在工作过程中请求澄清。你要做的是：优先解答影响下一步的问题，并明确哪些独立工作可以在你思考期间继续。如果你要离开一会儿，提前告诉 Codex 哪些任务可以继续、什么时候该停下来等你。
- **需求变化时重定向** ：用新信息"转向"进行中的任务，说清楚什么要改、什么保持不变，避免在已经不合需求的方案上继续烧钱。

## Computer Use：没有 API 的软件也能自动化

GPT-6 Astra、GPT-6.1 Sol 和 GPT-6 Luna 都支持 **Computer Use** ——模型可以直接操作网站和桌面应用，哪怕这些应用根本没有 API。典型场景：让模型调查一个 bug、修好代码，然后在浏览器里打开你的产品验证修复是否生效。

选择执行方式时遵循" **最简单的可靠路径** "原则：

- 能用 API 或已接入的工具直接完成的，就不要绕到界面上。
- 只有当模型确实需要"看屏幕、点按钮、填表单"时，才动用 Computer Use。

如果你要在自己的应用里集成 Computer Use，需要给模型提供一个能执行代码来控制浏览器或桌面的工具： **Playwright** 用于浏览器， **PyAutoGUI** 用于桌面应用。

## 总结

回顾这篇指南的核心要点：

- **选型是算术题** ：Astra 攻坚最难推理，Sol 以五分之一价格覆盖复杂编码与研究，Luna 规模化处理目标明确的日常任务。
- **缓存是最大的成本杠杆** ：稳定指令前置、工具定义保持一致，缓存输入最高省 95%，别漏算缓存写入和长上下文费用。
- **Prompt 要瘦身为"委派书"** ：说清结果、约束和"done"的标准，用决策边界取代"凡事都问"，过度具体的指导在新模型上反而有害。
- **长任务靠三件套管住** ：mid-turn steering 中途纠偏、异步工具调用避免空等、multi-agent 委派并行推进；在 Codex 中还要约定好"离开期间哪些能继续、何时必须暂停"。
- **Computer Use 是最后手段而非首选** ：有 API 走 API，需要看屏点击时才上 Computer Use，Playwright 管浏览器、PyAutoGUI 管桌面。

展望来看，这份指南透露的信号很清晰：模型能力的竞争正在让位于"Agent 工程化"的竞争——谁把转向、委派、缓存、监控这套基础设施玩得越熟，谁就能用更低的成本把更强的智能落进生产环境。对开发者而言，现在正是把团队 Prompt 资产和工作流按 GPT-6 的思路重构一遍的好时机。
