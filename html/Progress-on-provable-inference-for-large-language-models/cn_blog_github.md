# FlashProve：400B 模型推理可验证

你付费调用某个大模型，怎样确认回答真的来自它，而不是路由服务悄悄换上的便宜模型？只看输出质量并不可靠，但这会影响独立评测、第三方调用、安全审计和监管。Anthropic 发布的 FlashProve 用 zkSNARK 为推理生成一份密码学“证书”：验证者无需拿到模型权重，也不必重跑模型，就能检查指定输入和输出是否对应已承诺的模型。在 4-bit 量化的 400B 参数 MoE 模型 Llama 4 Maverick 上，单张 H100 的证明生成速度约为 110 Token/s，每份 1,024 Token 请求的证明约 19 MB。代价仍然明显：证明耗时约为 vLLM 普通推理的 70～95 倍，因此它目前更像审计工具，而不是可以忽略开销的实时功能。

## 为什么不能只看回答质量

如果用户可以直接看到权重并重新运行模型，核对回答并不困难。但前沿模型的权重通常保密，而一次完整推理所需的算力又远超普通用户、甚至许多独立评测者能够承担的范围。于是，“回答看起来像这个模型”无法替代“回答确实由这个模型生成”。

可证明推理（Provable Inference，PI）要解决的正是这个缺口。它允许算力有限、完全不掌握权重的验证者，确认某个回答来自请求的模型。Anthropic 在文章中给出了四类应用场景，它们需要的并不是模型自我声明，而是一份第三方能够独立检查的凭证：

- **控制 AI 发展节奏。** 监管者可以要求服务商为一段时间内处理的推理请求提供证书，确认硬件确实在服务指定模型。不过，这不能证明同一硬件没有同时开展训练。
- **发现服务器篡改。** 外部攻击者或未经授权的模型若替换预期权重，就必须为原权重伪造有效证明才能躲过检查。Anthropic 此前已通过另一个相关项目为推理流量签名，并在可信服务器上重算；FlashProve 走的是纯密码学路线。
- **确认文本来源与投入。** 服务商可以证明某段分析由指定模型完成，甚至提供“失败证明”：例如，某个模型检查特定补丁至少 1M Token 后仍未发现漏洞。这是文章设想的用途，不是已展示的漏洞扫描结果。
- **落实模型准入。** 若监管规则只允许提供获批模型，每个响应附带的证明便可绑定实际使用的模型，未经批准的替代品无法通过验证。

这些用途也不要求在可信硬件和密码学之间二选一。可信执行环境依赖制造商提供防篡改硬件；FlashProve 关注纯软件方案，其安全性建立在计算问题的困难性上。两者提供的保证和取舍不同，可以互补。

## 一份证书如何隐藏权重又证明推理

FlashProve 使用的 zkSNARK，全称是“零知识简洁知识论证”。可以把它理解成一张由密码学生成的计算收据：证明者让验证者相信某次计算被正确执行，收据不泄露计算中的秘密，而且检查收据远比重做整次计算便宜。

系统中有模型服务商这个**证明者**，以及用户或审计方这个**验证者**，流程分为两步：

1. **离线承诺。** 服务商公开模型权重的承诺，也就是固定某一套精确权重的短指纹。权重本身仍保持秘密，后续所有推理证明都与这份承诺绑定。
2. **在线证明。** 针对提示词及对应输出 Token，服务商生成证明文件，声明“已承诺的模型处理该输入后，恰好产生这些 Token”。任何持有承诺、提示词和回答的人都能验证，无需获得权重。

一份有效证明需要同时满足四项性质。**完备性**保证诚实证明会被接受；**可靠性**保证错误陈述的有效证明无法伪造，除非攻破广泛认可的密码学假设。只有这两项还不够，因为掌握权重且算力充足的验证者直接重跑模型也能得到类似结论。

真正降低使用门槛的是另外两项：**零知识**确保证明不泄露权重、中间计算值以及每层调用了哪些专家，但不隐藏模型架构；**简洁性**则把 400B 参数模型的运行结果压缩成约 19 MB 的证明，让只有 CPU 的验证者也能检查。这个量化模型约占 232 GB，验证者下载的权重承诺则只有约 6.5 MB。

## 单张 H100 怎样证明 400B 模型

把 zkSNARK 套到大模型上，难点不是写出“证明”两个字，而是控制证明器的计算量和内存。FlashProve 的三项工程选择直接针对这两个瓶颈。

第一，它让证明工作量跟随 MoE 中真正运行的专家，而不是全部参数。Llama 4 Maverick 虽有约 400B 参数，每个 Token 实际只使用约 17B 参数；证明器按这 17B 的规模工作，同时仍隐藏专家选择结果。笔者认为，这是该系统与 MoE 结构结合最关键的一点：稀疏激活不仅节省原生推理，也减少了需要被证明的计算。

第二，请求在事后批量证明。证明器像 prefill 一样并行读取已经生成的文本，并且每批只打开一次权重承诺，而非每个请求都重复操作。第三，模型各层权重被切分为段，逐段证明；权重放在普通主机内存中再流式传入 GPU，因此一张 80 GB GPU 配合约 290 GB 主机内存即可运行。

底层构造沿用了成熟的密码学思路：先将交互式预言机证明（IOP）这一信息论对象，借助哈希函数编译成密码学证明；其 IOP 又组合了带线性约束的代码邻近测试和查找论证等工具。团队表示，这一路线还可提供后量子安全性。真正困难的部分，是为大模型推理把这些组件组合成专用 IOP，而不是发明一套完全脱离既有原则的新框架。

这种设计选择的是**事后证明**，不是与推理解码同步进行的**在线嵌入证明**。前者允许更慢的处理速度，不必为了极限效率牺牲安全性；代价则是需要重算、保证来得更晚，还要处理推理固有的非确定性。

## 110 Token/s 的测试条件与真实代价

FlashProve 的速度数字很醒目，但只有连同批量、模型精度、硬件和比较基线一起阅读才有意义。团队使用公开的 4-bit 权重测试 Llama 4 Maverick，每个验证请求覆盖 1,024 Token 窗口，每份证明检查一个 Token。

| 项目 | 测试设置与结果 |
| --- | --- |
| 离线承诺 | 每个模型约 39 分钟；一份承诺可支持约 1,600 万次请求，之后需要重新承诺 |
| 在线证明 | 单张 H100、24 个 CPU 核心；24 个请求一批，约 223 秒 |
| 证明吞吐 | 约 110 Token/s |
| 单份证明大小 | 18.78 MB |
| 客户端验证 | 无需 GPU；24 线程约 17 秒，单线程约 21 秒，包含离线阶段检查 |
| 与 vLLM 对比 | 同模型 FP8 版本运行在 8 张 H100 上；按每 GPU 计算，同批 24 请求的证明约慢 72 倍，不同轮次为 66～77 倍，最高负载时约 94 倍 |

这组结果说明两件事。一方面，客户端确实摆脱了 400B 模型的推理基础设施：下载 6.5 MB 承诺和一份约 19 MB 证明后，用 CPU 就能完成检查。另一方面，证明远未便宜到可以默认附加在每次实时对话上，约两个数量级的 GPU 时间开销仍是实际部署必须考虑的成本。

## 为什么还需要 Lean 形式化验证

证明系统越快，其实现往往越复杂；密码学代码中的一个细微错误，就可能破坏整套安全承诺。据 Anthropic 介绍，Claude 参与了 zkSNARK 优化和协议规范撰写，但复杂系统中的优化决策很难只靠人工审阅判断，因此团队用 Lean 证明助手给出可机器检查的顶层安全命题。

Lean 中形式化了完备性、可靠性和零知识三项性质，这些命题在随机预言机模型下陈述，用于分析依赖哈希函数的密码学协议。此次发布还包括技术报告、Claude 撰写的协议规范、证明器、C++ 快速验证器、Lean 可执行验证器，以及辅助审计的定理交互可视化工具。代码、Lean 证明和文档均采用 Apache 2.0 许可证。

不过，“有形式化证明”不等于“整条实现链都已被证明”。团队明确留下了两道信任缺口：

- **命题是否符合本意仍需人工审计。** 形式化工具能检查推导，却不能自动确认数学命题准确表达了现实需求；可视化工具只是降低审计负担。
- **可执行代码是否等价于形式化协议仍需审计。** 可靠性只依赖验证器，因此团队提供较慢的 Lean 验证器，并证明它只接受可靠性定理所允许的证明。日常使用的 C++ 验证器没有形式化保证，只是在团队测试中与 Lean 验证器对所有证明给出一致结果。完备性可在诚实双方场景下通过测试增强信心；零知识则依赖证明器，而运行 Lean 证明器并不现实，仍需人工或智能体辅助的安全审计。

## 与此前工作相比，进步在哪里

可证明推理属于通常称为 zkML 的研究方向。早期系统只能处理小型视觉或语音网络，随后才逐渐扩展到 Transformer。以下数字来自原文汇总，模型、硬件和统计口径并不一致，适合观察演进，不宜当作严格的横向排行榜。

| 系统与年份 | 模型及原文报告结果 |
| --- | --- |
| SafetyNets（2017） | 验证两层卷积 MNIST CNN 和小型全连接语音模型 |
| zkCNN（2021） | VGG-16，15M 参数，每份证明 88.3 秒 |
| ZKML | 117M 参数 GPT-2，每 Token 约 159 秒，约 0.006 Token/s |
| Modulus Labs | 1.5B 参数 GPT-2 XL，超过 90 小时 |
| EZKL（2023） | 1M 参数 GPT 风格 Transformer，每 Token 约 966 秒 |
| zkLLM（2024） | LLaMA-2-13B，2,048 Token 输入约 15 分钟；单 A100 批处理约 2.5 Token/s |
| zkGPT（2025） | GPT-2 降至 21.8 秒，约 0.05 Token/s |
| zkPyTorch（2025） | Llama-3 8B，单 CPU 核每 Token 约 150 秒 |
| ZKTorch（2025） | GPT-J 6B，约 20 分钟 |
| DeepProve | 单机 GPT-2 约 2.9 Token/s、Gemma 3 约 1.4 Token/s，分布式约 31 Token/s |
| SASH（2026） | Llama 3.1 8B，单 H100 约 1.25 Token/s |
| Attestable | Gemma 4 31B，单 H100 为 53～77 Token/s；原文发布时尚未开源对应库 |

最有可比性的参照是同一个 Llama 4 Maverick。此前 VerInf 在 DGX Spark 上为 1,000 Token 生成证明需要 14.3 小时，证明大小 93.6 GB，验证接近一天，吞吐约 0.02 Token/s。FlashProve 报告的单 H100 吞吐为 110 Token/s，证明约 19 MB，CPU 验证为秒级。模型相同让这一对比很有说服力，但硬件和实现不同，不能把所有差距都归因于某一个算法组件。

## 这个原型还不能保证什么

FlashProve 是中间研究成果，不是覆盖所有线上模型和攻击面的完整方案。它的边界至少包括以下几项：

- **快速代码没有完整形式化保证。** Lean 协议、论文和快速可执行代码都由同一协议派生，但团队不保证三者完全一致。
- **证明对象是整数模型和贪心解码。** 浮点推理或采样解码可能在某个位置偏离被证明的计算。团队称整数版本在一般测试中通常与真实浮点推理只有较小误差，但对抗性提示不在这一经验结论的覆盖范围内。
- **当前设计依赖 MoE 结构且不隐藏架构。** 权重、专家选择和中间值可以保密，架构本身不在保护范围内；稠密模型等架构的适用性也不能由本次结果直接推出。
- **不覆盖侧信道。** 证明本身不泄露权重，不代表证明耗时等外部观测不会泄露信息，这类攻击不在本次发布范围内。
- **上下文最多 1,024 Token。** 这与真实聊天积累的长上下文、以及前沿模型常见的数十万至数百万 Token 上下文窗口仍有明显距离。
- **事后证明带来延迟和重算。** 它适合对抽样流量或指定请求补充保证，并不等同于实时、全量证明已经落地。

## 结语

- FlashProve 把“回答来自哪套权重”从服务商声明变成了用户可独立验证的密码学命题，同时保持权重秘密。
- 在 4-bit Llama 4 Maverick 上，单 H100 达到约 110 Token/s，证明约 19 MB，CPU 验证约 17～21 秒；相同模型的既有公开结果远低于这一水平。
- 性能来自按实际激活专家计算、事后批处理和分层流式权重，但相对 vLLM 仍有约 70～95 倍 GPU 时间开销。
- Lean 证明加强了顶层安全性质的可审计性，却没有消除命题审计、代码一致性和侧信道的信任缺口。

对模型评测机构、第三方路由平台和高价值推理审计场景，这套开源原型已经值得实际研究；若目标是给普通聊天逐条实时附证，则要先解决开销、1,024 Token 上下文和整数贪心解码等限制。
