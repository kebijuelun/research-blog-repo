# DFlash 2：继续保持并行草稿——投机解码的下一步进化

推理（Inference）正在成为 Agent 时代的瓶颈。Agent 要读文档、做规划、调工具，动辄连续运行数小时甚至数天，它们消耗 token 的速度是传统聊天场景从未达到的量级。而每一个 token 都意味着对整个模型做一次完整的前向传播。Inco AI 正在构建面向未来 token 经济学的推理栈，这篇博文就是他们最新成果的抢先曝光： **DFlash 2** 。

## 背景：从 DFlash 说起

今年 1 月，Inco AI 团队发布了 DFlash，如今它已经跑在 SGLang、vLLM、TensorRT-LLM 和 llama.cpp 等主流推理引擎里。生态成绩相当亮眼：

- NVIDIA 在 Blackwell GPU 上测出了最高 **15× 吞吐提升** ；
- Google 报告在 TPU 上每秒 token 数提升 **3×** ；
- CoreWeave 的生产级 Kimi K2.7 Code 端点（Artificial Analysis 上该模型最快的端点）默认开启 DFlash；
- NVIDIA、Red Hat、Modal 都发布了自己的 DFlash drafter；Meta（Muse Glimmer）、Poolside（Laguna）、小米（MiMo-V2.5-Pro）、NVIDIA（Nemotron 3.5 Lightning）也都随自家模型发布了官方 drafter；
- Hugging Face 上 DFlash 模型累计下载量已超 **350 万次** （截至 2026 年 8 月）。

### 投机解码的核心逻辑

投机解码（Speculative Decoding）是现代推理栈的核心组件：一个小的草稿模型（draft model）一次性猜出一整块 token，目标模型（target model）用一次前向传播验证整块。猜得准，一次前向就能产出多个 token；猜得不准，大不了丢弃重来。

但多年来，“草稿”这一步本身一直是自回归的——一个 token 一个 token 地猜。DFlash 的突破在于把草稿也变成了 **一次前向完成** ：整块草稿、每个位置，全部 **并行预测** 。

### DFlash 2 的成绩单

DFlash 2 在并行草稿的路上又推进了一步：

- 每次验证 pass 的产出提升 **超过 20%** （各 benchmark 实测增益 16–25%）；
- 代价仅为约 **1% 的额外循环延迟** ；
- 输出 **可证明保持不变** （即不损失精度）；
- 配合本次发布的 Qwen3.8-27B drafter，SGLang 在 batch size 1 下达到自回归解码 **2.7–3.4× 的吞吐** 。

每个位置独立预测，会在两个地方留下提升空间：一是 **选对 token** ，二是 **让准确率在块末尾不塌陷** 。DFlash 2 把这两处冗余都收了回来，同时没有放弃一次前向的设计。下面我们分别拆解。

## 创新点一：正确的 token 其实已经在候选列表里

DFlash 并行地、独立地预测每个位置。单看每个位置，预测结果都说得过去，但没有任何机制保证它们能拼成一段连贯的文本——不连贯的块在验证阶段会被提前截断。

近期的方法如 Domino 和 DSpark 用 **串行的修正头** （sequential heads）来重写每个位置的全词表分布，以此换取连贯性。但这套昂贵的自回归修正真的必要吗？

作者的回答是： **不必要** 。证据就藏在 DFlash 自己的候选列表里。以块的第一个位置为例：

- DFlash 的 top-1 预测命中率为 **85.4%** ；
- 但正确 token 落在 **top-16 候选内的概率高达 99.5%** 。

也就是说，即使 top-1 猜错了，正确答案通常也已经在候选名单上。一个总能从 top-16 中选对候选的“先知”（oracle），可以把平均接受长度从 **4.27 提升到 6.79** 。这中间的差距就是纯粹的 **选择空间（selection headroom）** ——我们要做的，只是在候选中选出正确的那条路径。

## 创新点二：轻量级路径选择器（Path Selector）

连贯性在很大程度上是 **局部的** ：一个候选 token 合不合适，主要取决于它前面紧邻的那个 token。因此，给相邻 token 对打分就足够了。

DFlash 2 保留每个位置的 top-16 候选，并对每一对相邻候选打分。对于前驱候选 $a$ 和当前候选 $b$，得分由两部分组成：

$$
S_t(a, b) = U_t(b) + \langle A a, \; H(h_t) \odot B b \rangle
$$

- 第一部分 $U_t(b)$ 是 DFlash 自己的 logit：drafter 本来就有多喜欢 $b$；
- 第二部分衡量 $b$ 接在 $a$ 后面有多顺：$A$ 和 $B$ 分别把每个 token 映射为紧凑的 256 维 embedding，两个 embedding 在一个 **上下文门控** $H(h_t)$ 下做匹配，由门控决定匹配的哪些维度算数。

本质上，这是一个作用在相邻候选上的 **低秩双线性注意力（low-rank bilinear attention）** 。

关键在于，打分过程 **仍然完全并行** ：所有位置的所有相邻 token 对一次性算完，不需要额外的 backbone 或 LM-head 前向。唯一的串行工作是在预先算好的分数上做最后一次“行走”：从上一个已验证 token 出发，贪心模式每步选最优后继；采样模式则从同一组分数中采样，再配合拒绝采样（rejection sampling）恢复精确的目标分布。

效果如何呢？这个选择器让 DFlash 在 $T = 0$ 时平均多产出 **0.34** 个 token，在 $T = 1$ 时多产出 **0.47** 个 token。它在两种设置下都击败了 DSpark 的修正方案，而参数量约为后者的 **1/40** ，延迟开销约为后者的 **1/16** 。一句话总结： **选，比重新预测便宜** 。而且空间还没吃满——oracle 的上限是 6.79。两两打分是作者能想到的最简单的选择器，这个方向显然还有更多可挖的东西。

## 创新点三：后缀衰减（Suffix Decay）是个局部问题

另一条线索来自召回率的观察：上面提到的两行召回数据都在 **块的末尾下降** 。连 oracle 都躲不过——即使选择完美，准确率仍从第一个位置的 99.5% 掉到最后一个位置的 **87.8%** 。这没有任何选择器能修复，因为 **候选本身在枯竭** 。作者把这种现象称为 **后缀衰减（suffix decay）** ，并认定这是一个 backbone 层面的问题。

### 嫌疑一：容量不够？

一个自然的怀疑是容量：5 层的 backbone 可能太小，无法把依赖关系维持到块的远端。如果真是这样，加深层数应该主要帮助靠后的位置。实验证实了这一点：3 层、5 层和 15 层的 DFlash 模型在第一个位置几乎无差别，但沿着块逐渐拉开差距。

但加层是“无差别轰炸”：多出来的 10 个 attention 块把容量均匀地洒在所有位置上，包括那些本来就没多少提升空间的早期位置，同时抹掉了 DFlash 引以为傲的效率优势。

### 嫌疑二：注意力分配的失衡

作者想要的是 **针对性的修复** ，而 DFlash 的注意力分布指出了问题所在。它的注意力有两项工作：读取块之前的上下文，以及建模块内部的依赖。但它在第二项上投入得越来越少：块内注意力占比从 **第 1 层的 30% 跌到第 5 层的 8%** ，而且残存的部分还集中在不断收缩的少数几个头上。

于是作者的思路是 **分工** ：让一个专用模块接管块内的工作，让注意力专心读上下文。

## 创新点四：轻量级局部卷积

块内的工作本来就是短程的：一个块只跨 4 到 16 个 token，最强的依赖都发生在邻居之间。最自然的算子就是短卷积：两个 tap，一个作用在当前位置，一个回溯前一个位置，且权重随内容自适应。

借鉴 Canon Layers、Dynamic Short Convolutions 和 Convolution for Large Language Models 等工作，作者在每个 attention 和 feed-forward 子层的前后各插入一个 **两 tap 的动态深度卷积（dynamic depthwise convolution）** ：

- 每个卷积系数由一个学习到的基础核（base kernel）加上一个从当前隐状态算出的小修正项组合而成，每 16 个通道共享一个修正项；
- 第一个位置读取上一个已验证 token 的表示，之后的每个位置读取其前驱位置的表示。

信息就这样跨块流动，而所有位置依然 **并行计算** 。由于卷积是块局部且无状态的，它可以无缝插入 DFlash，无需改动 attention、LM head 或验证流程。

### 效果对比

只增加 **16.5M 参数（3%）** 之后，5 层 DFlash + 卷积的表现 **逼近 15 层 DFlash** ，后缀衰减被显著抑制：

- 卷积只给草稿–验证循环增加 **0.7%** 的延迟；而多加 10 层 Transformer 要增加 **15.2%** ；
- 第 4、5 层的平均块内注意力从 **9.4% 降到 0.5%** ——印证了卷积接管了局部工作，注意力重新回到“读上下文”的本职上。

一个只回溯一个位置的卷积核，换回了十层深度的大部分收益——这说明后缀衰减 **主要是个局部问题** 。

## 整体实验：组合之后的完整对比

前面的选择器和卷积是分开测的，下面的完整对比把两者组合起来。作者在相同设定下自行训练了 DFlash 和 DSpark 的 drafter，MTP（Multi-Token Prediction）则随模型原生附带。

### 核心结论

- DFlash 2 在 **每一个 benchmark 上领先** ；
- 各 benchmark 平均下来，比 DFlash 多 **1.05 个 token（+21%）** ，比 DSpark 多 **0.48 个 token** ；
- 升级代价依然低廉：选择器加卷积合计只给 5 层 DFlash 的草稿–验证循环增加 **1.3%** 的延迟。

在 MATH-500 上，增益逐位置可见：DFlash 2 的准确率一路稳定保持在 **86% 附近** 直到最后一个位置，而每个 baseline 在块尾都比它低 **6 到 9 个百分点** 。

## 今天发布的两个 Drafter

本次同步发布两个 DFlash 2 drafter：

- 一个面向 **Qwen3.8-27B** ：对比对象是该模型原生的 MTP 路径和一个社区版 DSpark drafter；
- 一个面向 **Meta 的 Muse Glimmer** ：对比对象是随模型发布的官方 DFlash drafter 和一个社区版 DSpark drafter。

差距相当明显：在两个模型上，DFlash 2 平均都比 DSpark **领先超过一个完整 token** ，也都击败了各自的官方 drafter（Qwen3.8-27B 上的 MTP 和 Muse Glimmer 上的 DFlash）。换算成吞吐：

- Qwen3.8-27B：自回归解码的 **2.7–3.4×** ；
- Muse Glimmer：自回归解码的 **3.1–4.6×** 。

更细的分任务、分并发加速比可以在 Hugging Face 的模型卡中查看。

## 总结与展望

一个 Agent 一个下午写出的内容，相当于聊天机器人一个月的产量，而解码就压在每一个 token 下面。DFlash 2 以 **接近自回归解码 3 倍的速度** 、约三分之一的单 token 计算量，产出 **完全相同的结果** 。

七个月里，DFlash 从一篇论文变成了事实上的行业标准，下载量超过 350 万。在同样的设计框架内，DFlash 2 让每个 pass 多吐出一个完整的 token——而且近乎免费。正如作者所说：这只是整个 serving 栈的一个组件， **推理远未触及它的地板** 。Inco AI 正在构建端到端的 serving 栈来继续压低这个地板，DFlash 2 只是第一块拼图。
