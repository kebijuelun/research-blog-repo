# Performance Factory：Codex 自动修复性能回退

ChatGPT 变慢后，最耗时的往往不是收到告警，而是跨指标、日志、链路和代码定位原因，再在部署后确认恢复。随着 Codex 加快产品迭代，OpenAI 搭建 Performance Factory，让云端 Codex agent 调查、提出修复、响应评审并验证线上效果，工程师保留关键判断与合并权。团队报告，首个 Regression Workflow 在三个多月里跟踪了 1700 多次调查，为 600 多个案例找到根因，约合每天 17 次；但这些数字只说明自动化规模，不代表问题已能无人值守解决。

## 把一次诊断变成持续任务

OpenAI 先把人工经验沉淀为 30 多种性能工具，再让 Codex 协助搜索代码、指标和 trace，随后将调查流程写入共享技能 `perf-forensics`。从工程师复制告警、转发结论，到云端自动启动调查，最终才形成任务工厂。关键不是对话更长，而是把状态与证据保存在会话之外：任务服务定义状态及人工节点，调度循环分派就绪任务，云端执行 API 提供受控的代码和观测权限，事件订阅则在评审、CI 或部署后唤醒任务。agent 不必空转，接手者也不用重建上下文。

## 从告警走到线上恢复

Regression Workflow 依次推进调查、根因、修复和解决。agent 会向前追溯真正的变慢起点，区分“相似请求变慢”与“慢请求占比上升”，再检查部署、功能开关和代码，用日志与 trace 验证因果。早期系统会停在首个合理解释，因此 OpenAI 用独立 Codex 会话反驳诊断。一次对话失败调查中，原 agent 把原因归为图片下载错误；评审 agent 发现定位文件的内部服务已经恢复，图片请求却仍在失败，于是重新打开调查。

人工评审 100 条根因建议时，70% 被评为准确，30% 仍需完善或因果关系不足；这一特定样本不能外推为所有回退的解决率。诊断通过后，Codex 创建 PR，附上指标、CPU 火焰图和 trace，由工程师决定是否合并。部署后，另一个 agent 检查基线：完全恢复才关闭任务，部分恢复则为剩余问题新建任务，无改善就退回调查。OpenAI 明确表示，修复比找到根因更难，agent 可能给出过度复杂的方案甚至引入缺陷，缓存等方案也涉及架构取舍，因此修复同样需要对抗式评审。

## 自动化的边界在人的判断力

自动化还可能把瓶颈搬到评审环节。系统因此聚合同一回退的告警与监控事件，按指标分组、按影响排序，而不是制造更多长报告。团队用去除泄题信息的历史事故回放调查能力，再用任务快照评测摘要是否足以支持工程师行动，将“诊断正确”与“人能否据此行动”分开检验。每日运行的 agent 还会检查工具与权限故障并创建修复任务，但是否合并仍由人决定。

目前工作流仍由告警触发，OpenAI 希望未来通过跨版本 profile、堆转储和 trace 提前发现问题。回到“变慢之后怎么办”，其价值不是无人值守，而是把调查经验变成可复用、可评测的流程：1700 多次调查证明生产规模，70% 的样本准确率则提醒团队，诊断、修复与发布仍需要人的制衡。
