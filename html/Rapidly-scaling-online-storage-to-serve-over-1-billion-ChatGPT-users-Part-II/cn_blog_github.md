# Habitat：全球读延迟降 12 倍

当一个存储平台要服务超过 10 亿用户、覆盖 40 个地域并承载超过 500 PB 数据时，难题已经不只是“数据库够不够大”：一个热门键可能拖慢登录，一次区域切换可能引发连接风暴，跨国读取还会把延迟带进产品关键路径。OpenAI 的在线存储平台 Habitat 分阶段解决这些问题：先与 Azure 团队共同改造 Cosmos DB 的多租户能力，再通过数据复制、缓存和 Rust 重写优化全球读取。团队报告，这套组合将全球读取 p50 延迟从约 120 ms 降至约 10 ms，提升 12 倍；最大的 Cosmos DB 账户可存储数十 PB 数据，服务超过 2000 万 QPS。

比数字更有借鉴价值的，是 Habitat 如何在隔离、容量规划和全球延迟之间反复取舍。本文是系列第二部分，聚焦底层 Azure Cosmos DB 的扩展，以及围绕它建立的协同运维、缓存和变更数据捕获体系。

## 多租户为什么走了个“来回”

基础设施团队通常要在单租户与多租户之间选择。单租户让每个产品团队维护自己的系统，故障边界清晰、负载彼此隔离，但每个团队都要做容量规划，也容易过度预留资源。多租户把资源交给更专业的中央数据库团队管理，却会产生“坏邻居”（noisy neighbor）：某个租户突然占用大量资源，拖累同机的其他租户。

Habitat 没有一次性选边，而是经历了“共享容器—独立容器—默认共享容器”的完整循环。理解这个循环前，需要先明确 Cosmos DB 的四层关系：账户定义容器集合和复制策略；每个容器预配一定吞吐量，单位是 RU/s；容器内按逻辑分区键分片；多个逻辑分区又会被放入较少的物理分区，并随存储量或吞吐需求拆分。

真正的约束往往发生在物理分区，而不只是逻辑分区。这一区别决定了后面的三次架构调整。

## 第一阶段：共享容器暴露了三种故障

最初，Habitat 在每个账户中只使用一个默认容器，也基本放行所有客户端流量，希望文档所述的每个逻辑分区键 10K RU/s 上限能够自然形成背压。这个方案足够简单，却在实际负载中暴露出三个问题。

### 相同的键，不同的业务

早期 API 允许客户端直接选择逻辑分区键，不同产品因此频繁使用相同的 `user_id` 或 `workspace_id`。这些业务共享同一逻辑分区的限制，使单个用户可获得的整体吞吐量受到其他业务影响。

在迁往 Habitat 和 Cosmos DB 之前，团队扩展 Postgres 时就遇到过类似问题：一个极热的组织或键可能拖垮整个数据库。当时团队不得不缓存这些键，并为缓存未命中加入租约，避免大量回源请求同时压向数据库。

![不同客户端使用相同逻辑分区键](https://raw.githubusercontent.com/kebijuelun/research-blog-repo/main/html/Rapidly-scaling-online-storage-to-serve-over-1-billion-ChatGPT-users-Part-II/images/figure-4.png)

> 图解：多个客户端虽然属于不同业务，却可能选中同一个逻辑分区键，因此共享该键的吞吐量限制。

### 物理分区放大“坏邻居”

文档中的容量和吞吐限制面向逻辑分区，但实际执行限制的是物理分区。多个逻辑分区共处一个物理分区时，会分享物理分区的能力，单个逻辑分区未必能达到名义上的 10K RU/s。

这意味着，影响范围不再局限于同名键。小众功能的数据只要与登录、注册数据落在同一物理分区，就可能干扰这些核心流程。

![不同用户共享同一物理分区](https://raw.githubusercontent.com/kebijuelun/research-blog-repo/main/html/Rapidly-scaling-online-storage-to-serve-over-1-billion-ChatGPT-users-Part-II/images/figure-5.png)

> 图解：不同用户、不同逻辑分区的数据仍可能落在同一个物理分区，因而共同受到该分区资源上限的约束。

### 数据变多，分区反而“变弱”

物理分区的吞吐上限还取决于容器总吞吐量：容器预配的 RU/s 大致均匀分给所有物理分区。数据增长触发分区拆分后，分区数量增加；如果总预配吞吐量不变，每个分区分到的能力就会下降。

对存储量大、类似 Blob 的负载，这是一种隐蔽的退化：请求量完全没变，仅因数据持续增长，活跃业务可获得的吞吐能力就下降了。

![物理分区拆分后吞吐上限下降](https://raw.githubusercontent.com/kebijuelun/research-blog-repo/main/html/Rapidly-scaling-online-storage-to-serve-over-1-billion-ChatGPT-users-Part-II/images/figure-6.svg)

> 图解：这是一张说明性堆积面积图，并非实测时间序列。总需求保持 6K RU/s；分区拆分后，单分区容量从 10K 降至 5K RU/s，成功请求（HTTP 200）从 6K 降至 5K RU/s，被限流请求（HTTP 429）则从 0 增至 1K RU/s。容器总预配吞吐量仍为 20K RU/s。

## 第二阶段：隔离有效，容量规划却失控

针对最重要的新业务，Habitat 开始配置独立 Cosmos DB 容器。独立容器拥有独立物理分区，既避免分区键空间重叠，也把“坏邻居”限制在容器内部。团队还用脚本让容器总吞吐量随物理分区数量同步增长，以缓解分区变弱的问题。

这一策略确实把许多全站级故障缩小为单个功能或服务降级，但默认容器里的历史关键数据并未迁移。随着规模扩大，团队只能继续为新服务或大型功能配置独立容器，防止默认容器继续承压，运维负担也随之增长。

共享容器原本能利用不同业务混合后的稳定总量：某个新功能即使从 0 增至 100 万 QPS，也未必显著改变全局负载。换到独立容器后，同样的上线可能意味着相对内部试用基线增加 1000 倍流量，发布前必须单独预扩容。原文描述的情况是，产品团队有时忘记预扩容，工程师只能在发布当天进入 SEV 事故响应流程临时扩容。

趋势脚本也无法彻底解决问题。准确扩容需要了解产品何时切换流量、何时增长，结果几乎让每个产品团队都重新参与容量规划；各团队投入程度不同，组织层面无法稳定扩展。隔离解决了技术故障，却把复杂度转移给了组织。

## 第三阶段：共享容器补上隔离能力

Habitat 因而重新回到默认多租户，并与 Azure 团队针对最初的三类问题共同改造 Cosmos DB。

- **热点键限流**：优先限制最热的键，避免它耗尽物理分区吞吐量，把全站影响收窄到具体热点。
- **服务质量（QoS）分级**：批量写入、数据导出等离线请求使用低优先级并先被限流，保护面向用户的交互请求。
- **改进的 Serverless 模式**：原有 Serverless 虽能避免预配模式下的弱分区问题，却只按存储量扩展，并把单物理分区限制在 5K RU/s，无法支撑高 RU 负载。Azure 团队为 OpenAI 构建的新模式将单物理分区上限提高到 10K RU/s，并在按存储量拆分之外加入按 RU 使用量拆分，减少了人工监控和扩容容器的需要。

回到共享容器后，产品团队不再需要为每个用例做前置和持续的容量规划，同时仍保留工作负载隔离。团队报告，此后数月，即使产品开发继续加速，也没有发生预配或“坏邻居”相关事故。这里的关键并不是“多租户天然更好”，而是只有补齐限流、优先级和弹性分区，默认共享才重新成为可行选择。

## 超大规模下，托管服务也需要共同运维

多租户改造解决了日常隔离问题，区域级故障却暴露了另一层边界：当 OpenAI 成为最大的 Cosmos DB 用户之一，许多负载已经成为云服务商基础设施中的异常值，标准托管与测试流程不足以覆盖其规模。

2024 年末，一个大型 Cosmos DB 账户的主 Azure 区域发生停电。随后的故障切换演练显示，最大账户需要数小时才能切换到辅助区域，而 OpenAI 与 Azure 团队此前都没有在这一规模下测试过。约一个月后，账户切回原区域时又发生严重事故：网关模式客户端在故障回切中的特殊行为，让所有客户端立即向原区域建立连接并发送请求，尽管当时只有部分物理分区已经迁回，连接风暴最终压垮了原区域的 Cosmos DB 网关。

两次事故之后，双方没有停留在各自修复根因，而是改变协作方式：共同监控从 Habitat 服务到 Cosmos DB 物理存储的各层；在与生产规模相当、但不承载生产流量的账户上测试变更；共同迭代 SDK、制定账户规模规划方法；通过 Teams 直接联系工程师，甚至可以绕过常规支持层级直接呼叫对方。

过去一年的联合改造还包括提升 Cosmos DB 控制面和网关扩展性，在网关增加负载保护和元数据缓存，通过连接池与更高连接复用降低 Python habitat-service 进程群带来的压力，尽可能共置工作负载，并用不同 VPC 隔离关键与离线负载。对普通规模的应用，托管服务意味着交出运维；在这种规模下，它反而要求双方打破组织边界，共同拥有故障模式。

## 全球读取提速，靠的不是单点优化

系统到 2025 年逐渐稳定后，延迟成为下一项约束。计算与存储容量经常位于不同地域，跨区域请求难以避免，产品开发者只能在客户端增加缓存、批量请求、减少数据库读写，并把工作移出关键路径。这些做法增强了产品面对数据库问题时的韧性，却也增加复杂度，违背了 Habitat 让开发者无需理解数据库、快速迭代的初衷。

![计算与存储跨地域访问示意图](https://raw.githubusercontent.com/kebijuelun/research-blog-repo/main/html/Rapidly-scaling-online-storage-to-serve-over-1-billion-ChatGPT-users-Part-II/images/figure-7.png)

> 图解：全球用户的请求由不同地域的计算资源处理，而数据未必存放在同一地域，因此读取路径可能跨越很远的网络距离。

2026 年，团队把重点转向读取优化，因为读取占 Habitat 请求的 90% 以上。具体策略分为三层，每层都受不同条件约束。

### 数据靠近用户，但容量未必允许

对于有数据驻留要求的用户，Habitat 已在全球多个 Azure 区域部署账户；对没有硬性要求的用户，就近存放同样能降低延迟。不过，许多区域无法容纳与其用户流量相匹配的庞大存储量。

在机房容量、电力或制冷有限的区域，团队甚至要直接选择：把资源留给就近存储以降低 Habitat 延迟，还是留给更多服务计算，让存储请求绕远。因而，数据放置既是工程问题，也是不同产品、用户群延迟与原始存储、计算容量之间的产品取舍。

### 广泛复制，只给最小且最敏感的数据

认证元数据等每次请求都需要的数据，对延迟尤其敏感。Habitat 将这些数据放入具有大量辅助区域的 Cosmos DB 账户，缩短计算与存储之间的往返时间；部分账户复制到全部 40 个服务区域，其他账户至少覆盖每个大洲的一个区域。

为了在不同复制拓扑的账户之间移动数据，团队不得不比原计划更早建设透明的数据移动与路由层。广泛复制依然受容量限制，只能用于少数经过选择的数据集，不能成为所有数据的通用答案。

### 其余数据交给集成缓存

Habitat 的读取高度集中：应用不断读取设置、状态和属性，相对较小的热点工作集贡献了大量流量，适合分布式缓存。团队因此集成基于 Valkey 的分布式旁路缓存，把最近访问的对象和边放在靠近请求处理位置的服务器上，用缓存隐藏跨区域延迟。

常见 TTL 策略必须在命中率与陈旧度之间妥协：TTL 太短，数据很快过期，频繁回源；TTL 太长，命中率高，却可能长期返回旧数据。写操作时主动失效也有部分失败等边界情况，多地域网络以及缓存失效与底层复制之间的竞争会让问题更复杂。

Habitat 采用变更数据捕获（CDC）驱动失效，思路类似 Meta 的 TAO：服务消费 Cosmos DB change feed，在底层数据更新后向本地缓存发送失效操作，全球传播通常在数秒内完成。下一次读取发生缓存未命中，再装入最新版本，从而兼顾高命中率与较低陈旧度。

最后，团队还用 Rust 重写原先 Python 实现的 Habitat 服务，降低代理层自身开销。就近复制、区域缓存和 Rust 重写共同落地后，全球读取 p50 才实现从约 120 ms 到约 10 ms 的下降。

缓存主要改善中位数，最慢的请求仍需从底层存储读取未缓存数据，而且可能跨地域访问。团队计划随着容量上线和存储效率改善，进一步解决数据从一开始就靠近访问位置的问题，因此不能把 p50 的结果理解为所有尾延迟都已解决。

## CDC 不只是缓存的附属品

支撑缓存失效的 CDC，本身也已成为平台级基础设施。它负责把数据库变化传播给下游系统：每秒数百万条变更，来自数千个容器和数百万个容器分区，再流经一百多个 Kafka 主题，服务于最终一致的二级索引、数据移动、离线分析和实时产品功能。

如果让产品开发者自行监听，他们必须找出数据所在的 Cosmos 账户与容器、各区域对应的 CDC 部署，并分别扩展 CDC worker、Kafka 和消费者。Habitat 的 CDC 平台把这些细节收敛为一个接口：客户端注册变更行的回调函数，其余连接与扩展由平台处理。

内部控制面持续确认所有必要容器都被捕获，选择读取的 Cosmos 区域，并在多个地域的数千个 worker 之间分配工作。平台使用副本区域和低优先级 feed 读取，避免后台捕获影响延迟敏感流量；通过 worker 生命周期和租约加固、流之间故障隔离、配置与发布保护应对持续出现的故障；用死信队列避免永久投递失败阻塞后续消息；区域故障时则切换读取区域。团队还修改 Azure CDC SDK，在内存中批量处理检查点并定期落盘，降低检查点开销。

这层抽象与 Habitat 本身的目标一致：基础设施内部可以非常复杂，但产品开发者不应被迫理解整套部署拓扑。

## 下一个十亿用户，需要换一套存储底座

Habitat 的扩展顺序很清晰：先保证关键业务可靠，再优化全球读取，最后降低大规模运维成本。默认多租户不是起点，也不是简单回归，而是在热点限流、QoS、弹性分区和云厂商共同运维成熟后才成立；12 倍读延迟改善则来自数据放置、选择性复制、CDC 缓存和 Rust 的共同作用，并受云容量与尾延迟问题限制。

面向下一个十亿用户，团队认为更大规模的跨基础设施数据复制仍是难点。为此，OpenAI 正在自研 EB 级在线存储系统，面向 Habitat 的大体积数据类型，将 Rockset 的 RocksDB Cloud 核心与基于 Raft 的复制结合。它实现与 Cosmos DB 相同的文档模型，并通过存算分离和物理复制减少闪存容量，代价是峰值 QPS 更低。

对正在设计大规模在线存储的团队，这套经历给出的可执行经验是：先明确故障边界和容量责任，再选择租户模型；在全球性能优化中，则分别处理少数关键数据与大多数缓存友好的读取，不要用同一种复制策略覆盖全部数据。至于正在开发的自研系统，原文尚未给出上线结果，其实际收益仍有待验证。
