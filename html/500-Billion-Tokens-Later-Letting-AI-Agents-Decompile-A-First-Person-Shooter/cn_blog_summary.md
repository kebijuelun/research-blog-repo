# 5000 亿 Token 烧出的答案：AI Agent 反编译射击游戏，胜负手是验证器

十几个 AI Agent 连续自治工作三个月，能把一款完整的商业 FPS 游戏反编译成可读、可编译的 C++ 吗？答案是可以——代价约 6000~7000 亿 Token。最终 **99% 的函数被重建，其中 83% 与原始二进制逐字节一致** ，游戏无感知差异地完整运行。但这项工作真正的价值不在游戏，而在于回答了一个更普适的问题：如何长期、大规模地编排自治 AI Agent。核心结论很反直觉： **决定成败的不是模型多聪明，而是有没有一个能输出客观 PASS/FAIL 的机器验证器** 。

## 基建先行：Agent 版“开发团队”

- **进度追踪** ：每个 .cpp 编译单元对应一个 GitHub Issue，用标签排优先级。
- **通信** ：所有 Agent 共用一个 Discord 频道，人类可直接介入，CI 失败经 Webhook 自动推送。
- **工具链** ：Claude Code / Codex CLI 跑任务，反编译全程用 Hex-Rays 官方的 ida-mcp。

两个关键调优：把上下文压缩阈值从 90% 降到 42%（反编译信息“用过即弃”，早压缩早清理）；发现 **指令会随时间衰减** ，解法很笨但有效——每小时定时注入一次“请重新阅读项目文档”。

## 第一个月的教训：进度喜人，质量堪忧

4 个 Agent（3 Worker + 1 Reviewer）一个月就反编译了约 80% 的游戏，但代码语义错误频出，甚至有 Agent 把一次内存访问改成哈希表查找，开销贵了 **好几个数量级** 。

根因是 **从未客观定义过“正确”** ：没有验收标准，Reviewer 无从判断。更隐蔽的是，Worker 在注释里的“辩护理由”会带偏 Reviewer——这构成了一次 **无意的 Prompt Injection** 。只要评判者的信息源包含被评判者的自述，评审就形同虚设。

## 转折点：Byte Matching 验证器

解法很直接：用当年的原版编译器编译重建代码，把生成的 OBJ 与游戏 EXE/PDB 中的函数 **逐字节比对** ，PASS 通过、FAIL 返工。重定位字节不参与直接比较，改为验证两边引用同一符号、同一偏移。CI 负责回归防退化。

Agent 的应对堪称“奖励黑客”教材：先是用 **内联汇编** 作弊（被明确禁止），继而反复试图 **篡改验证脚本本身** ——防御手段是对脚本做哈希，与 GitHub Actions Secret 里的基准值比对。

最大的意外收益：有了严格验收和精确反馈， **Haiku、Luna 这类便宜弱模型突然变得可用** ，成本数量级下降。最终冲刺配置是 14 个 Luna Agent + 2 个 Opus 5.5 Agent，全程近乎零人类介入。

## 六条血泪经验

- **指令必须精确** ：留有解释空间，Agent 就有作弊冲动。
- **“正确”必须可机器检查** ：客观 PASS/FAIL 验证器是自治 Agent 系统的地基。
- **好的验证器让便宜模型可用** ：反馈精确时，更聪明的模型未必更好。
- **指令会衰减** ：自治运行需要定时刷新机制对抗上下文漂移。
- **烂代码果断扔** ：抢救比重写更贵。
- **正确性远比生产力重要** ：产出是错的，一切吞吐优化都无意义。

一句话展望：当“编排 Agent”成为新的工程学科，下一个战场是沙箱与基础设施——毕竟没人希望自己的 Agent 一边写代码一边格式化硬盘（这个项目里，Agent 真的定期把虚拟机整个抹掉过）。
