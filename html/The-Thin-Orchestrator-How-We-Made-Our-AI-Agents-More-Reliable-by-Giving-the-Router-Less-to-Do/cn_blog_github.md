# Meta 的“瘦编排器”：把路由器的活变少，AI Agent 反而更可靠了

Meta 的数据管道团队遇到了一个反直觉的问题：他们给 AI Agent 塞的领域知识越多，它在生产环境里的表现反而越差。最终有效的解法不是更好的提示词，也不是更大的上下文窗口，而是让中央编排器几乎什么都不做——一个 1300 行的编排器，负责把 20 多种工作流路由给 14 个专门的子 Agent，自己不做任何领域推理。团队在工程博客中把这个做法称为“瘦编排器”（thin orchestrator）模式，并给出了它为什么有效、如何在其他团队复用的完整论证。

## 一个“什么都知道”的 Agent，在生产环境开始幻觉

Meta 的推荐系统数据管道采用配置即代码的架构：Python 配置驱动 C++ 代码生成，代码生成喂给数据处理服务，服务再填充分析系统。给一个新数据列做接入（onboarding），需要横跨三个代码仓库、三种编程语言，在配置注册表、后端服务和数据管道之间做协调修改，每一列的数据到位之前最多要经过六个必须保持同步的阶段。

团队最初的思路和大多数人一样：造一个“全知”的 Agent。他们把全部领域知识都装了进去——配置模式、代码生成规则、管道路由逻辑、验证要求，以及 10 多个数据源的填充模式。这个 Agent 在演示中表现很好，但在生产环境开始幻觉。

问题出在上下文规模上。团队发现，越过某个上下文阈值之后，新增知识不是在提升而是在拖累性能。Agent 会把概念交叉污染：把一个子系统的字段命名习惯套用到另一个子系统，或者把为数据源 A 设计的代码生成模式用在数据源 B 的填充任务上。团队引用了西奈山伊坎医学院 Windreich 人工智能与人类健康系一篇预印本的发现作为对照：在 80 个任务一批的规模下，编排式多 Agent 系统保持了 65.3% 的准确率，而单 Agent 掉到了 16.6%，同时 token 用量最多降低 65 倍。论文作者把原因归结为任务隔离阻止了上下文干扰——Meta 团队经历的正是这一结论的反面：一个 Agent 溺死在自己的知识里。

他们也评估过另一条单 Agent 路线：为每个任务手工编写定制的系统提示词。这样做的成功率能到 70–80%，但一旦没有这种逐任务的“人工扶持”，成功率就跌到 10–20%。团队的结论是，这不是提示词工程问题，而是架构问题。

## 解法：只管路由的编排器，加 14 个各管一摊的专家

新架构分成两层。

第一层是确定性的编排器，它不做任何领域工作：不写代码、不生成配置、不碰代码库。它只做四件事——分类用户意图、收集必填字段、执行可靠性检查、把工作委派给正确的专家。它就是一个路由器。

第二层是 14 个专门的子 Agent，每个都是拥有隔离上下文的领域专家。模式管理 Agent 只懂配置注册表，填充 Agent 只懂 10 个数据源各自的代码生成方式，验证 Agent 只懂构建系统和质量检查。没有任何一个 Agent 能看到全局——团队强调，这是特性，不是缺陷。

编排器对每个请求都执行固定的七步协议：

1. 读取相关子 Agent 的指令文件；
2. 检查目标是否已存在（防止重复创建）；
3. 向用户收集必填字段；
4. 自动推断可以推断的信息（仓库类型、已有配置）；
5. 可靠性门禁检查（是否有活跃告警、是否需要指定审核人）；
6. 携带完整上下文委派给子 Agent；
7. 处理结果、暴露错误、确认成功。

关键在于：第 1–5 步和第 7 步全部是确定性逻辑，只有第 6 步涉及大模型推理，而且这次推理发生在一个只加载了自身领域知识的隔离子 Agent 内部。LLM 被限制在最需要它、也最不容易闯祸的地方。

## 用工作流模板扩展，而不是造新 Agent

![Meta 瘦编排器的工作流架构](https://raw.githubusercontent.com/kebijuelun/research-blog-repo/main/html/The-Thin-Orchestrator-How-We-Made-Our-AI-Agents-More-Reliable-by-Giving-the-Router-Less-to-Do/images/Meta-Thin-Orchestrator-workflow.jpg)

> 图解：左侧，用户（Actor）的 Prompt 进入一个只做路由和协调、无状态、不含领域知识的 Workflow Management 层，响应也由此返回；该层通过 Workflow Templates 调用右侧的模板细节。右侧框内是“概率推理与隔离领域上下文”区域——Schema Management、Validation、Onboarding、Testing 等子 Agent 各自持有受限的领域上下文，下方接存储。图中两处标注点明设计原则：领域智能被隔离进有作用域的模板里，编排层本身与领域无关。

团队在架构上分离了两件事：“需要发生什么”和“每一步具体怎么做”。编排器通过工作流模板定义阶段顺序——这些模板是确定性的状态机，用来约束 LLM 的决策空间。团队给出了三个例子：

- 列接入：Schema → Validation → Population → Testing
- 事件接入：Schema → Population → Validation → Testing → Event Processing
- 管道迁移：Assessment → Planning → Population → Validation → Monitoring

每个模板都以不同顺序复用同一池 14 个子 Agent。当需要支持管道迁移这个全新用例时，团队没有写任何新 Agent，只是写了一个新的工作流模板，把已有 Agent 换了个顺序编排。零新增 Agent 代码，获得完整生产能力。

子 Agent 本身也遵循统一结构：知识来源（运行时加载哪些领域文件，通常每个几千 token）、预收集清单（委派前编排器必须收齐什么）、逐步工作流（领域内的执行计划）、发现模式（如何在 monorepo 里找到相关代码模式）、故障排查（常见错误到解决方案的映射）。这种一致性意味着新增一个子 Agent 是照模板填空，而不是从零开始的工程——第 15 个子 Agent 在结构上和第 1 个一模一样。

知识文件的处理方式同样服务于“瘦”：25 个以上按工作流领域组织的知识文件在子 Agent 执行时按需加载，而不是嵌进编排器。知识文件更新后，下一个会话自动使用最新版本，编排器无需任何改动；同一套知识文件还能服务该 Agent 的多个平台实现。

> 图解：表中列出了瘦编排器系统的生产指标——无需逐任务提示词工程时成功率约 70%（对照：单 Agent 在无手工提示时仅 10–20%），生产回滚率约 0.2%，上线时 SWE-bench 风格的评测得分约 95.5%，累计落地代码变更 1,282 个，处理数据列 1,384 列，同一批 Agent 支持 5 个工作流领域，且不需要任何人工提示词工程。

## 为什么“重编排器”会失败

常规做法是让编排器成为系统中最聪明的组件：给它全部上下文，让它既推理“做什么”又推理“怎么做”。团队认为这条路在规模小、步骤简单时可行，但恰恰在你最需要它的时候失效——大规模、多步骤、跨异构子系统的场景下。

瘦编排器有效，是因为它让架构边界和计算边界对齐。团队列出了四条理由：

- **确定性决策保持确定性。**“这个任务该交给哪个子 Agent”是路由问题，不是推理问题，不该动用 LLM。
- **上下文隔离防止交叉污染。**负责数据源 A 的填充 Agent 永远看不到数据源 B 的模式，它想幻觉错的对象也没有素材。
- **故障被限制在局部。**某个子 Agent 失败，编排器可以重试或上报，失败不会污染编排器自身的状态或其他子 Agent 的上下文。
- **每一层可以独立改进。**换一个更强的模型，14 个子 Agent 同时受益；更新一个知识文件，立即生效；加一个新的工作流模板，不动任何 Agent 就解锁新能力。没有任何单个组件承受整个系统的重量。

团队还给出了一个从失败模式出发的论证：重编排器一旦幻觉，错误会向下游全面扩散——路由到错误的 Agent、收集错误的字段、跳过可靠性检查。瘦编排器的路由和可靠性步骤不依赖 LLM 推理，只遵循固定协议，留给幻觉的空间很小；创造性工作全部发生在下游隔离的、限定领域的上下文里，幻觉风险被压低，失败也被圈在局部。

## 其他团队可以照搬的五条做法

团队强调这个模式与数据管道无关，并给出五条可操作建议：

1. **把路由和推理分开。**如果你的编排器在做领域决策，它就做太多了。路由应该是确定性的——关键词匹配、意图分类、字段收集；所有领域推理都推进隔离的子 Agent。
2. **把子 Agent 设计成结构统一的专家。**每个子 Agent 应该有相同的骨架：知识来源、所需输入、执行步骤、错误处理。这样新增能力是模板化工作，而不是架构变更。
3. **用工作流模板而不是新 Agent 来扩展。**接到新用例时先问：能不能把已有 Agent 换个顺序编排？如果一个 Agent 无法跨工作流复用，说明它和具体用例耦合得太紧。
4. **知识在运行时加载，而不是构建时嵌入。**嵌进编排器意味着每次更新都要重新部署；按需加载则更新即时生效，且跨所有平台生效。
5. **显式画出确定性/概率性的边界。**对每个组件问一句：这是路由决策（确定性）还是推理任务（概率性）？编排器站一边，子 Agent 站另一边，不要混。

## 边界与下一步

需要说明证据的边界：文中最硬的数字——约 70% 成功率、0.2% 回滚率、95.5% 的上线评测分、一小时内的配置准备时间——都来自 Meta 团队自己的生产系统报告，针对的是他们这类配置即代码、阶段固定、领域边界清晰的管道任务，尚没有第三方复现。这套模式是否同样适用于开放式、阶段难以预先枚举的任务，原文没有回答。

团队的下一步是把这套架构扩展到更多管道领域和更多的数据列。他们的组合式论点是：扩展意味着新增工作流模板和知识文件，而不是重建 Agent，因此架构本身应该能随规模成立。团队还在探索让系统从生产使用中持续改进——用自动化反馈回路识别失败模式，并针对子 Agent 的知识提出改进建议，但任何变更都必须经过人工审核把关。

回到最初那个反直觉的结论：在这个 AI Agent 系统里，最重要的组件恰恰是干活最少的那个。编排器保持薄，专家保持深，整套系统反而更可靠。
