# Meta 的“瘦编排器”：路由器干得越少，AI Agent 越可靠

Meta 数据管道团队发现一个反直觉现象：给 AI Agent 塞的领域知识越多，它在生产环境的表现反而越差。解法不是更好的提示词，而是让编排器几乎什么都不做——一个约 1300 行的确定性编排器，只把 20 多种工作流路由给 14 个专门子 Agent，自己不做任何领域推理。

## “全知” Agent 开始幻觉

背景是配置即代码的推荐系统数据管道：新数据列接入横跨三个仓库、三种语言，最多六个须保持同步的阶段。团队最初把配置模式、代码生成规则和 10 多个数据源的填充模式全装进一个 Agent，演示很好，生产环境却开始幻觉——把数据源 A 的代码生成模式套用到数据源 B。一篇预印本提供了对照：80 个任务一批时，编排式多 Agent 保持 65.3% 的准确率，单 Agent 掉到 16.6%，token 最多省 65 倍。为每个任务手工写定制提示词能把成功率提到 70–80%，去掉人工扶持就跌回 10–20%：这是架构问题，不是提示词问题。

## 只管路由的编排器

编排器只做四件事：分类意图、收集必填字段、可靠性检查、委派给正确的专家。14 个子 Agent 各持隔离的领域上下文，没有一个能看到全局——这是特性而非缺陷。每个请求走固定七步协议，只有“携带完整上下文委派”一步涉及大模型，且发生在隔离的子 Agent 内部。

扩展靠工作流模板而非新 Agent：模板是定义阶段顺序的确定性状态机（如列接入：Schema → Validation → Population → Testing），换顺序复用同一池子 Agent，支持管道迁移这个新用例时零新增 Agent。25 个以上知识文件运行时按需加载，更新后下个会话即生效。

## 效果与原因

团队报告：无逐任务提示词工程时成功率约 70%（对照单 Agent 的 10–20%），生产回滚率约 0.2%，上线评测约 95.5 分，累计落地 1,282 个代码变更、1,384 列数据。新列的配置准备从三到四天压到一小时内，约三分之二变更无需明显人工修改。

为什么有效：路由是确定性问题，不依赖 LLM，幻觉就没有扩散通道；上下文隔离防交叉污染；故障被圈在局部；各层可独立改进——换更强的模型，14 个子 Agent 同时受益。

## 做法与边界

五条建议：路由与推理分离；子 Agent 结构统一；用模板而非新 Agent 扩展；知识运行时加载；显式区分确定性路由与概率性推理。须说明：上述数字均来自 Meta 自己的生产报告，针对阶段固定的管道任务，尚无第三方复现；是否适用开放式任务，原文未回答。回到开头：最重要的组件恰恰是干活最少的那个——编排器保持薄，专家保持深，系统反而更可靠。
