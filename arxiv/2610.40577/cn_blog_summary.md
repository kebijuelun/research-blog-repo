# Multi-View MoE：让路由偏好重塑专家计算

稀疏 MoE 的容量扩展依赖条件计算，但单一路由不仅可能选错专家，还让所有入选专家接收同一输入；Multi-View MoE 让路由分数同时决定“选谁”和“看什么”，在 10B 总参数、每 Token 激活约 1B 的模型上训练 708B Token 后，将九项任务平均分从 33.07 提至 34.25，且 Expert FLOPs 与 All-to-All 通信量不变。

## 从共同投票到专家专属输入

- **Multi-Router 共同选专家**：多个独立路由头从完整隐藏状态打分，各自经过 Sigmoid 后求和，再执行一次 Top-$k$。负载均衡偏置只参与选择，输出门控仍用未加偏置的分数。必须先做非线性再求和，否则多个线性路由头会退化为一个。
- **Multi-View 构造输入**：路由头与 Latent View 一一配对，各 View 由独立投影生成。对每个入选专家，将其原始分数跨路由头归一化，得到 View 混合比例，再把不同 View 混合成该专家专属输入。
- **只混合输入，不重复计算**：同一 Token 的不同专家可看到不同内容，但每个入选专家仍只前向计算一次，并非按 View 分别运行后再混合输出。

笔者认为，这一设计的聪明之处是复用求和前原本被抹掉的相对路由偏好，无需另设混合网络；新增开销主要集中在轻量投影与路由接口。

## 收益明确，但并非项项提升

主实验采用 24 层、256 个 Routed Expert、每 Token 激活 8 个的统一骨干：

- Multi-Router 将九任务均值提高 0.62 点，完整 Multi-View 再提高 0.56 点，累计提升 **1.18 个百分点**。
- Multi-View 在 GPQA 上比基线高 **5.60 点**，CMMLU、MMLU 和 MMLU-Redux 也均提升；但 MMLU-Pro 与 BBH 分别下降 0.16 和 0.34 点，收益并不均匀。
- 最后 1000 步的平均 Loss 从基线 2.25621 降至 2.24883，改善 **0.00738**。

机制实验进一步排除了“只是多几个参数”的解释：多路由分数与专家输出效用代理的全局 Spearman 相关由 0.1245 升至 0.1346，相对提高 8.1%；固定专家和门控、仅打乱 View 比例后，NLL 上升，说明模型确实利用了 Token、专家与混合比例之间的对应关系。

## 成本边界与结论

- **有效**：路由偏好同时用于专家选择和输入构造，平均分与训练 Loss 均改善。
- **有代价**：双 View 全模型增加约 1887 万参数，约占 10B 骨干的 **0.19%**，投影和打分并非零开销。
- **有边界**：保持不变的是激活专家数、Expert FLOPs 和 All-to-All 通信量；证据目前仍限于单一骨干、种子和训练阶段，尚需更多规模与任务验证。
