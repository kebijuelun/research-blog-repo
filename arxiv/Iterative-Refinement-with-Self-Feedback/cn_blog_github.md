# Self-Refine：让大模型自己改稿

大模型一次生成的答案往往“能看”，却未必满足复杂任务的多重要求，例如对话既要相关、有趣，又要具体、安全。这种一次性生成模式限制了模型在开放创作、代码优化和多约束推理中的上限。Self-Refine 的核心思路很直白：让同一个 LLM 先写初稿，再给自己提出具体反馈，最后根据反馈反复改稿，全程不更新参数。论文在 7 类任务上报告了平均约 20 个百分点的绝对提升；其中 GPT-4 的对话偏好分从 25.4% 升至 74.6%，代码优化比例从 27.3% 升至 36.0%。

## 一、为什么需要“自我改稿”

人类写邮件、写代码时，很少把第一稿当成终稿。我们先产出草稿，再检查语气、逻辑或效率，最后针对性修改。LLM 的一次解码则更像“落笔后不许回头”：即使它具备识别问题和修改答案的能力，也没有机会显式调用这些能力。

已有的迭代改进方案通常有三类成本：

- **训练独立 Refiner**：PEER、Self-Correct 等方法需要为特定领域训练修改器，迁移到新任务时要重新准备数据或训练。
- **依赖外部反馈**：人工偏好、编译器、单元测试、Wikipedia 编辑记录或奖励模型都能提供信号，但不一定适用于开放式生成。
- **更新模型参数**：RLHF 等强化学习方法把反馈压缩成标量奖励，再反向优化模型，流程和算力成本都高于测试时 prompting。

按论文当时的归类，Self-Refine 与相关方法的差异如下。

| 方法类别 | 无需监督训练的 Refiner | 无需监督训练的 Feedback | 多方面反馈 | 迭代改进 |
|---|---|---|---|---|
| 学习式 Refiner：PEER、Self-Critique、CodeRL、Self-Correct | 否 | 视方法而定 | 否 | 视方法而定 |
| Prompt 式 Refiner：Augmenter、Re³、Reflexion | 是 | 视方法而定 | 否 | 否 |
| Self-Refine | 是 | 是 | 是 | 是 |

这里的“无需监督训练”不等于“完全没有人工监督”。Self-Refine 仍需要人工设计 few-shot 示例，只是这些示例只进入 prompt，不用于训练模型参数。

因此，真正值得追问的不是“模型能不能再生成一次”，而是：**能否让模型把对自己输出的诊断，变成下一轮修改的明确指令？**

## 二、Self-Refine：同一个模型，轮流扮演三个角色

![Self-Refine 的反馈与改进循环](https://raw.githubusercontent.com/kebijuelun/research-blog-repo/main/arxiv/Iterative-Refinement-with-Self-Feedback/figures/preview.jpg)

> 图解：输入先在步骤 0 进入模型 $\mathcal{M}$，得到初始输出；步骤 1 中，同一个模型评价自己的输出并生成 Feedback；步骤 2 中，模型读取反馈并生成 Refine 后的新版本。步骤 1 和 2 循环执行，直到达到停止条件。图中没有第二个评价模型，也没有参数训练过程。

这个设计的聪明之处在于，它把“评价”和“修改”拆成两次显式生成。模型不必在一次前向过程中同时完成任务、发现问题并修复问题，而是像作者兼编辑一样，在不同 prompt 下切换角色。

### 2.1 初始生成：先得到一份可修改的草稿

给定输入 $x$、生成提示词 $p_{\mathrm{gen}}$ 和模型 $\mathcal{M}$，初始输出为：

$$
y_0 = \mathcal{M}(p_{\mathrm{gen}} \Vert x)
$$

其中 $\Vert$ 表示拼接。$p_{\mathrm{gen}}$ 是任务相关的 few-shot prompt，示例采用输入—输出对 $\langle x^{(k)},y^{(k)}\rangle$。这一步与普通的直接生成没有本质区别，后续收益主要来自反馈循环。

### 2.2 自我反馈：不仅说“不好”，还要指出怎么改

模型读取原输入和当前输出，生成自然语言反馈 $fb_t$：

$$
fb_t = \mathcal{M}(p_{\mathrm{fb}} \Vert x \Vert y_t)
$$

反馈提示词 $p_{\mathrm{fb}}$ 包含 $\langle x^{(k)},y^{(k)},fb^{(k)}\rangle$ 三元组。论文特别强调，好的反馈应同时满足两个条件：

- **Specific（具体）**：定位到需要修改的短语、代码结构或推理步骤，而不是只说“质量不好”。
- **Actionable（可执行）**：给出能够直接指导下一步修改的动作，而不是只打一个低分。

例如，“提高代码效率”是泛泛评价；“这段代码用循环暴力求和，可以改用 $n(n+1)/2$”才同时指出问题和修复路径。

论文用两个例子展示了这种反馈如何进入改稿过程。对话任务中，初稿只说“乒乓球有助于社交和保持活跃”，反馈指出它没有提供乒乓球信息，也没有充分理解用户需求；修改稿随后补充了这项运动需要快速反应和手眼协调，并询问用户是否想学习。

代码优化任务则更直观：

```python
# 初始输出：计算 1 + 2 + ... + n
def sum(n):
    res = 0
    for i in range(n + 1):
        res += i
    return res
```

模型生成的反馈是：循环属于暴力计算，可改用求和公式。随后得到：

```python
# 根据反馈改进
def sum_faster(n):
    return (n * (n + 1)) // 2
```

> 图表解读：原论文的任务示例图按“初始输出 → 反馈 → 改进输出”排列。对话示例体现内容与人际互动质量的改进，代码示例则把 $O(n)$ 循环改成 $O(1)$ 公式，说明同一框架可以处理自然语言和源代码。

### 2.3 根据反馈改稿：把历史错误也放进上下文

最简形式下，Refine 只读取当前输出和当前反馈：

$$
y_{t+1} = \mathcal{M}(p_{\mathrm{refine}} \Vert x \Vert y_t \Vert fb_t)
$$

实际算法还会保留历轮输出与反馈，让模型知道自己之前犯过什么错误：

$$
y_{t+1} = \mathcal{M}(p_{\mathrm{refine}} \Vert x \Vert y_0 \Vert fb_0 \Vert \cdots \Vert y_t \Vert fb_t)
$$

$p_{\mathrm{refine}}$ 使用 $\langle x^{(k)},y_t^{(k)},fb_t^{(k)},y_{t+1}^{(k)}\rangle$ 四元组，示范“如何按照反馈修改”。保留历史有助于避免重复错误，但也会使上下文随轮数增长，这是实际部署时必须考虑的 Token 成本。

### 2.4 循环与停止：固定轮数或让模型打分

Feedback 和 Refine 交替执行，停止条件可以是到达指定轮数，也可以是反馈中出现停止标记或标量分数。主实验最多进行 4 轮；某些任务会选择得分最高的历史版本，而不是机械地返回最后一版。

```text
输入：x、模型 M、三类 prompt、停止条件 stop
y0 = M(p_gen || x)

for t = 0, 1, 2, ...:
    fb_t = M(p_fb || x || y_t)
    if stop(fb_t, t):
        break
    y_(t+1) = M(p_refine || x || y0 || fb0 || ... || yt || fb_t)

返回最终输出；多指标任务可按分数选择最佳历史输出
```

至此，方法本身只需要一个基座模型和三组 prompt。接下来更关键的问题是：这种循环究竟在哪些任务上有效，收益又来自哪里？

## 三、实验设计：7 类任务、3 个基座、3 种评价

### 3.1 任务与数据

| 任务 | 数据与规模 | 核心目标 | 主要指标 |
|---|---|---|---|
| Sentiment Reversal | 1000 条评论段落 | 反转整段评论的情感 | 人类或 GPT-4 偏好 |
| Dialogue Response Generation | FED 数据集，任务表列出 372 段对话 | 生成相关、具体、有趣且安全的回复 | 人类或模型偏好 |
| Code Optimization | PIE，1000 个程序 | 在保持功能的前提下提升运行效率 | 被优化程序比例 |
| Code Readability Improvement | CodeNet 随机选取 300 个程序 | 改善变量命名、注释和模块化 | 合适变量名比例等 |
| Math Reasoning | GSM8K，1319 道题 | 修复数学推理或 Python 解答 | Solve Rate |
| Acronym Generation | 新整理 250 个缩写 | 兼顾发音、拼写、相关性和联想 | 人类或 GPT-4 偏好 |
| Constrained Generation | CommonGen-Hard，200 个样本 | 在连贯句子中覆盖 20–30 个概念 | Concept Coverage |

三个主要基座分别是 GPT-3.5（`text-davinci-003`）、ChatGPT（`gpt-3.5-turbo`）和 GPT-4；代码任务还测试了 Codex（`code-davinci-002`）。即使基座本身善于遵循指令，作者仍统一使用 few-shot prompt 实现 Feedback 与 Refine，以减少模型间设置差异。主实验报告使用温度 0.7，最多迭代 4 轮。

### 3.2 指标不能混着看

论文使用三类评价：

1. **任务自动指标**：数学题看解题率，代码优化看被优化程序比例，约束生成看概念覆盖率。
2. **盲测人类偏好**：标注者不知道两个候选分别来自哪种方法，只选择更符合任务要求的输出。
3. **GPT-4 偏好代理**：用于情感反转、对话和缩写等缺少统一自动指标的任务；它与人类偏好的一致率分别为 82%、71% 和 68%。代码可读性则让 GPT-4 估计上下文合适的变量名比例。

因此，主表中的数字都应以百分比理解，但不同行并不是同一种“准确率”。

| 任务 | GPT-3.5 Base | GPT-3.5 + Self-Refine | ChatGPT Base | ChatGPT + Self-Refine | GPT-4 Base | GPT-4 + Self-Refine |
|---|---:|---:|---:|---:|---:|---:|
| Sentiment Reversal | 8.8 | **30.4**（+21.6） | 11.4 | **43.2**（+31.8） | 3.8 | **36.2**（+32.4） |
| Dialogue Response | 36.4 | **63.6**（+27.2） | 40.1 | **59.9**（+19.8） | 25.4 | **74.6**（+49.2） |
| Code Optimization | 14.8 | **23.0**（+8.2） | 23.9 | **27.5**（+3.6） | 27.3 | **36.0**（+8.7） |
| Code Readability | 37.4 | **51.3**（+13.9） | 27.7 | **63.1**（+35.4） | 27.4 | **56.2**（+28.8） |
| Math Reasoning | 64.1 | **64.1**（0） | 74.8 | **75.0**（+0.2） | 92.9 | **93.1**（+0.2） |
| Acronym Generation | 41.6 | **56.4**（+14.8） | 27.2 | **37.2**（+10.0） | 30.4 | **56.0**（+25.6） |
| Constrained Generation | 28.0 | **37.0**（+9.0） | 44.0 | **67.0**（+23.0） | 15.0 | **45.0**（+30.0） |

> 表解：每一对 Base 与 Self-Refine 都使用同一个基座模型，因而主要差异来自测试时反馈循环。偏好类任务和约束生成的提升最明显；数学推理几乎没有变化，说明“会解题”并不等于“会发现自己的错”。

### 3.3 主要结果说明了什么

- **多目标、开放式任务收益最大**。GPT-4 对话偏好增加 49.2 个百分点；ChatGPT 的代码可读性增加 35.4 个百分点。
- **约束越多，初稿越容易遗漏**。CommonGen-Hard 要求覆盖 20–30 个概念，反馈可以逐项找出缺失概念，再让下一轮补齐。
- **强模型往往能更好地利用反馈**。即使 GPT-4 的 Base 在某些任务上起点更低，Self-Refine 后仍能取得很高结果，支持了“强模型的能力未必在一次生成中完全释放”这一判断。
- **数学任务是明显例外**。ChatGPT 在 94% 的数学样本反馈中表示“看起来没问题”，瓶颈主要是错误定位，而不是修改能力。

在人类盲测中，每个数据集评价 150 个样本，结果同样偏向 Self-Refine：

| 任务 | Self-Refine 被选比例 | Direct 被选比例 | 两者相当 |
|---|---:|---:|---:|
| Sentiment Transfer | 75.00% | 21.43% | 3.57% |
| Acronym Generation | 44.59% | 12.16% | 43.24% |
| Response Generation | 47.58% | 19.66% | 32.76% |

附录还给出 Wilson 置信区间和显著性标记：GPT-4 的增益几乎都达到统计显著，ChatGPT 和 GPT-3.5 分别在 7 个数据集中的 4 个和 3 个上显著。需要注意的是，附录表注写明 95% 置信区间，而相邻正文另处出现 99% 的表述；复现显著性检验时，应回查原始实验设置，而不能混用这两个口径。

平均提升只能说明整体趋势。要判断方法是否值得使用，还需要拆开看反馈质量、迭代次数和模型能力分别贡献了什么。

## 四、消融与误差分析：收益到底来自哪里

### 4.1 具体反馈比“再试一次”更重要

作者比较了 Self-Refine 反馈、泛泛反馈和不给显式反馈三种设置。后两者仍可进行迭代，但缺少具体、可执行的诊断。

| 任务 | Self-Refine 反馈 | Generic Feedback | No Feedback |
|---|---:|---:|---:|
| Code Optimization | **27.5** | 26.0 | 24.8 |
| Sentiment Reversal | **43.2** | 31.2 | 0 |
| Acronym Generation | **56.4** | 54.0 | 48.0 |

> 表解：代码优化使用 ChatGPT，缩写生成使用 GPT-3.5；情感反转的实验也使用 ChatGPT。三项指标沿用各自主实验定义。情感反转在没有反馈时完全失效，说明“重复生成”本身不是核心，反馈内容才是关键。

这组结果也解释了为什么自然语言反馈比单一标量更灵活：一句“避免 for 循环中的重复计算”同时携带了错误位置和修改方向，而“效率较低”只指出了问题，没有给出定位与修改路径。

### 4.2 多轮有效，但边际收益递减

这组数据在原文中以“分数表 + 增益柱状图”呈现，三个模型的结果取平均。这里保留相同的逐轮数值，并将每轮增益 $\Delta$ 放入括号。

| 任务 | $y_0$ | $y_1$（$\Delta$） | $y_2$（$\Delta$） | $y_3$（$\Delta$） |
|---|---:|---:|---:|---:|
| Code Optimization | 22.0 | 27.0（+5.0） | 27.9（+0.9） | **28.8**（+0.9） |
| Sentiment Reversal | 33.9 | 34.9（+1.0） | 36.1（+1.2） | **36.8**（+0.7） |
| Constrained Generation | 29.0 | 40.3（+11.3） | 46.7（+6.4） | **49.7**（+3.0） |

> 图表解读：横轴是从初稿 $y_0$ 到第三轮 $y_3$ 的迭代过程，纵轴沿用各任务分数。第一轮通常贡献最大，后续仍可能改善，但增益整体收窄。这意味着实际系统应把停止条件与调用成本一起优化，而不是默认轮数越多越好。

质量也并非总是单调上升。缩写生成要同时权衡多个维度，某一轮可能更好读，却在其他维度退步：

| 轮次 | 缩写 | 发音（5） | 拼写（5） | 相关性（5） | 积极联想（5） | 总分（25） |
|---:|---|---:|---:|---:|---:|---:|
| 1 | USTACCSF | 1 | 1 | 5 | 3 | 11 |
| 2 | TACC-SIM | 4 | 4 | 5 | 3 | 17 |
| 3 | TACCSF | 1 | 2 | 5 | 3 | 12 |
| 4 | TACC-SIMF | 4 | 4 | 5 | 3 | 17 |

因此，作者让反馈模块输出多方面的数值分数，并在多轮结果中选择最佳版本。这比“最后一稿必然最好”的假设更稳妥。

### 4.3 不是简单多采样：1 个改稿结果对 4 个独立初稿

一个自然的质疑是：Self-Refine 会不会只是因为生成了更多 Token？作者让 ChatGPT 独立采样 $k=4$ 个初始输出，再拿一个 Self-Refine 输出与这 4 个结果做 1-vs-$k$ 比较。只有 Self-Refine 胜过全部 4 个初稿，才算它获胜。

即便这个比较对 Self-Refine 更严格，人类仍更偏好它的输出。这说明收益不能简单归因于“多生成几次”，针对性的反馈与修改确实提供了额外价值。

### 4.4 失败首先卡在反馈，而不是改稿器

作者人工检查了 Code Optimization 和 Math Reasoning 上共 70 个样本，其中成功、失败各 35 个。失败案例中：

| 失败原因 | 占比 |
|---|---:|
| 反馈找错了错误位置 | 33% |
| 反馈给出了不合适的修复方案 | 61% |
| 反馈正确，但 Refiner 没有正确落实 | 6% |

成功案例中，61% 是准确反馈引导了精确修复；另有 33% 即使反馈部分有误，Refiner 仍能修正原输出。这体现了一定的容错性，但整体结论依然明确：**提高自我评价的正确率，比单纯加强改稿能力更关键。**

对话任务的附录分析也支持这一判断。反馈侧出现了 25% 的错误反馈、30% 的泛泛反馈和 10% 的错误打分；改稿侧则有 25% 忽略反馈、20% 引入新问题、10% 对坏反馈不够稳健。另一方面，60% 的分析案例中，模型能够忽略错误或泛泛反馈，避免被带偏。

### 4.5 弱模型未必玩得转这套循环

Vicuna-13B 能生成初始答案，却难以稳定遵循反馈和改稿格式：它可能生成空反馈、重复原答案，或跑偏成一段虚构对话。即使直接提供 Oracle 或硬编码反馈，它也经常无法按 prompt 修改。

作者进一步尝试 Mixed-Refine：Vicuna-13B 只负责初始化，ChatGPT 负责反馈和改稿。GSM8K 成绩从 24.18% 提升到 40.5%。这证明了“弱模型起草、强模型编辑”的潜力，但它已经不再是严格意义上的单模型 Self-Refine。

## 五、七类任务的落地细节与复现要点

主结果给出的是共性结论，附录则揭示了每个任务如何定义反馈。对复现者而言，真正需要设计的是各任务的评分维度和停止条件，而不是重写算法框架。

### 5.1 情感反转：逐词定位“还不够正面或负面”

任务不是改写单个句子，而是反转整段评论的情感。Feedback 会指出仍与目标情感冲突的具体词语，例如 `questionable`、`subpar`、`underwhelming`，再建议用更强或更弱的表达替换。循环最多 4 轮，达到目标情感即可停止。

附录还报告了基于 VADER 分类器的检查：目标为正面时，Direct 与 Self-Refine 都达到 100% 分类准确率；目标为负面时，两者分别为 92% 和 93.6%。这说明简单分类器很难区分“情感方向正确”和“表达足够鲜明”，所以论文更重视偏好评价。

在另一组定点反馈消融中，情感偏好率从有信息量反馈的 85% 降至 73%，表达生动性的偏好率从 80.09% 降至 58.92%。它与主文消融的共同结论是：指出具体词语，比笼统地说“情感不对”有效得多。

### 5.2 对话生成：把“好回复”拆成 10 个维度

对话反馈覆盖 Relevant、Informative、Interesting、Consistent、Helpful、Engaging、Specific、Safe、User Understanding 和 Fluent 十个方面，每项给出解释与分数。这样做比直接问“这个回复好不好”更容易定位改进方向。

附录设置中，初始化、反馈和改进均使用 few-shot prompt，最多迭代 3 轮；作者从非初始候选中选择总分最高的回复。自动评价使用 342 个测试实例，人类评价则随机抽取 100 个实例。

| 人类评价 | GPT-3.5 | ChatGPT | GPT-4 |
|---|---:|---:|---:|
| Self-Refine 胜 | 36.0 | 48.0 | 54.0 |
| Init 胜 | 23.0 | 18.0 | 16.0 |
| 两者相当 | 41.0 | 50.0 | 30.0 |

以论文中的乒乓球对话为例，初稿虽然相关、流畅、安全，却缺少信息、具体性和帮助性，总分为 20/30。修改稿加入入门建议，并用追问延续话题。这里的提升不是“辞藻更华丽”，而是多个可解释维度共同变好。

### 5.3 代码优化：反馈要指向算法瓶颈

PIE 任务要求优化功能正确的 Python 程序。Self-Refine 先诊断性能瓶颈，再将自然语言建议转成算法级修改。论文展示了一个从多重循环枚举转为 Dynamic Programming（动态规划）的例子：

```python
# 改进后的核心逻辑
def solve(amount):
    coins = [200, 300]
    prices = [380, 550]
    dp = [float('inf')] * (amount + 1)
    dp[0] = 0
    for i in range(len(coins)):
        for j in range(coins[i], amount + 1):
            dp[j] = min(dp[j], dp[j - coins[i]] + prices[i])
    return dp[amount]
```

> 代码图解读：原始基线几乎保留输入程序的多重嵌套循环，只改了少量逻辑；Self-Refine 的反馈明确指出“用六层嵌套循环枚举所有组合导致缓慢”，随后将其实现为 DP。论文将新方案的复杂度记为 $O(\text{amount}\times\text{coins})$。

附录的一组代码优化消融进一步区分了迭代与反馈：

| 设置 | 轮次 | 优化比例 | Relative Speedup | Speedup |
|---|---:|---:|---:|---:|
| Direct | — | 9.7 | 62.29 | 3.09 |
| Self-Refine 无反馈 | 1 | 10.1 | 62.15 | 3.03 |
| Self-Refine 无反馈 | 2 | 10.4 | 61.79 | 3.01 |
| Self-Refine | 1 | 15.3 | 59.64 | 2.90 |
| Self-Refine | 2 | **15.6** | **65.60** | **3.74** |

与更多基线比较时，也要避免过度概括论文结论。GPT-4 + Self-Refine 达到 36.0% 的优化比例，但 PIE Few-shot Best@32 为 38.3%；后者使用最多 32 个样本，而 Self-Refine 最多 4 轮。更准确的读法是：Self-Refine 以较少生成预算接近强基线，并非在所有代码优化比较中都排名第一。

### 5.4 代码可读性：从原代码直接开始“批评—编辑”

这一任务的 Init 是 no-op，即不另写初稿，直接对输入代码进行反馈。第 $k$ 轮可写成：先得到批评 $c_{k+1}=\mathrm{critique}(y_k)$，再生成 $y_{k+1}=\mathrm{editor}(y_k,c_{k+1})$，共执行 5 轮。

作者比较了反馈采样温度 $T=0.0$ 和 $T=0.7$，代码编辑器始终使用贪心解码。附录三张曲线均以 Iteration 为横轴，分别展示有意义变量比例、每行注释数和 Function Units；三项总体随迭代增加。较高温度的反馈更倾向于改变量名和补注释，贪心反馈则更倾向于模块化重构。

在 60 个由人类同步改写的样本上，结果如下：

| 方法 | 有意义变量比例 | 每行注释数 | Function Units |
|---|---:|---:|---:|
| 人类标注者改写 | 0.653 | 0.24 | 0.70 |
| Self-Refine（$T=0.0$） | 0.628 | 0.12 | **1.41** |
| Self-Refine（$T=0.7$） | **0.700** | **0.25** | 1.33 |

这些指标只衡量可读性的部分侧面，并不等价于完整的可维护性评价；但它们清楚展示了反馈目标如何改变最终代码风格。

### 5.5 数学推理：外部正确性信号暴露真正瓶颈

数学任务沿用 PaL（Program-Aided Language Models）的形式，用 Python 书写解答。Feedback 按语义完整的代码块逐段检查，Refine 再修复错误步骤。附录一组逐轮实验中，解题率从第 0 轮的 71.34% 依次变为 73.39%、75.06%、75.74% 和 76.19%。

然而主实验几乎不提升，因为模型经常无法发现错误。作者加入 Oracle Feedback：利用正确答案提供正确性信息，只在当前答案错误时进入 Refine。

| 数学设置 | GPT-3.5 | ChatGPT | GPT-4 |
|---|---:|---:|---:|
| Base | 64.1 | 74.8 | 92.9 |
| 普通 Self-Refine | 64.1 | 75.0 | 93.1 |
| Oracle 触发的 Self-Refine | **68.9** | **76.2** | **93.8** |

Oracle 设置带来的提升分别为 4.8、1.4 和 0.7 个百分点。它说明只要外部信号能可靠指出“这题错了”，后续修改就有价值；但 Oracle 使用标准答案信息，不能再被描述为纯自我反馈。

在附录的另一组 GSM8K 对比中，Self-Correct 使用 GPT-3 得到 45.9%，Self-Refine 使用同一级别基座得到 55.7%，提高 9.8 个百分点；GPT-4 + Self-Refine 报告为 94.5%，PaL + GPT-4 为 93.3%。这些数字对应附录的对比设置，不应与主表的不同实验配置混算。

### 5.6 缩写生成：用多维评分处理 trade-off

缩写需要在简洁、易读、易拼、与标题相关、积极联想和知名度之间折中。作者从公开缩写列表整理并人工过滤出 250 个样本，反馈模块按五个维度评价：发音、拼写、标题相关性、积极联想和是否常见。每个分数前先给出类似 Chain-of-Thought 的理由，再汇总为 25 分制评分。

以标题 “Sequence to Sequence Learning with Neural Networks” 为例：

| 评价维度 | GPT-3 输出：STSLWN | Self-Refine 输出：Seq2Seq |
|---|---|---|
| 发音 | 逐字母朗读，很困难 | “seq-two-seq”，容易 |
| 拼写 | 很难拼写 | 容易拼写 |
| 与标题关系 | 没有明显关系 | 包含 sequence，与标题相关 |
| 积极联想 | 没有明确含义 | 给人易用、自然的联想 |
| 知名度 | 不是常见缩写 | 接近常见词 sequence |
| 总分 | 5/25 | 20/25 |

这个例子也揭示了多维反馈的风险：优化某一维度可能伤害另一维度，因此需要保留历史候选并按总分选优，而不能只看最后一轮。

### 5.7 约束生成：把缺失概念和常识错误分开反馈

CommonGen 原本只要求句子包含 3–5 个相关概念，CommonGen-Hard 将数量提高到 20–30 个，并要求句子连贯、语法正确。Feedback 被拆成两部分：Concept Feedback 列出遗漏概念，Commonsense Feedback 判断句子是否合乎常识。

例如，“The horse catches the lasso and rides on it”不仅漏掉 `animal`，还存在“马抓套索并骑在套索上”的常识错误。修改过程先改为牛仔用套索抓马，再补齐剩余概念。

附录用 GPT-3.5 做了偏好比较：

| 方法 | Concept Winning Ratio | Commonsense Winning Ratio | Overall Winning Ratio |
|---|---:|---:|---:|
| Direct | 3 | 5 | 0 |
| Self-Refine | **35** | **10** | **32** |

> 表解：三个指标分别衡量概念覆盖、常识合理性和整体质量的胜出比例。Self-Refine 在概念覆盖和整体评价上优势明显；这里的 Winning Ratio 与主表的 Coverage 是不同口径，不应直接比较数值大小。

## 七、局限与实践边界

- **基座能力决定上限**：模型必须具备足够的 few-shot 学习和指令遵循能力，否则连反馈格式都难以稳定生成。
- **反馈没有天然正确性保证**：数学和代码错误分析都表明，错误定位与错误修复建议是主要失败来源。
- **多轮不等于单调变好**：多指标任务需要评分、候选保留和最佳版本选择，不能默认最后一稿最优。
- **测试时成本上升**：每轮至少需要反馈与改稿调用，历史上下文还会持续变长；论文没有系统报告延迟和 Token 成本，实际部署需单独评估。
- **评价存在模型依赖**：部分核心指标使用 GPT-4 作为裁判，应结合盲测人评理解，不能把模型偏好当作绝对质量。
- **可复现性仍有外部约束**：主要基座为闭源、付费模型，预训练语料、规模和偏差细节并不完全公开；作者开放代码、输出和 prompt 以缓解这一问题。
- **语言与安全覆盖有限**：实验只使用英文数据，方法也没有显式防止恶意 prompt 将迭代能力用于生成更有害的内容。

从工程角度看，最合理的落地方式不是无条件开启多轮，而是先定义可检查的反馈维度，再用停止分数、最大轮数和外部验证器控制成本与风险。数学中的 Oracle 实验尤其说明：在关键任务上，编译器、测试或规则校验等外部信号可以与 Self-Refine 互补。

## 八、总结

- Self-Refine 用同一个 LLM 完成初稿生成、自我反馈和反馈驱动改稿，无需额外训练或强化学习。
- 方法的核心不是多采样，而是生成 Specific 且 Actionable 的自然语言反馈，再把它显式用于下一轮修改。
- 7 类任务整体取得平均约 20 个百分点的绝对提升，对话、可读性和多约束生成收益尤其明显。
- 多轮迭代通常带来递减收益，多维任务还可能出现质量波动，因此需要停止条件和最佳候选选择。
- 最大瓶颈是自我反馈的准确性；弱模型、闭源基座、英文-only 评价和缺少安全约束仍限制其泛化。

这项工作开启的方向，是把“模型会生成”进一步推进为“模型会检查并修改”，同时用可靠外部信号弥补自我评价的盲区。论文代码、数据与 prompt 发布于 [selfrefine.info](https://selfrefine.info/)。
