# Olifant：用 CPU 记忆起草，让文本生成提速降耗

本地大模型生成不仅要快，还要省电，但传统投机解码的神经网络草稿模型本身就会消耗大量计算。对不能上传云端的医疗、法律等私密文本来说，能否在消费级设备上同时降低延迟和能耗，直接决定了生成式 AI 的可用性。Olifant 把草稿模型换成驻留 CPU 内存的记忆式分类器，不需要 GPU、反向传播或加速器显存。在领域匹配的法律文本上，它让无 KV cache 的 Mistral-7B 获得 **2.43 倍吞吐量**和 **2.51 倍能耗改善**；即使验证器已经启用 KV cache，仍能实现 **1.25 倍吞吐量**，并把能耗降到全研究最低的 **93 J/100 tokens**。

## 为什么快还不够：生成效率要同时看时间与能耗

大模型逐 token 生成，后一个 token 必须等前一个生成完毕，串行过程天然限制吞吐量。投机解码（Speculative Decoding）的思路很像“先让助手写提纲，再由专家集中审核”：便宜的草稿模型一次提出 $k$ 个 token，昂贵的大模型作为验证器，在一次前向传播中检查这些位置，并接受与自身 greedy 预测一致的最长前缀。

这个机制能否带来收益，取决于一笔简单的账：**一次验证多产出的 token，是否足以抵消生成草稿和验证草稿的开销。**过去研究更关注 wall-clock 时间，也就是真实等待时间；Olifant 则把每 token 能耗放到同等重要的位置。

另一个关键变量是 KV cache。Transformer 可以把历史 token 的 attention key 和 value 缓存下来，新 token 不必重新编码整段上下文。KV cache 让验证器快得多，却也意味着：**草稿模型原来能利用的“验证器很慢”这一优势被削弱了。**

因此，论文分别考察两种机制：

- **无 KV cache**：每轮都输入完整上下文和草稿，full-context attention 占主要成本，多附几个草稿 token 的边际成本很低。
- **有 KV cache**：历史上下文只 prefill 一次，逐 token 验证已经很便宜，草稿长度和草稿模型自身的成本变得敏感。

这两种机制并非简单的实验开关，而是会给出相反的最优草稿长度，甚至决定一种草稿模型是否还值得使用。

## Olifant：把草稿模型换成 CPU 上的记忆分类器

解决了“如何验证”的问题之后，下一个问题是：能不能把“起草”压缩到接近零成本？Olifant 的答案不是再训练一个小神经网络，而是使用 TiMBL 的 IGTree 算法，把语料编译成一棵可快速查询的前缀 trie。

### 从四 token 窗口预测下一个 token

所有训练语料都使用与验证器一致的 `mistralai/Mistral-7B-v0.1` SentencePiece tokenizer。模型取连续宽度 $w=4$ 的窗口，构造如下实例：

$$
(t_1,t_2,t_3,t_4)\rightarrow t_5
$$

IGTree 可以理解为 $k$-nearest neighbor 与决策树的结合。训练时，它按 **information gain（信息增益）**排列上下文位置，把最有预测力的位置放在树的较高层；查询时，从根节点逐层匹配，返回最深匹配节点中占多数的下一个 token。

如果四个 token 的完整上下文从未原样出现，模型也不会直接放弃，而是沿着最有信息量的位置回退到最深的匹配前缀，忽略较不重要的位置。相比只能复用原文片段的精确检索，这让它具备了一定的泛化能力。

训练阶段还会剪枝：若一个节点的多数标签与父节点一致，就不再存储该节点。论文报告，这通常可把 trie 缩小约 **95%**，同时不改变已存储上下文的查询结果。

笔者认为，这个设计最关键的不是“用了经典算法”，而是它同时满足了三个条件：**亚毫秒查询、与 verifier 共用 token 表示、可通过替换语料完成领域适配。**它把草稿从一次神经网络推理，变成了一次内存中的路径遍历。

### 四个实例库与三组对照

论文训练了四个 Olifant 模型，覆盖三类评测领域，并加入一个领域不匹配的大规模对照：

| 模型 | 训练语料 | 训练 token 数 | 作用 |
|---|---|---:|---|
| olifant-wikitext | WikiText-103 训练集 | 130M | 匹配通用文本 |
| olifant-pubmed | PubMed Summarization 训练集 | 536M | 匹配医疗文本 |
| olifant-eurlex | EurLex 训练集 | 94M | 匹配法律文本 |
| olifant-fineweb | FineWeb-edu 的一个 shard | 1.089B | 与三项测试来源均不重叠，作为通用对照 |

实例库完全放在 CPU RAM 中，大小从 eurlex 的 **145 MB**到 fineweb 的 **4.6 GB**。推理时按策略懒加载，并在用完后释放。

对照策略包括：

- **Plain**：不使用草稿，每个 token 调用一次 verifier。
- **4-gram**：在当前会话累计上下文上建立滑窗频率模型，能在线适应 verifier 刚生成的文本。
- **Neural**：TinyLlama-1.1B-Chat-v1.0，与 verifier 一起放在 MPS 加速器上，额外占用约 2 GB 加速器内存。

单 token 独立预测延迟的差距非常直观：4-gram 为 **0.09 ms**，Olifant 各版本为 **0.16–0.25 ms**，TinyLlama-1.1B 在 CPU 上则达到 **254 ms**。Olifant 比神经草稿便宜约三个数量级，而且不占用宝贵的加速器内存。

## 实验怎么测：三种文本、两种验证机制

验证器统一为 Mistral-7B-v0.1 base，以 `float16` 运行在 Apple M1 Max 的 MPS 上。所有实验使用同一台 32 GB RAM 的 Mac Studio，避免硬件差异干扰相对比较。

三项任务各取 100 个 prompt，每个 prompt 是原文前 50 个词，并生成 100 个 token：

- **通用文本**：WikiText-103 测试集。
- **医疗文本**：PubMed Summarization 测试集。
- **法律文本**：EurLex 测试集中的欧盟立法文件。

每种验证机制都遍历 7 种策略、$k\in\{3,5,8\}$ 和 300 个 prompt，共完成 6,300 次生成。评价指标包括 tokens/s、接受率、平均接受长度 MAL（Mean Accepted Length），以及相对 plain greedy 输出的 ROUGE-L。

无 KV cache 时，完整序列在一次前向传播中完成验证，可获得 $k+1$ 个位置的预测。有 KV cache 时，系统还加入两项设计：第一，首个草稿 token 直接由上一轮已经计算的 logits 验证，只有它被接受，才需要执行后续 $k$ token 的验证；第二，接受标准采用 token ID 的精确 greedy 匹配，使输出在精确算术下与 plain greedy decoding 一致。

## 无 KV cache：草稿几乎免费，领域匹配收益最大

在这种机制下，追加少量草稿位置的代价相对于完整上下文 attention 很小。因此，即使接受率不高，只要能够多接受一些 token，也往往可以提速。

最值得注意的是，**接受率下降不等于吞吐量下降。**olifant-eurlex 的 $k$ 从 3 增至 8 时，接受率从 38.1% 降至 19.9%，但 MAL 从 1.13 增至 1.53，吞吐量反而从 4.73 升至 5.55 tps。也就是说，虽然草稿的“命中率”降低了，每轮验证成功带出的 token 数却增加了。

收益并非无限增长。把法律任务扩展到 $k\in\{12,16,24\}$ 后，吞吐量在 $k=8$ 达到峰值，之后稳定在约 2.2 倍。MAL 仍从 1.53 缓慢增至 1.62，但额外草稿相对于约 150 token 的上下文已不再免费，因此 $k=8$ 是这里的实际最优点。

输出质量没有因加速而牺牲。所有策略在各项任务和各个 $k$ 上的平均 ROUGE-L 都为 0.956；相对独立 greedy 参考的少量偏差来自 MPS 浮点不确定性，并同样影响 plain decoding。

缓存机制消除了大部分 prompt 长度影响：无缓存时，法律与通用文本之间存在 18% 的吞吐量差距；有缓存后，这一差距缩小到 3%。与此同时，几乎所有投机收益都随 $k$ 增大而下降，与无缓存机制形成镜像。

领域不匹配的策略大多落在 0.9–1.1 倍附近。首 token 拒绝快速路径避免了严重损失，但 5%–20% 的接受率不足以产生明显收益。只有法律文本上的 olifant-eurlex 保留了较稳定优势：$k=3$ 时为 1.25 倍，$k=5$ 时为 1.26 倍、20.64 tps。

TinyLlama 的结果最具警示性：同一神经草稿在无缓存时能加速 1.15–1.20 倍，有缓存时却降至 **0.47–0.29 倍**。生成 $k$ 个草稿 token 的时间，已经超过 cached verifier 检查它们所需的时间。草稿接受率仍高也无济于事，因为成本发生在验证之前。

两种机制的接受率基本一致，例如法律文本上 olifant-eurlex 在 $k=3$ 时都为 38.1%。这确认收益变化来自验证成本，而非草稿模型行为改变。

cached speculative 输出的 ROUGE-L 为 0.955–0.959，cached plain 为 0.971。精确 ID 匹配在构造上保持 greedy 输出，抽查也确认了逐字节一致；残余差距来自 `float16` 下不同计算形状触发的 kernel 数值差异。

## 能耗：速度最快不一定最省电

吞吐量只回答“生成花了多久”，还不能回答“设备做了多少功”。论文使用 macOS `powermetrics`，以 1 Hz 采样 CPU、GPU 和 Neural Engine 的整机功率，并计算：

$$
\frac{\mathrm{J}}{100\ \mathrm{tokens}}
=\bar{P}\cdot\frac{t_{\mathrm{wall}}}{n_{\mathrm{tok}}}\cdot100
$$

其中，$\bar{P}$ 是生成窗口内的平均功率，$t_{\mathrm{wall}}$ 是实际耗时，$n_{\mathrm{tok}}$ 是生成 token 数。无缓存能耗使用每个配置 30 个 prompt 的独立测量；有缓存能耗则与吞吐量来自同一次运行，通过时间戳对齐功率日志。plain 配置的重复测量在两种机制下都保持在 2% 以内。

### 有 KV cache：时间与能耗开始脱钩

KV cache 本身就是最大的节能手段。cached plain 的能耗只有 **96–106 J/100 tokens**，约为无缓存基线的十分之一；节能幅度超过 6–7 倍的吞吐量提升，因为平均功率也从约 28 W 降到了 16.5 W。

原因不是运行时间，而是功率也变了。草稿越长，密集的 $k$ token 验证越能让加速器饱和：平均功率从 plain 的 16.4 W 上升到 olifant-eurlex、$k=8$ 时的 22.1 W。因此，法律任务在 $k=8$ 时虽然仍有 **1.16 倍速度**，却比 plain 多消耗 **1.18 倍能量**；$k=3$ 时才同时实现 **1.25 倍速度**和 **1.09 倍能耗改善**。

由此得到三个不同的最优点：无缓存速度偏好 $k=8$，有缓存速度偏好 $k=3$–5，有缓存能耗则偏好 $k=3$。**把速度最优配置直接当成能效最优配置，在这项实验中会得到错误答案。**

TinyLlama 同时承受两方面损失：生成时间翻倍，第二个神经网络又持续占用加速器。它从无缓存时节能 1.2–1.4 倍，变成有缓存时增加 2.5–3.8 倍能耗，达到 243–382 J/100 tokens。

### 训练能耗也要计入生命周期

Olifant 的训练只是在 CPU 上单次遍历语料，完成 tokenization、窗口化和 IGTree trie 编译，没有反向传播。最大的 fineweb 实例库包含 1.089B token，在评测机器上编译约 6 小时，估计耗能约 0.5 MJ。按无缓存实验的节能幅度，这笔一次性成本大约可在 1,000 次、每次 100 token 的生成中收回，较小语料的成本更低。

作为对照，TinyLlama 曾在 16 张 A100 上用约 90 天预训练 3T token，仅计算 GPU 板卡功率，能量量级约为 $10^{10}$ J，比记忆式模型高四到五个数量级。预训练模型当然可以通过大量下游任务摊销成本，但对 Olifant 而言，生命周期能耗主要来自推理，而非训练。

## 为什么有效：成本模型与领域冗余共同决定收益

实验结果之后，还需要回答两个问题：为什么 cached 机制下的实际盈亏平衡点没有理论值那么高？为什么法律文本上的收益远大于其他任务？

### 标准成本模型与 rejection fast-path

若验证 $k$ 个草稿 token 的成本等于逐个生成它们，标准投机解码的近似盈亏平衡条件为：

$$
\mathrm{acc\_rate}_{\mathrm{break\text{-}even}}\approx\frac{k}{k+1}
$$

这意味着 $k=3$ 时需要约 75% 的逐 token 接受率，$k=8$ 时约需 89%。论文中的模型都远未达到这一水平，却仍在 cached 机制下获得了收益。

关键在于首 token 拒绝快速路径：如果第一个草稿 token 就被拒绝，本轮无需额外执行 $k$ token 验证，失败成本接近 plain step。只有首 token 被接受后，才需要为更长的验证付费。因此，实际阈值下降到约 **20%–25% 的首 token 接受率**。低于此区间的策略接近盈亏平衡，法律 olifant-eurlex 的 38.1% 则足以形成正收益；TinyLlama 因顺序草稿太贵，在任何接受率下都不划算。

### 法律文本的优势来自跨文档公式化，而非单篇重复

论文进一步测量三类生成文本的冗余度。由于 greedy 验证保持输出，同一 prompt 下各策略生成相同文本，因此这些统计正好对应接受率所作用的文本。

| 任务 | 文内重复率 | 跨文档重合率 | gzip 压缩比 |
|---|---:|---:|---:|
| 通用 | 29.6% | 26.7% | 0.29 |
| 医疗 | 21.2% | 14.9% | 0.33 |
| 法律 | 12.1% | 73.6% | 0.18 |

文内重复率指一篇文本的 token 4-gram 中，此前已在同篇出现的比例；跨文档重合率指一篇文本的不同 4-gram 中，也出现在同任务其他文本里的比例；gzip 压缩比越低，整体冗余越高。

法律文本的文内重复率反而最低，只有 12.1%，所以单篇不断重复自己并不能解释 Olifant 的高接受率。真正的来源是跨文档公式化：法律文本中 73.6% 的不同 4-gram 会出现在其他法律文本里，gzip 压缩比也只有 0.18。离线领域训练捕捉的正是这种可复用结构。

方法本身也有独立贡献。在完全相同的法律文本上，$k=3$ 的接受率从 olifant-pubmed 的 7.5% 到 olifant-eurlex 的 38.1% 不等，4-gram 为 24.7%，神经草稿为 21.1%。文本保持不变，只有草稿模型变化，说明“任务有多少冗余”和“模型能捕获多少冗余”是两个可分离的因素。

## Olifant 与相邻方法：相似检索，不同归纳方式

4-gram 与 Olifant 都很便宜，但学习机制相反。4-gram 不离线训练，而是持续索引当前会话，包括 verifier 新生成的 token，因而能在线模仿输出分布，并捕捉近期词汇的重复爆发。Olifant 则在推理时固定，不能吸收会话反馈。

两者的表示也不同。Olifant 原生预测 Mistral 的 SentencePiece token，可直接进入验证流程；4-gram 预测以空白分隔的词，文本回退路径中只保留首个 sub-token，词级准确也难以完全转化为 token 接受率。

在领域匹配任务上，离线训练优势明显：法律文本的接受率为 38.1% 对 24.7%，$k=8$ 的无缓存加速为 2.43 倍对 1.20 倍。没有匹配模型时，4-gram 的在线适应则能缩小差距。一个自然方向是把固定实例库与会话级 recency/burstiness 组件结合，或直接在 verifier 的输出分布上训练 Olifant。

与 REST、inference-with-reference 等检索式方法相比，差别在于“检索片段”还是“压缩成预测器”：

- REST 用后缀数组精确匹配近期上下文，检索语料中的连续片段。
- inference-with-reference 从 prompt 已包含的参考文档中复制片段，适合 prompt 与输出高度重叠的场景。
- Olifant 把语料编译为下一 token 预测器，通过信息增益排序的回退为未见上下文也给出预测，但每次查询只产出一个 token。

前两者命中时可一次起草较长的原文片段，未命中时则没有草稿；Olifant 每次都能预测，却失去了长片段检索能力。三者谁更优，仍需要在同一硬件、同一 verifier 机制下直接比较。

## 结论与展望

- **草稿必须接近零成本**：verifier 越快，独立神经草稿越难收回自身推理开销。
- **Olifant 提供了一种低成本设计点**：0.16–0.25 ms 的 CPU 查询，不需要 GPU、反向传播或加速器内存。
- **领域匹配是收益核心**：法律文本无缓存时达到 2.43 倍吞吐量和 2.51 倍能耗改善，优势主要来自跨文档公式化结构。
- **KV cache 仍是第一优先级**：它把吞吐量提高 6–7 倍、能耗降至约十分之一，只有高接受率的 Olifant 能在此基础上继续增益。
- **速度与能耗需要分别调优**：cached 机制下，较长草稿会提高功率，最省电的 $k$ 可能小于最快的 $k$。

这项工作目前只验证了单一 M1 Max 平台、Mistral-7B、batch size 1 和 greedy decoding，领域模型也只在训练语料同源的 held-out 测试集上评估；未来需要检验其他模型与服务器 GPU、temperature sampling、batched serving、跨来源领域泛化，以及与检索式草稿和会话自适应混合方案的直接对比。
