# G-MTP：共享草稿头复用 KV，31B 提速 3.14 倍

投机解码的独立草稿模型需要重复 prefill、单独维护 KV Cache，抵消了加速收益并抬高端侧部署门槛。Google 的 G-MTP 将轻量多 token 预测头直接接入目标模型：Gemma 4 31B 在 H100 上从 73.2 提升至 230.1 tokens/s，端到端加速 **3.14 倍**；E4B 在 Samsung Galaxy S26 Ultra GPU 上也加速 **2.18 倍**。

## 核心方法：共享递归、零拷贝与词表压缩

- **单个共享草稿头**：用同一个 4 层 Transformer 递归预测多个候选，而非为每个位置配置独立模块。输入融合目标模型最终隐状态与当前 token embedding；后续步骤再注入上一步草稿隐状态和新预测 token，同时保留主模型语义与当前分支信息。训练只看未来 3 步，推理可递归到更长序列，最终由目标模型并行验证。
- **零拷贝 KV Cache**：草稿层通过交叉注意力直接读取骨干已计算的静态 KV 快照，不复制 Cache，也不重新处理上下文。三个局部层和一个全局层分别访问对应的骨干 Cache；固定位置编码配合递归隐状态表达预测位置，兼顾接受率、延迟与内存。
- **聚类词表投影**：针对 262,144 词表，先计算 2,048 个簇的 logits，再对概率最高的 32 个簇、共 4,096 个 token 精确计算。投影宽度降至 6,144，计算量约压缩 **43 倍**，token 命中率超过 **97%**。

## 实验结论：高接受率不等于高吞吐

统一 H100 测试中，E2B、E4B、12B、31B 分别加速 **1.97、2.33、2.67、3.14 倍**。31B 上，G-MTP 在所有受测前瞻长度均优于 DFlash 和 EAGLE-3；三者最佳加速分别为 3.14、2.60、2.10 倍。

但 Block Efficiency（BE）不是实际速度。26B MoE 虽达到 BE 3.27，小 batch 下仅加速 1.34 倍，前瞻长度 $\gamma\geq10$ 时甚至慢于基线；增大 batch 后，验证成本被并发摊薄，加速进入 1.55–1.71 倍区间。因此草稿不能无限变长，必须联合考察接受收益与硬件成本。

端侧结果同样体现这种权衡：手机 GPU 上 E2B、E4B 分别加速 1.69、2.18 倍；Pixel 11 Edge TPU 上，聚类投影虽减少约 20% 草稿时间，却因接受率下降，仅带来 **1.01 倍**额外端到端收益。

## 微调后仍要对齐草稿器

只微调目标骨干会造成分布失配：SciQA 上目标 NTP Accuracy 达 99.23%，接受率却降至 8.96%，目标前向次数升至 19,423。联合微调目标与草稿器后，接受率恢复至 28.64%，前向次数降至 **10,595**，减少约 **1.83 倍**；GSM8K 的 BE 也恢复至 3.77。两阶段概率蒸馏同样有效，但联合微调整体更佳。

适配采用 LoRA，并以全词表 Total Variation Distance 让草稿器模仿目标的完整概率分布，而非只追逐唯一真实 token。训练前瞻 3 步、评估递归 7 步仍保持较高接受率，验证了共享结构的可扩展性。当前端侧测试仅覆盖 E2B、E4B 和两台设备，内存、能耗及更多硬件上的收益仍待验证。
