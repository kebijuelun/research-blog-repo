# In-fusion：把视觉专用容量嵌入骨干浅层

多模态模型真正需要的或许不是独立视觉编码器，而是只服务视觉 token 的专用容量；这项研究据此兼顾视觉能力与图像请求延迟。从 0.6B 到 6.4B，Encoder-free 追平编码器的 VQA 约需 **3 倍训练算力**，In-fusion 却始终接近编码器；在 1.7B 骨干、0.4B 视觉参数下，两者 VQA 分别为 **49.2 和 48.9**，TTFT 则从 **210 ms 降至 182 ms**。

- **把“编码器”拆成三个变量**：预训练视觉先验、专用视觉容量、融合前放置。所有方案共用骨干架构和公共数据，从零训练，并以 **lifetime compute** 计入预训练、纯文本及多模态阶段的全部算力，避免把上游预训练当作免费。

- **单独预训练并非必需**：固定总算力时，上游预训练会挤占多模态联合训练。1.7B 下 Scratch、MetaCLIP、WebSSL 的 VQA 分别为 **49.0、47.5、49.3**；4B 下 Scratch 也以 **51.2** 领先三种预训练目标。即使预训练免费，ImageNet Top-1 从 80.4% 提升至 84.4%，VQA 反而从 43.2 降至 41.6。视觉数据同样不宜晚到：从第一步加入时 VQA 为 42.5，训练 75% 后才加入仅 34.4。

- **不可省的是视觉专用容量**：严格对照中，Scratch 与 Encoder-free 的 VQA 为 **44.4 对 39.0**，OCR/图表差距达 **13.0 分**。把同样的 0.4B 参数用于加宽或加深共享骨干，只能略增 Text，无法补回 VQA；共享 FFN 甚至需约 0.8B 额外参数，才能追平 0.4B 专用编码器。

- **In-fusion 是“共享主干＋视觉增量”**：共享 attention 与 FFN 保留不变，视觉 token 额外经过 vision-only 的 QKVO 投影和 FFN 分支，再加回 residual stream；分支零初始化，纯文本路径不变。位置消融显示，0.4B 分支放在前八层取得 **45.0** VQA，与 Scratch 的 44.4 相当；放在后八层仅 35.1，说明容量应尽早处理视觉表示，却不必位于融合之前。

- **结论跨规模、跨预算成立**：最长预算下，4B 的 In-fusion QKVO 与 Scratch 仅差 **0.2** VQA；从预训练语言模型继续训练时，In-fusion 达 50.1，也高于 Scratch 的 48.6。它省去独立编码器的串行阶段，在所有测试视觉预算中 TTFT 更低，但具体收益依赖部署方式。

结论仍限于 224×224 多模态训练、最高 6.4B 的 dense 骨干；更高分辨率、交错文本图像、视频及稀疏 MoE 路由仍待验证。
