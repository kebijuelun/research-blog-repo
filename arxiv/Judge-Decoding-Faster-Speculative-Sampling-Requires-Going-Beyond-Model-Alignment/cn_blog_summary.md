# Judge Decoding：推理提速9.7倍

投机解码常把**内容正确、但用词与目标模型不一致**的草稿拒之门外，使长草稿的收益迅速饱和。Judge Decoding 不再只问“目标模型会不会这样说”，而是用目标模型隐藏表示判断“续写是否正确”：8B/405B 配置平均一次接受 **19.7 个 token**，在 HuggingFace 上相对标准解码提速 **9.7 倍**。

## 一、瓶颈在验证标准，而非草稿质量

标准 Speculative Decoding 由小模型起草、大模型并行验证，并按两者概率之比接受候选，以保证输出分布与目标模型一致。但它采用前缀式验证：一个 token 被拒绝，后续候选全部作废。草稿太短，加速有限；草稿太长，早期拒绝又会浪费大量计算。

论文用实验排除了“草稿不够强”的解释：

- GPT-4o 生成的高质量答案，经 Llama-405B greedy 验证，平均也只接受约 **2 个 token**。
- 经过社区审阅的 Wikipedia 人工摘要，同样会因表达方式不同而被拒绝。
- 即使反转模型角色，让 405B 给 8B 当草稿，接受长度也没有提升。

因此，关键不是进一步对齐草稿与目标，而是识别那些**正确但不对齐**的续写。

## 二、用轻量线性裁判放宽验证

作者发现，目标模型处理错误 token 时，深层隐藏表示已包含“矛盾、需要纠正”等信号。于是不额外运行 LLM 裁判，只在目标模型最后一层 Token Embedding 上训练线性分类器，附着于原有前向计算，几乎不增加推理开销。

训练同样轻量：

- 仅 **500 组**人工标注的“问题—正确答案—错误答案”三元组，约 **30k token**。
- 标注错误答案首次出错的位置；正确答案及错误前前缀作为正样本。
- 冻结目标模型，只训练约 **16.4k 参数**，耗时不到 **1.5 小时**。
- 使用加权 Cross Entropy 应对约 20:1 的正负样本失衡，让不确定时更倾向于拒绝。

推理时，Judge 根据 Embedding 给出接受掩码，再与标准验证掩码取**逻辑或**：标准分支保留目标模型原生认可的 token，Judge 分支补入正确但分布不对齐的内容；一旦最终拒绝，后续 token 仍按前缀规则丢弃。

## 三、接受更长，优化框架中依然提速

8B/405B-Judge 的平均接受长度由标准方法的 6.3 提升至 19.7；在 **8 张 H100、8-bit 量化的 gpt-fast** 环境中达到 **3.9 倍加速、129.3 tokens/s**。8B/70B-Judge 也取得 18.8 的平均接受长度，以及 3.0 倍加速、141.8 tokens/s。

质量评估覆盖 GSM8K、HumanEval、MT-Bench、ARC 和 MMLU，Judge 基本保持目标模型表现；相比之下，仅接受目标分布 Top-K 候选的基线明显掉队。不过，这种质量保持来自实验观察，已不再具备标准投机解码的严格分布一致性保证。

## 四、适用边界决定部署价值

Judge Decoding 更适合“**强草稿 + 强目标 + 长候选 + 训练数据覆盖任务分布**”的组合。跨任务并非无损：移除代码样本训练后，HumanEval 从 86.6% 降至 80.4%，虽仍高于草稿模型的 71.3%，却说明新领域仍需相近标注。此外，弱草稿会频繁偏离正确答案，弱目标未必提供可靠的正确性信号，安全风险也需单独验证。

笔者认为，这项工作的核心贡献是把加速重心从“让草稿更像目标”转向“判断答案是否真的正确”。下一步需要以更少标注覆盖新领域，并为放宽后的验证建立可量化的质量与安全保障。
