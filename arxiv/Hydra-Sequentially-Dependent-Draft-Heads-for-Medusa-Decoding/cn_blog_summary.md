# Hydra：顺序草稿让解码提速 2.70 倍

大语言模型逐 Token 解码常受内存带宽限制，投机解码虽能“先猜后验”，Medusa 的多个草稿头却看不到彼此预测，浪费了候选文本中的顺序依赖。Hydra 将前序候选 Token 接回后续草稿头，在几乎不改基础模型的前提下提高接受率；Hydra++ 最终相对 Medusa 最高提速 **1.31 倍**，相对普通自回归解码最高提速 **2.70 倍**。

## 从各自为战到顺序预测

Medusa 在基础模型隐藏状态上挂多个轻量 Draft Head，并行预测未来 Token，再由基础模型一次验证整棵候选树。问题是所有头只读取同一隐藏状态：第二个头不知道第一个头猜了什么，后续预测因此丢失自然语言中的上下文依赖。

Hydra 的改动很直接：

- 第 $i$ 个头同时读取基础模型隐藏状态，以及此前候选 Token 的 Input Embedding。
- 草稿头仍是轻量 MLP，无需修改基础模型，可直接替换标准 Draft Head。
- 论文报告平均候选接受长度最多增加 **0.46 个 Token**；仅这一顺序依赖改动，就使 Hydra 比 Medusa 快约 **10%–11%**。

## Hydra++：更准，也要更便宜

顺序信息之外，Hydra++ 叠加三项增强：

- **Scaling**：草稿头 MLP 扩至 4 层，提升表达能力；5 层及以上没有额外收益。
- **Distillation**：学习基础模型的下一 Token 分布，让训练目标直接对齐验证对象。
- **Prefix Attention**：增加草稿专用 Self-Attention Decoder Layer，为所有头提炼上下文；每轮只需额外调用一次，不参与基础模型正常生成。

更准的草稿还需要合适的候选树。论文先按节点规模逐步扩展树，近似最大化期望接受长度，再在目标硬件和 Batch Size 上实测吞吐，选择最快的树，而非候选最多的树。

## 速度收益经得起多场景检验

在 Vicuna 7B、13B、33B 上，Hydra++ 相对自回归解码分别提速 **2.70、2.50、2.53 倍**，相对 Medusa 分别提速 **1.27、1.27、1.31 倍**。Greedy Verification 保证输出与基础模型贪心解码一致，因此比较的是纯粹速度。

- Batch Size 从 1 增至 8 后，Hydra++ 相对普通解码的加速由 **2.70 倍**降至 **1.63 倍**，收益收窄但未消失。
- SpecBench 的 8B 模型测试中，Hydra++ 覆盖对话、翻译、摘要、问答、数学和 RAG，平均加速 **2.17 倍**，相对 Medusa 平均吞吐提升 **1.24 倍**。
- 相比 EAGLE，Hydra++ 接受长度约为其 **0.92 倍**，吞吐却约为其 **1.01 倍**：实际速度不只取决于猜得准，也取决于草稿成本。

这项工作的核心启示是：顺序依赖不是草稿模型的可有可无细节，但接受长度也不等于最终速度；只有扣除草稿与验证开销后的真实吞吐，才能判断设计是否值得。大 Batch 收益收窄、摘要与 RAG 加速较弱，仍是后续需要解决的问题。
