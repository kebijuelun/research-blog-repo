# REST：用检索替代草稿模型，免训练加速大模型解码

大模型推理慢的根源是自回归逐 token 生成：每产出一个 token 都要把几十亿参数从显存重新加载一遍。主流投机解码虽能加速，却需要为每个大模型专门训练一个"合身"的小草稿模型，工程门槛极高。北大与普林斯顿的工作 REST 给出了更轻的答案：**把参数化草稿模型换成一个非参数化检索数据库，直接从语料里"查"出候选草稿**，零训练、即插即用。单卡单 batch 设定下，REST 对 7B/13B 模型实现 **1.62×–2.36×** 无损加速，且在 HumanEval 上优于调参到最优的草稿模型版投机解码（11.82 vs 15.90 ms/token）。

## 核心思路

文本生成中存在大量反复出现的高频片段——写出 `for i` 之后大概率是 `in range(`。这类"套路"不必算出来，查出来即可。REST 的推理分三步：

- **检索**：用后缀数组做精确后缀匹配，贪心地从 $n_{max}=16$ 逐步缩短查询，找到 datastore 中与当前上下文最长后缀匹配的"上下文-续写"对。检索+建 Trie 平均耗时**不到 1ms**。
- **选草稿**：把所有候选续写插入一棵 Trie，按前缀频次用最大堆保留 top-64 高频节点，剪去低频分支——频次替代了小模型的"置信度"。
- **验证**：将 Trie 子树按 BFS 拍平成伪序列，配合 tree attention mask 一次前向验证整棵草稿树；草稿是否接受完全由大模型自身采样决定，输出与标准自回归**逐字一致**（无损）。

相比投机解码，REST 不依赖小模型、不占额外 GPU 显存（检索在 CPU 上跑）、不受词表和架构约束，换任何 LLM 接上就能用。

## 实验结果

- **代码域**：HumanEval 上 CodeLlama 7B/13B 提速 2.12×–2.36×，greedy 下 7B 的 27.89 ms/token 压到 11.82 ms。
- **对话域**：MT-Bench 上 Vicuna 7B/13B 提速 1.62×–1.77×，低于代码域——开放文本重复片段更少，命中率先天受限。
- **datastore 越大越快且未饱和**：代码库从 0.9GB 扩到 27GB，加速比从 1.83× 单调升到 2.36×，检索耗时仅从 0.2ms 涨到 0.7ms；即便 465MB 小库也能稳定拿到 1.5× 以上加速。
- **消融验证**：Trie 频次选择优于随机采样（11.82 vs 12.80 ms）；草稿 token 超过 48 个后边际收益消失；$n_{max}$ 超过 6 即无感，实际命中以长度 2–9 的短匹配为主（约 85%）。

## 局限与展望

作者坦承两点短板：效果依赖 datastore 的质量与覆盖度；精确匹配缺乏语义理解，无法处理"个性化变量名"这类上下文相关内容。REST 的最大启示是把"加速解码"从模型问题变成了数据问题——收益随 datastore 规模持续爬坡，更大规模的检索基建乃至与投机解码、RAG 的合流，是这条路线最值得期待的方向。
