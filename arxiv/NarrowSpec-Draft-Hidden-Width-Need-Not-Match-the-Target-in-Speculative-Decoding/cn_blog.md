# NarrowSpec：缩窄投机解码草稿，GB10最高提速1.44倍

投机解码里的草稿模型通常直接继承目标模型的隐藏宽度，但这条“默认配置”会让草稿的每一层投影和词表头都付出不必要的开销。NarrowSpec 的核心做法很直接：让 DFlash、EAGLE-3 草稿的整条残差流只保留目标模型的一半或四分之一宽度，再用边界 Adapter 对接目标模型。在 880 条 SPEED-Bench 提示、batch 1、temperature 0 的设置下，B200 端到端解码提速 **1.06–1.12 倍**，DGX Spark（GB10）提速 **1.13–1.44 倍**。更重要的是，半宽在 B200 上最多只损失 3.0% 的接受长度，四个“草稿族—目标模型”组合中有两个没有下降。

## 投机解码的瓶颈，不只是“猜得准不准”

先把投机解码（Speculative Decoding，SD）想象成“草稿先写、目标审稿”：小模型连续提出候选 token，目标模型用一次批量前向同时验证，并接受最长的正确前缀。这样，一次目标模型前向可以提交多个 token。

两个指标决定了最终速度：

- **接受长度** $\mathrm{AL}$：每次验证平均提交多少 token。
- **单次迭代耗时** $T_{\mathrm{iter}}$：草稿生成与目标验证一共花多少时间。

每个输出 token 的解码延迟 $\mathrm{TPOT}$ 可以写成：

$$
\mathrm{TPOT}=\frac{T_{\mathrm{iter}}}{\mathrm{AL}},\qquad
T_{\mathrm{iter}}\approx t_{\mathrm{verify}}+t_{\mathrm{draft}}
$$

这个公式把优化路线分成了两类。一类提高 $\mathrm{AL}$，例如利用目标隐藏状态、增加预测头或构造候选树；另一类降低 $T_{\mathrm{iter}}$，例如缩短草稿上下文、减少层数、裁剪词表或提前停止草稿。

NarrowSpec 关注的是后者中一个很少被单独研究的维度：**草稿残差流的隐藏宽度**。DFlash、EAGLE-3 和 MTP（Multi-Token Prediction，多 token 预测）等特征条件草稿都会读取目标模型的隐藏状态，因此工程上往往顺手把草稿宽度也设成目标宽度。但“输入来自目标模型”并不意味着“中间每一层都必须和目标一样宽”。

这个区别很关键：压缩词表只减少最后一步，缩减 MLP 只影响一部分层，而缩窄残差流会同时缩小所有读取或写入它的投影矩阵。

## NarrowSpec：只改宽度，不改草稿范式

记目标模型和草稿模型的隐藏宽度分别为 $d_t$、$d_d$，词表大小为 $V$，隐藏状态分别为 $h_t\in\mathbb{R}^{d_t}$ 和 $h_d\in\mathbb{R}^{d_d}$。NarrowSpec 将草稿宽度设为：

$$
d_d=\frac{d_t}{2}\quad\text{或}\quad d_d=\frac{d_t}{4}
$$

草稿仍然从目标模型读取 $d_t$ 宽的特征，也仍然对目标词表打分；变化的只是草稿内部用于传递信息的残差流。

![NarrowSpec 的全宽与半宽草稿层](figs/fig_method_overview.tex)

> 图解：上方是宽度为 $d_t$ 的全宽 DFlash 草稿层，下方是 $d_d=d_t/2$ 的半宽版本。蓝色残差流按 2:1 画出，所有读取或写入残差流的 QKV、O、MLP gate/up、MLP down 和词表投影都会缩小；灰色 Attention 内部计算与 MLP 中间维度保持不变。半宽模型只在入口增加 $d_t\to d_d$ 的 Input Adapter。

这里有一个容易误解的地方：**缩窄并不会把所有计算都缩小。** Attention head 数量、head dimension 和 MLP intermediate size 都保持不变，因此 Attention 本身和草稿 KV cache 的大小不变。真正缩小的是各层投影、目标特征接入投影以及词表投影。

这个设计的聪明之处在于，它没有另造一种草稿算法，而是把“宽度”变成可独立调节的架构轴，因此可以同时作用于并行草稿和自回归草稿。

### 两类草稿，覆盖两种典型服务路径

论文选择 DFlash 和 EAGLE-3，不只是因为它们常用，还因为它们在“如何生成草稿”和“如何使用词表头”上恰好形成对照。

| 设计项 | DFlash | EAGLE-3 |
|---|---|---|
| 草稿主体 | 5 / 8 层堆叠 Decoder（Qwen3-8B / GPT-OSS-20B） | **1 层** Decoder，顺序运行 $k=7$ 次 |
| 草稿方式 | Block-parallel，每个 anchor 一次生成一个 block | 自回归链 |
| LM head | 借用冻结的目标头，形状为 $V\times d_t$ | 自训练头，形状为 32K / 64K $\times d_d$ |
| 窄宽度下的输出头 | 折叠为 $W_{\mathrm{fold}}=W_{\mathrm{lm}}W_{\mathrm{out}}$，形状为 $V\times d_d$ | 本身已处于 $d_d$，无需折叠 |
| 服务时 Input Adapter | 保留运行时 GEMM，耗时 4.2–7.2 μs | **为零**，已折叠进 `embed_tokens` |
| Output Adapter | $d_d\to d_t$，加载时折叠消除 | 无 |
| 读取目标层数 | 5 层 | 3 层 |

DFlash 每轮处理一个 bonus token 和 $k-1$ 个 mask token，通过一次前向提出 $k-1$ 个候选。Qwen3-8B 上 $k=16$，GPT-OSS-20B 上 $k=8$。

![DFlash 的一轮解码与宽度作用位置](figs/fig_serving_path.tex)

> 图解：DFlash 一轮分为目标验证、上下文预处理、草稿前向三段。蓝色模块运行在草稿宽度 $d_d$，灰色模块保持目标宽度 $d_t$ 或不受宽度影响。训练时的橙色虚线路径先经 Output Adapter 回到 $d_t$，再使用目标的冻结 LM head；部署时，这两次线性映射被合成一个窄头。

EAGLE-3 则是单个 Decoder layer 自回归运行 7 步。第 1 步读取刚被目标接受的 token 及三层目标特征；第 2–7 步读取草稿自己上一步的 token 和隐藏状态。它使用裁剪后的草稿词表：Qwen3-8B 为 32,000 / 151,936，GPT-OSS-20B 为 64,000 / 201,088。

![EAGLE-3 的一轮解码与宽度作用位置](figs/fig_serving_path_e3.tex)

> 图解：EAGLE-3 的同一层顺序执行 $k$ 次。第 1 步的 $3d_t$ 目标特征先由 `fc` 压到 $d_d$；后续步骤将草稿 token embedding 与隐藏状态拼成 $2d_d$。橙色虚线是训练时的目标 embedding 加 Adapter，导出时二者合成草稿自己的 $V\times d_d$ 窄 embedding 表。

这两个案例说明，宽度压缩并不依赖某一种特定草稿机制：DFlash 借用完整目标词表头，EAGLE-3 自带裁剪词表头，两者都能受益。

### 训练时：从头训练窄草稿，而不是切掉全宽模型

NarrowSpec 的窄草稿都在目标宽度下**从头训练**，并非训练完再剪枝。只要草稿遇到目标宽度张量，就放置 Adapter：

- `fc` 将 DFlash 的 $5d_t$、EAGLE-3 的 $3d_t$ 目标特征压到 $d_d$，保证后续每层都读取窄输入。
- 目标 token embedding 来自 $V\times d_t$ 的表，因此需要 $d_t\to d_d$ 的 Input Adapter。
- DFlash 的 Context K/V 投影直接读取 `fc` 的输出，所以自然变窄，不需要额外 Adapter。
- DFlash 借用目标 LM head，需要 Output Adapter 将 $d_d$ 映射回 $d_t$；EAGLE-3 的头直接在 $d_d$ 上训练，不需要这一步。

宽度变化后，训练超参数也要重新选择。EAGLE-3 每减半一次宽度，学习率就翻倍，初始化范围也按宽度调整；直接照搬全宽配置并不是作者推荐的做法。

| 草稿族 | 目标模型 | 宽度 | Learning rate | `initializer_range` |
|---|---|---:|---:|---:|
| DFlash | 两者 | 所有宽度 | 6e-4 | 默认 |
| EAGLE-3 | Qwen3-8B | 4096 / 2048 / 1024 | 2e-4 / 4e-4 / 8e-4 | 0.005 / 0.01 / 0.02 |
| EAGLE-3 | GPT-OSS-20B | 2880 / 1440 / 720 | 3e-4 / 6e-4 / 1.2e-3 | 0.007 / 0.02 / 0.028 |

### 部署时：把两个线性映射折叠成一个

如果 DFlash 按训练结构直接部署，每轮仍要执行 Output Adapter，再读取完整的目标 LM head。这会重新引入全宽开销，削弱窄草稿的收益。

由于最终 Norm 位于 Output Adapter 之前，Adapter 与 LM head 之间没有非线性，两个矩阵可以在加载时一次性合成：

$$
W_{\mathrm{lm}}(W_{\mathrm{out}}h_d)=W_{\mathrm{fold}}h_d
$$

$$
W_{\mathrm{fold}}=W_{\mathrm{lm}}W_{\mathrm{out}}\in\mathbb{R}^{V\times d_d}
$$

![DFlash 的 LM head 折叠](figs/fig_folding.tex)

> 图解：朴素路径是 $h_d\to W_{\mathrm{out}}\to W_{\mathrm{lm}}\to\text{logits}$，仍要运行完整目标头；折叠路径在加载时计算 $W_{\mathrm{fold}}=W_{\mathrm{lm}}W_{\mathrm{out}}$，服务时只需一次从 $d_d$ 到 $V$ 的 GEMM，Output Adapter 完全消失。

折叠在代数上是精确的，但浮点舍入位置会改变：原路径逐 token 将中间激活 $h_{\mathrm{up}}$ 舍入到 BF16，折叠路径则在加载时一次性将 $W_{\mathrm{fold}}$ 舍入到 BF16。因此两者不保证 bit-level 一致，却不涉及额外近似算法。

EAGLE-3 在导出时也可将 Input Adapter 乘进目标 embedding 表，得到草稿自己的 $V\times d_d$ 表。半宽时这张表约占 0.6 GB BF16 显存；如果显存紧张，也可以不折叠，改为在 7 个草稿步骤中逐步运行 Adapter。

DFlash 虽然也能折叠输入侧，但它的 Input Adapter 每轮只运行一次，而 EAGLE-3 要顺序运行 7 次，所以论文对 DFlash 保留运行时 Adapter，对 EAGLE-3 默认折叠。

### 为什么草稿耗时可以独立于接受率分析

每轮草稿提出的 token 数是固定的：DFlash 为 $k-1$，EAGLE-3 为 $k$，而不是目标最终接受的数量。DFlash 每轮都处理完整 block；EAGLE-3 每轮都执行全部 7 次前向，SGLang 在 CUDA Graph 下还将第 1 步 padding 到 8 个位置。

因此，接受率主要改变写入草稿上下文的 token 数，而不是本轮草稿的计算形状。于是一阶近似下，$T_{\mathrm{iter}}$ 由宽度和 $k$ 决定，$\mathrm{AL}$ 由训练质量决定，二者可以分开测量。这也是 NarrowSpec 能清楚解释“更快迭代”与“接受率损失”如何共同决定最终速度的原因。

## 实验怎样保证“只比较宽度”

论文在两个目标模型上分别训练 DFlash 和 EAGLE-3，形成四个 cell；每个 cell 都有全宽、半宽、四分之一宽三个版本。深度、Attention head 几何、MLP intermediate size、词表、训练数据、数据顺序和 seed 均保持一致，窄模型只改变 `hidden_size` 并增加边界 Adapter。

| 目标主体 / head 精度 | NVFP4 / BF16 dense | MXFP4 MoE / BF16 dense |
| 目标隐藏宽度 $d_t$ | 4096 | 2880 |
| 目标词表 $V$ | 151,936 | 201,088 |
| 每 epoch 语料样本 / token | 799,936 / 587M | 788,544 / 1.04B |
| 训练回答生成长度上限 | 512 | 2048 |
| DFlash 宽度 | 4096 / 2048 / 1024 | 2880 / 1440 / 720 |
| DFlash 层数 / intermediate size | 5 / 12,288 | 8 / 7,680 |
| DFlash block size $k$ | 16 | 8 |
| DFlash 可训练参数（全 / 半 / 四分之一） | 1048.6M / 541.1M / 270.5M | 784.8M / 400.7M / 200.4M |
| DFlash 训练与报告 checkpoint | 6 epochs；报告 ep. 5，2.94B tokens | 6 epochs；报告 ep. 6，6.26B tokens |
| DFlash global batch | 16 | 64 |
| EAGLE-3 宽度 | 4096 / 2048 / 1024 | 2880 / 1440 / 720 |
| EAGLE-3 层数 / intermediate size | 1 / 12,288 | 1 / 2,880 |
| EAGLE-3 Q / KV heads，head dimension | 32 / 8，128 | 64 / 8，64 |
| EAGLE-3 草稿步数 $k$ | 7 | 7 |
| EAGLE-3 草稿词表 | 32,000 / 151,936 | 64,000 / 201,088 |
| EAGLE-3 可训练参数（全 / 半 / 四分之一） | 399.5M / 208.2M / 104.1M | 275.4M / 141.8M / 70.9M |
| EAGLE-3 训练与报告 checkpoint | 3 epochs；报告 ep. 3，1.76B tokens | 3 epochs；报告 ep. 3，3.13B tokens |
| EAGLE-3 global batch | 64 | 64 |

训练提示来自 Nemotron-Post-Training-v2 英文数据和 CodeAlpaca，只保留 user turns；assistant 回答全部由对应目标模型在 temperature 0 下重新生成。这样草稿学习的是目标自己的输出分布。所有版本使用 SpecForge 在 4 张 B200 上从头训练，AdamW、cosine schedule、4% warmup、gradient clipping 1.0，序列最长 3072 token。

需要强调：这是在**相同数据预算**下的比较，而不是各宽度都训练到收敛。窄草稿达到同一预算所需训练算力更少，但不同预算下的接受率差距仍可能变化。

推理侧使用 SGLang 0.5.18 nightly、paged KV、CUDA Graph 和 overlap scheduling，关闭 radix cache。主评测包含：

- SPEED-Bench qualitative split：11 类、每类 80 条，共 880 条提示。
- temperature 0 和 1，seed 7，batch 1，最多生成 4096 token，上下文 32,768。
- 另测 GSM8K、MATH-500、AIME25、HumanEval、MBPP、LiveCodeBench、MT-Bench、Alpaca 八个基准。
- 硬件以 B200 和 GB10 为主，另在 H100 上复现 DFlash-Qwen3-8B。

$\mathrm{AL}$ 采用 pooled 口径，即全评测集的完成 token 总数除以验证步数，因此长回复的权重更大；$\mathrm{TPOT}$ 只衡量 decode，不包含 prefill。

## 主结果：半宽已经够用，更窄是否划算取决于硬件

可以读出三个结论：

1. **迭代耗时随宽度稳定下降**，四个 cell 最高加速 1.16 倍；端到端差距主要来自 $\mathrm{AL}$。
2. **半宽几乎没有接受率代价**。DFlash-Qwen 和 EAGLE-3-GPT-OSS 还分别高出 0.84% 和 2.11%，但每个版本只有一次训练、一个 seed，应理解为持平而非稳定增益。
3. **四分之一宽不总是更快**。它在 DFlash-Qwen 上因 5.44% 的接受率损失输给半宽，在另外三个 cell 则最快或与半宽持平。

换句话说，NarrowSpec 不是“越窄越好”，而是把原本隐藏的容量—延迟权衡暴露出来。

### GB10：同一批 checkpoint，收益明显放大

在带宽更低的 DGX Spark（GB10）上，四分之一宽在四个 cell 中全部成为最快版本。

| 草稿族 | 目标模型 | 半宽 $\Delta\mathrm{AL}$ | 四分之一宽 $\Delta\mathrm{AL}$ | 半宽端到端提速 | 四分之一宽端到端提速 |
|---|---|---:|---:|---:|---:|
| DFlash | Qwen3-8B | −0.17% | −6.17% | 1.20× | **1.26×** |
| DFlash | GPT-OSS-20B | −2.02% | −3.89% | 1.13× | **1.20×** |
| EAGLE-3 | Qwen3-8B | −3.02% | −2.81% | 1.21× | **1.44×** |
| EAGLE-3 | GPT-OSS-20B | +0.33% | −2.65% | 1.23× | **1.34×** |

接受率损失与 B200 相差不超过 1.8 个百分点，所以额外收益不是评测变化造成的，而是窄草稿在 GB10 上真正运行得更快。GB10 的半宽迭代提速为 1.15–1.25 倍，四分之一宽为 1.24–1.48 倍；B200 对应只有 1.07–1.12 倍和 1.11–1.16 倍。

### 分布外基准与 temperature 1：加速并不只存在于主评测集

八个数学、代码和聊天基准上，三个 cell 的半宽接受长度都在全宽的 2.2% 以内；DFlash-Qwen 在 8 个基准中的 5 个还高于全宽。EAGLE-3-Qwen 的半宽损失较大，为 4.3–6.2%；四分之一宽在任一基准上的损失都不超过 7.4%。

### 只缩 MLP 或只缩词表头，为什么不够

按实测操作成本估算，在四个 cell 中的三个，即使完全删除词表头或整个 MLP，也无法达到四分之一宽的草稿延迟降幅。例如 DFlash-Qwen 上，删除 head 和 MLP 分别只能节省 206、271 μs，而缩窄总共节省 390 μs。

## 为什么低带宽 GPU 受益更多

## 附录里的三个关键问题

### 折叠真的不会改变结果吗

作者用 29 条评测集提示中的 3405 个真实半宽 DFlash-Qwen 隐藏状态，比较 folded、unfolded 两条 BF16 路径与 FP64 参考。归一化 RMS 定义为：

$$
\frac{\lVert Z-Z_{64}\rVert_F}{\lVert Z_{64}\rVert_F}
$$

| BF16 路径 | 最大绝对误差 | 归一化 RMS | Top-1 与 FP64 相同 |
|---|---:|---:|---:|
| folded（实际部署） | 0.251 | 0.20% | 97.2% |
| unfolded | 0.270 | 0.21% | 97.0% |

折叠路径反而略接近 FP64。两条路径约 3% 的位置与 FP64 argmax 不同，但都发生在前两名 logit 几乎持平的位置；二者彼此在 99.1% 的位置上给出相同 top-1。

在 880 条提示、temperature 0 的成对端到端运行中，半宽和四分之一宽 checkpoint 的每条输出都 token-identical，$\mathrm{AL}$ 差异不超过 0.03%。不折叠反而因每轮读取完整 $V\times d_t$ 头，使每轮分别慢 3.1% 和 4.7%。

这里的准确表述不是“任何精度下 bit-level 完全相同”，而是：**代数映射相同，有限精度下只有舍入差异。** 量化场景还要更谨慎，因为通常有：

$$
Q(W_{\mathrm{lm}}W_{\mathrm{out}})\neq Q(W_{\mathrm{lm}})W_{\mathrm{out}}
$$

论文的 NVFP4 版本先从 BF16 头折叠，再只量化一次；没有评估“先量化目标头再折叠”的路径。

### 折叠头会占额外显存，窄草稿一定更省显存吗

### 缩窄与量化能否叠加

作者在 DFlash-Qwen 上比较三种宽度的 BF16 与 NVFP4 W4A4 后训练量化版本。Decoder GEMM 和词表投影使用 FP4 权重、FP4 激活，`fc`、Input Adapter、Norm、Attention 和 KV cache 保持 BF16。

| full 4096 | BF16 | 4.298 | — | 3.585 | 0.834 | — | — | 1.00× |
| half 2048 | BF16 | 4.334 | — | 3.313 | 0.764 | — | — | 1.09× |
| quarter 1024 | BF16 | 4.064 | — | 3.197 | 0.787 | — | — | 1.06× |

两者可以组合，但量化的边际收益随宽度缩小：全宽量化让迭代快 1.09 倍，半宽只有 1.04 倍，四分之一宽只有 1.02 倍。原因包括每个 FP4 投影仍需单独的激活量化 kernel，合计约 48 μs/step，以及小 FP4 GEMM 已触及约 5 μs 的耗时下限。

在 batch 1 的这一组实验中，单纯半宽 BF16 的 1.09× 已优于全宽量化的 1.07×，且没有接受率损失；半宽加量化达到最快的 1.11×，但四分之一宽加量化相对同宽 BF16 只剩 0.99×。

## 还有哪些边界与可组合方向

NarrowSpec 与已有工作并不是简单的替代关系：

- FR-Spec、VocabTrim、NanoSpec 压缩词表维度，NarrowSpec 压缩隐藏维度，二者有潜力互补。
- SlimSpec 只在词表投影中加入低秩瓶颈，草稿层仍保持全宽；NarrowSpec 同时缩小投影与所有草稿层。
- MagicDec、LongSpec、SpecExtend 和 windowed drafting 缩短草稿关注范围，self-speculative 方法减少使用的目标层数；它们优化的是上下文或深度，而 NarrowSpec 优化特征宽度。
- EAGLE-3 本身已有裁剪词表，实验说明即使如此，继续缩窄隐藏宽度仍能进一步缩小投影。
- 对内置 MTP drafter，论文尚未实测，但其借用完整词表头、逐步自回归生成候选的结构可能让词表头开销更突出；折叠窄头因此是值得验证的方向。

分类实验也揭示了不能忽略的失败案例。四分之一宽 DFlash-Qwen 在 RAG 上损失 14.8% $\mathrm{AL}$，端到端只有 0.95×；多语言类为 1.00×。RAG 的大幅下降主要来自 80 条提示中的 7 条，它们的提示与回答总长超过训练序列的 3072 token：这 7 条上四分之一宽比全宽少接受 38%，其余 73 条只少 2.5%。这提示训练长度覆盖与模型容量会共同影响极窄草稿的适用范围。

最后需要保留论文自己给出的限制：

- 每个变体只有一次训练、一个 seed，比较的是相同数据预算而非收敛状态。
- 只测试两类草稿和两个目标模型；draft 占整轮比例更小的目标，收益可能更低。
- 上下文扫描止于 32k，由于 KV Attention 不缩小，更长上下文下收益预计继续下降。
- MLP-only 消融使用未训练切片，只比较延迟，不能替代真实训练后的容量对照。
- 量化只覆盖 DFlash-Qwen、batch 1 和后训练量化，其他组合、大 batch 与 quantization-aware training 仍待研究。

## 结论：草稿宽度应该独立设计，而不是照抄目标模型

- **核心发现**：在论文评测范围内，DFlash 和 EAGLE-3 的草稿残差流无需与目标模型同宽，半宽或四分之一宽仍能保持较高接受率。
- **核心机制**：缩窄整条残差流会同时缩小 Decoder 投影、目标特征接入和词表投影，而不是只优化单个组件。
- **关键工程技巧**：DFlash 将 Output Adapter 与借用 LM head 一次性折叠，部署时只运行窄头；EAGLE-3 可折叠输入 embedding，但需权衡常驻显存。
- **最强结果**：batch 1、temperature 0 下，B200 端到端提速 1.06–1.12 倍，GB10 提速 1.13–1.44 倍；大 batch 下最高均达 1.21 倍，且没有窄草稿慢于全宽。
- **实践建议**：B200 这类数据中心 GPU 可优先尝试半宽，GB10 这类低带宽设备更值得尝试四分之一宽；同时要重新调学习率与初始化，并确认词表投影也真正变窄。

未来更值得追问的不是“草稿还能否继续变窄”，而是如何在目标硬件、训练预算和任务分布上联合选择宽度，并将这一维度与窗口化草稿、词表裁剪和量化组合起来。
