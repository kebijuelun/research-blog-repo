# SpecOPD：分支并行让监督吞吐提升 16.09 倍

推测解码能加速大模型生成，但在线策略蒸馏（OPD）仍被“起草—验证—接受—再采样”的串行流程拖住，造成训练 GPU 大量等待。SpecOPD 将不同参考位置的草稿分支并行采样、评分，并复用公共前缀计算：在 Qwen3.8-27B、8 张高性能 GPU 的原生配置下，监督 Token 吞吐达到顺序 rollout OPD 的 **16.09 倍**；另一组 27B serving 实验中，生成吞吐最高达到自回归解码的 **3.56 倍**。

## 关键转折：监督不必等待完整轨迹

传统 Draft-OPD 必须先验证当前块，才能确定下一轮采样起点。SpecOPD 发现，训练一个草稿块只需要两类信息：

- **参考前缀**：确定锚点之前的上下文；
- **当前 Drafter 的采样历史**：构造锚点之后的真实预测历史。

因此，不同锚点可以独立生成局部分支，Target 无需先判断服务时哪些 Token 会被接受。它仍是 On-Policy 训练——分支随当前模型每次更新重新采样——只是外层上下文来自离线参考响应。笔者认为，这一拆解的价值在于把“是否接受”从数据采集的前置条件，转变成 Loss 中的优化目标。

## Proposal Tree：共享前缀，隔离分支

SpecOPD 以参考序列为树干，在多个锚点采出草稿分支，组成 Proposal Tree，再批量交给冻结的 Target 评分。其实现有三个要点：

- **历史一致**：预测某个 Token 时读取其前驱节点的隐状态，避免答案泄漏；分支只能沿祖先路径读取历史。
- **按架构复用**：Full Attention 用 Tree Mask 共享树干 KV；Sparse Attention 重建跨锚点的 indexer group；Linear Attention 从检查点恢复并重放私有状态，防止兄弟分支污染。
- **直接优化接受长度**：E2E-TV 以草稿与目标分布的重叠衡量单点接受概率，再用前缀乘积让早期错误影响后续奖励，而非只优化逐 Token 准确率。

## 实验结论：训练提速显著，收益并非均匀

- **训练效率**：updates/s 提升 **4.95 倍**，每次更新的监督 Token 数提升 **3.25 倍**，二者共同形成 **16.09 倍**吞吐收益。
- **接受长度（AL）**：8B DFlash 在 $T=0$ 时五任务平均 AL 从 2.649 升至 3.747，提升 **41.45%**；27B 最大平均提升仅 **3.48%**，125B 为 **5.01%**。
- **推理吞吐**：27B 上跨五任务几何平均，相对自回归在并发 1、8、32 下分别加速 **2.97×、2.23×、1.35×**，高并发收益明显收窄。
- **On-Policy 必要性**：相同优化步数与参考序列呈现量下，所测 Off-policy checkpoint 的 AL 均低于共同初始化，SpecOPD 则高于初始化，说明 Loss 下降不等于真实解码进展改善。

## 边界与总结

SpecOPD 的核心贡献不是发明新的草稿模型，而是重排 OPD 流水线：**分支内有序、分支间并行，分歧前共享计算、分歧后隔离历史**。但 16.09× 只是原生配置下的监督 Token 吞吐比，不等于端到端收敛加速；它还依赖离线参考数据，且部分对照并非等算力。后续更应比较达到目标 AL 的总训练成本，并验证其在更多 serving 后端、RL 与多模态场景中的收益。
