# Speculative Decoding：一次验证多个 Token

大语言模型逐 Token 生成造成的串行延迟与显存带宽浪费，正抬高实时对话和 Agent 的部署成本；Speculative Decoding 以“低成本起草、目标大模型并行验收”在不放松输出约束的前提下提速。统一评测中，EAGLE 在 RTX 3090、Vicuna-7B、FP16、贪心解码下平均提速 **2.08×**，数学推理达 **2.44×**；A100 上 Medusa 平均提速 **2.42×**。

## 核心机制：便宜地猜，严格地验

自回归解码每生成一个 Token，通常都要重新读取大量模型参数，GPU 计算单元却未被充分利用。推测解码把这一过程改为一轮“起草—验证—纠正”：

- **起草**：独立小模型或目标模型的轻量模块，一次产生 $K$ 个候选 Token。
- **验证**：目标模型并行计算各候选位置的分布，按顺序接受符合条件的 Token。
- **纠正**：在首个分歧位置按目标分布修正，丢弃其后的草稿；若全部接受，还能额外生成一个 Token。

实际收益由**平均接受 Token 数与起草延迟**共同决定：草稿再准，生成草稿太贵也可能变慢。其关键创新是把生成质量与并行度解耦——小模型只提供可能性，大模型保留最终决定权。

## 三条方法主线

- **Drafting**：Independent Drafting 使用外部小模型或检索文本，效果好但增加显存与调度成本；Self-Drafting 复用目标模型的预测头、中间层或特征。EAGLE 以自回归预测头复用 KV Cache 与特征，候选更稳定。
- **Verification**：贪心验证只接受目标模型 Top-1，保证贪心输出一致；Speculative Sampling 通过概率接受与分布纠正，理论上保持目标输出分布。Token Tree 则合并多条候选路径，提高覆盖率，但会增加验证开销。
- **Alignment**：用序列级、分布级或在线知识蒸馏提高起草器与目标模型的一致性，从而提升接受率，而不必同步扩大起草器。

## 统一评测：没有固定加速倍率

Spec-Bench 覆盖多轮对话、翻译、摘要、问答、数学推理和 RAG，共 **480 个样本**，在相同硬件、模型与精度下比较六种方法。

- **任务影响**：RTX 3090 上，PLD 在摘要中达 **2.41×**，但翻译仅 **1.11×**；Lookahead 在翻译上甚至只有 **0.98×**，说明推测机制也可能得不偿失。
- **温度影响**：温度从 0 升至 1，EAGLE 平均提速由 **2.08×** 降至 **1.74×**，贪心结果不能直接代表采样收益。
- **硬件与规模影响**：A100 上 Medusa、Lookahead 明显改善，SpS 却从 **1.77×** 降至 **1.59×**；模型扩大到 13B、33B 后，EAGLE 分别平均提速 **2.53×、2.50×**，表现更稳定。
- **精度影响**：FP32 下各方法收益普遍缩水；论文还指出，FP16 浮点误差可能使实际输出并不始终一致。

## 结论

- 推测解码的价值来自低成本候选与严格验证，而非牺牲质量换速度。
- 方法选择必须结合任务、温度、硬件、模型规模和精度，跨论文倍率不能直接排名。
- 当前评测仅覆盖 Batch Size 1；批量服务中的接受率差异与额外计算仍是关键挑战。

未来更重要的是与批量调度、显存管理等技术协同，在真实负载下稳定降低端到端延迟。
