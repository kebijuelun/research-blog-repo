# PEARL：并行验证与自适应草稿提速 4.43×

大语言模型逐 Token 解码带来的高延迟，是代码生成、数学推理和多轮对话部署的关键瓶颈；PEARL 通过让草稿与验证并行、让草稿长度随接受情况自适应，在不额外训练且不改变目标模型输出分布的前提下，相对自回归解码和原始投机解码最高分别提速 **4.43×** 和 **1.50×**。

## 核心问题：模型互相等待，固定窗口又难适配

原始投机解码（SD）由草稿模型生成候选，再由目标模型批量验收，但两个阶段严格串行：起草时目标模型等待，验证时草稿模型空闲。固定窗口 $\gamma$ 也无法适应不同前缀：过短会打断本可连续接受的草稿，过长则产生将被丢弃的无效计算。

## 两条策略实现真正并行

- **pre-verify：提前验证首个 Token。** 草稿模型生成 $\gamma$ 个候选时，目标模型并行计算原始前缀的分布，用它验证第一个草稿。若被拒绝，后续候选全部丢弃并采样修正 Token，省去整批验证；若被接受，则进入整批验证。
- **post-verify：验证时继续起草。** 目标模型验证当前批次时，草稿模型沿现有候选继续生成下一批。若整批接受，下一批已准备好，省去独立草稿阶段；若中途拒绝，则丢弃错误分支及后续候选，切回 pre-verify。
- **自适应草稿长度。** 困难片段更早拒绝、少生成，简单片段持续接受、连续生成，实际草稿长度不再恒等于 $\gamma$。所有候选仍沿用原始 SD 的无损验证，因此并行只改变调度，不改变生成分布。

## 理论结论：窗口由速度比直接决定

设目标模型与草稿模型单次前向耗时比为 $c$，PEARL 的最优窗口为 $\gamma'=c$，部署时取最接近的整数，无需按任务搜索接受率与窗口。在接受率独立同分布的假设下，其期望接受 Token 数不低于原始 SD；实验中平均接受数最高达 **39.90**，而原始 SD 在各组配置中仅为 **5.27～8.32**。

## 实验结果与部署代价

- **HumanEval：** PEARL 在全部 6 组模型配置中取得表内最佳，CodeLlama 7B&70B 达 **4.43×**，原始 SD 为 **3.03×**。
- **GSM8K 与 MGSM：** 11 个语言项均超过基线，平均 **3.95×**，原始 SD 为 **2.70×**。
- **MT-bench：** Llama 2 7B&70B 八类子任务平均 **2.64×**，原始 SD 为 **1.89×**；Llama 3.1 上平均由 **2.42×** 提升至 **3.59×**。
- **消融：** 去掉任一策略都会变慢，去掉 post-verify 的下降更明显，说明持续并行起草贡献更大。

PEARL 的优势是更短墙钟时间，而非更少计算：前向总次数约增加 **1.29～1.42×**，部署需考虑额外计算与功耗。资源充足时可分卡运行；资源竞争时可利用流水线空档并转移 KV Cache，实验保留约 **89%～99%** 的原始性能，但最高加速比不能直接外推到所有硬件与负载。
